# API Design Philosophy

This document explains the design principles and conventions of the FsusBlog API layer. It is a **required prerequisite document** for all API changes.

> Latest update: 2026-07-19 — RiskControl combined challenge converges to UUIDv7 envelope, ordered member progress and a single aggregate proof.

## Minimal Disclosure of Strong-anonymity Eligibility

The public statement of `fsus.anonymous.comment.v5` / layout `6` only permits root/version/hash binding, scope-bound nullifier, and `is_eligible`, `may_comment`, `rate_class` (only `common|unknown`), and `requires_moderation`. Precise credential epoch, credential tier, reputation bucket, and account age can only be used as private witnesses under signed constraints; they must not enter request responses, tickets, comment projections, moderation, providers, statistics, or admin DTOs. The public predicate combination in production must have at least 20 members; if insufficient, it can only be merged into common/unknown and re-proven; if merging is not possible, it must fail closed.

## Core Principles

### 1. Contract Stability First

- Once an endpoint path is published, non-breaking semantic changes are stacked on the original path; breaking changes must be expressed through new frame types, payload layouts, explicit route segments, or new endpoints, and must not arbitrarily reuse old path semantics.
- All request/response fields use `src/shared/Contracts/Outputs/ServerResponseContracts.cs` as the single source of truth; no business logic layer may define its own parallel DTOs.
- The notification stream transport must not guess event importance on its own. All active events must be explicitly declared by a shared delivery policy catalog regarding ordering, durability, loss/coalescing, priority, maximum useful age, and replay/resync; unknown types fail closed. Replacable events may only be merged in the live shallow lane; durable backlog, cursor, and AEDS payload remain unchanged; when lossless enqueuing fails, an explicit replay/full-resync directive must be sent to the client.
- Hand-written machine-readable sources of cross-language security protocols are placed in `src/shared/Contracts/Validation/Security/`, and are derived by the cross-stack generators in `tools/contracts/` only for C# and TypeScript consumers; the root-level `contracts/security/` and single-side `tools/frontend/` must not form a second entry point.
- Request-period network identity can only be generated at the synchronous entry point as usage-isolated, short-epoch rate-limiting/dedup material; no AEDS response, async message, retry/fallback, log, trace, or metric contract may carry raw IP. When dependencies are unavailable, returning a fixed low-cardinality status from existing response frames and discarding statistics is allowed; transferring request context to background compensation is not.
- Anonymous identity mode must not introduce new AEDS frame types that simulate account-bound behavior. New account onboarding must go through `POST /api/binary/auth/anonymous/bootstrap`, request frame `AuthAnonymousBootstrapRequest`; this path only initializes the anonymous account container and the current session, and does not accept user-provided login passwords, nor reuse the old username/password contract. Old `/api/binary/auth/register` and `/api/binary/auth/login` password endpoints are no longer production APIs; the old password-auth request number has been retired from the AEDS frame catalog and cannot be consumed as a legacy/test frame.

### 2. AEDS Binary-only Runtime Protocol

The runtime main business API only exposes the AEDS binary channel:

| Channel | Content-Type | Decoder | Path Prefix |
| ------ | ------------- | ------- | --------- |
| **AEDS Binary** | `application/octet-stream` | TypeScript adapter / C++23 Wasm Worker | `/api/binary/...` |
| **Public AOT hydration sidecar** | `application/vnd.fsus.aeds` | public hydration bootstrap / shell navigation | `/aot-cache/payloads/.../*.aeds` |

Old text business APIs are no longer registered; non-binary business paths under `/api/**` uniformly return the `ApiError` AEDS frame. Clients must not fall back to text API requests on decode failure. Exceptions are limited to standard protocols, health probes, and tooling entries registered in [AEDS-only policy](aeds-only-policy.md). Notification preflight failures return the AEDS `ApiError` frame and no longer return the JSON error envelope; the old JSON entries `/api/read-proof/**`, `/api/public/articles/{id}/related`, `/api/telemetry/rum`, `/api/subscriptions`, `/api/author/**`, and `/api/admin/security/**` have been removed.

The frontend's article reading and post-login private APIs are fixed to consume the current AEDS binary contract; they do not provide user-switchable transport state, nor write transport selection into `localStorage` or `sessionStorage`. Troubleshooting capability can only be observed as in-memory state in development builds explicitly guarded by `import.meta.env.DEV`, and must not change API paths, request frames, credential strategies, or production bundle behavior.

Shared types for frontend binary request/response, worker frame metadata, and decode results are only defined in `src/frontend/src/contracts/`; these contracts do not import runtime modules. The business API, request codec, and response adapter may only depend in the direction of the contract; the response adapter must not reverse-import the API implementation. `services/binaryTransport.ts` only consumes the injected `BinaryFramePayloadDecoder`; the concrete frame mapper is explicitly registered by `composition/binaryDecoderRegistry.ts` and assembled in `composition/binaryTransport.ts` or the decode worker entry. This dependency direction must not change AEDS frame numbers, POD field order, `ApiError` mapping, or binary-only semantics, nor introduce JSON fallback, a second transport, or a compatibility adapter.

Integrity verification sidecars under `/integrity/**` are public JSON manifests, not runtime business APIs and not `/api/binary/**` fallback. Publish proof and Rights V3 proof routes only read persisted proof rows, signing metadata, and transparency log pointers; they do not generate proofs on request and must not expose admin principal id, IP address, user agent, session id, device id, private drafts, comments, private messages, tokens, private keys, or failure details.

The HTTP shell contract is provided by `src/shared/Contracts/Validation/fsusblog.openapi.json`, including method/path/status/content-type/security and `x-fsus-*` extensions; AEDS payload, frame number, POD schema, and golden fixtures are still owned by `aeds-protocol.json`, the POD contract, and the fixtures.

Local/test auxiliary endpoints must not become production identity fallback. Any fixture entry that writes login, admin, or security-state cookies must be limited to Development mapping, and use a separate `X-Fsus-*` shared-secret header for fixed-time comparison; it fails closed when the secret is not configured. Browser fixture activation must also satisfy localhost, `import.meta.env.DEV`, development mode, and non-PROD simultaneously; the activation marker is written to the current tab's SessionStorage and then the fixture query is immediately deleted using `history.replaceState`; the server-side redirect must not add the query back.

### 3. Unified Response Wrapper

All runtime main business response bodies are AEDS v2 frames. Successful write operations use `EmptySuccess` or `MutationId`; creation operations that will be immediately selected, associated, or redirected to by the frontend must return `MutationId` (for example, category, tag, and article creation), and cannot let the frontend guess by refreshing the list and matching by name. Common mutations like category and tag still return the 8B `MutationIdPod`; article create/update/rollback under the same frame type returns the 48B `ArticleMutationResultPod`, simultaneously giving the article, revision, release, status, rights snapshot, idempotency replay flag, `applied/no_change` outcome, and explicit error code; callers must not guess this binding result from the subsequently read "latest state". Failures, authentication denials, rate limiting, and exception fallbacks uniformly use the `ApiError` frame. AEDS v1 frames are no longer compatible, and old frame fallback is not retained.

### 4. Native AEDS Internal API Principle

The production entry of the author workspace `/api/binary/author/**` and the admin security `/api/binary/admin/security/**` must directly implement AEDS v2 frames: the endpoint reads the route-specific request frame itself, successful responses write the route-specific response frame directly, and errors uniformly write the `ApiError` frame. RiskControl control plane reads and runtime writes (`risk-control/overview`, `risk-control/options`, `risk-control/options/rollback`, `challenges/overview`, `policies/overview`) are also only exposed through native binary endpoints, and the `/api/admin/security/**` JSON fallback cannot be restored.

Admin security configuration writes must fail closed: fields such as external URLs, callback addresses, and provider endpoints that can trigger server-side outbound requests must be validated against the allowlist/scheme/port at both the write entry and the use entry; illegal values return `ApiError`, and silent fallback to old or default configuration is not allowed. Crawler range remote URLs only allow HTTPS `developers.google.com` / `www.bing.com`, used to prevent using admin configuration to turn backend workers into SSRF outbound channels.

`JsonApiResponse<T>`, `Results.Ok(JsonApiResponse<...>)`, and `/_fsus/internal/binary-bridge/**` must not be used for runtime internal business APIs. Browser-accessible `/api/binary/**` endpoints must not directly expose JSON envelopes; new business endpoints are designed by default according to [aeds-only-policy.md#internal-application-api-definition](aeds-only-policy.md#internal-application-api-definition), and no runtime compatibility bridge is added. The mounting point is in `src/backend/Infrastructure/Bootstrap/WebApplicationCompositionExtensions.cs`, and the allowlist is in [aeds-only-policy.md#permitted-exemptions](aeds-only-policy.md#permitted-exemptions).

### 5. Authentication Consistency

Authentication requirements are determined by `/api/binary/**` endpoint declarations. Public, login, admin, PoW, MFA, Passkey, and other boundaries must be validated directly within binary endpoints; text endpoints do not exist as permission references.

The signature validity of a normal account bearer token is not equivalent to the session being still valid. All binary endpoints that require a normal account principal uniformly validate `sid` during the JWT `OnTokenValidated` phase: by default, it reads a short TTL Redis L2 version snapshot shared across instances; on miss, Redis exception, or corrupted payload, only one PostgreSQL authoritative fallback is done by the session primary key; database failures fail closed. The fallback is protected by an independent concurrency budget and fault circuit breaker, and uses monotonic `xmin` CAS to best-effort repair Redis; old active snapshots cannot overwrite newer restricted/revoked snapshots. `session_mode=normal|restricted|revoked` is determined by the database state; the JWT claim is only an input hint; when the two are inconsistent, the more restrictive mode is used. Restricted principals are only allowed to read the endpoint-explicitly-declared account status/ban reason, logout, own session viewing and revocation, account deletion, and necessary step-up; other comment, message, content, identity, public, and admin capabilities are denied by default; the notification stream does not accept restricted principals. Single session revocation, other session revocation, and refresh replay DB updates must appear paired with the revoked snapshot publication, so old access tokens become invalid without waiting for JWT `exp`; public hot-read has no authenticated principal and does not enter the session cache/DB path. The admin principal retains an independent admin session validator and does not reuse the normal `sys_user_session`. Implementation and fallback constraints are in [user-session-revocation.md](../user-session-revocation.md).

Refresh Token is a server-stateful opaque credential, not a JWT, and cannot be attributed by the client's `SessionId`. Each user session has a fixed `RefreshFamilyId`; normal rotation only increments generation; the current hash and the used hash tombstone together form the positioning evidence. The loser of atomic CAS and the replay submitted again after commit are different states: the former only returns conflict, the latter exactly compromises the family to which the token belongs. Any compatibility or degradation path must not restore old generation, expand revocation by device fingerprint, or write the full token/hash value to logs. See [Refresh Token lineage](../security/refresh-token-lineage.md).

The security subject of a normal account is the `sys_user.account_subject_hash` physical projection. Migration uses the same C# canonical hasher as the application to backfill in batches; new accounts write this field before returning the bootstrap response; JWT, MFA, binary auth, notification stream, blacklist, and account-state cache can only read the projection value. When missing or malformed, it must fail closed; it cannot be re-derived from account id, public handle, Passkey handle, or old cache payload. Rolling deployment is compatible with old binaries through the nullable Expand column, but candidate accept-traffic must pass the permanent startup invariant gate.

High-value authentication actions can stack RiskControl proof on top of existing binary paths instead of adding parallel login APIs. The production user login entry only retains Passkey, Recovery Key, and necessary step-up; `auth.passkey.begin`, `auth.passkey.complete`, `recovery-key.verify` must declare action through endpoint metadata, and uniformly use `RequiresRiskControlFilter` to return AEDS `ApiError`; missing challenge proof returns 428, block/throttle returns 429. Stacking RiskControl does not remove legacy PoW, admin step-up, or MFA proof boundaries; endpoints that require two proofs must be explicitly registered in [contracts.md](contracts.md#security-challenge-contract) and the header table of this document. `auth.login` is only retained as a legacy risk-control action name, and does not correspond to a production user-side password endpoint.

Browsers are only allowed to accept typed leases of verified proof through the generic binary transport; the transport writes three `X-Fsus-Challenge-*` headers from the lease, and is responsible for single-settlement of pre-send cancellation, in-flight, server response, and unknown network results. Comments, Recovery Key, and Passkey pages must not hand-write headers or copy proof glue. 428 is only normalized at the transport layer by AEDS error code and low-cardinality outcome; business pages do not parse free-form text; automatic continuation is only allowed for idempotent commands or the same command with a fixed mutation identity; possibly sent non-idempotent operations must not be automatically replayed.

The step-up proof for account security credential change must be an action-bound one-time proof token, transmitted via `X-Fsus-Mfa-Proof`. Normal accounts can use the current account Passkey assertion through `/api/binary/auth/step-up/passkey/begin|complete` to exchange for a one-time proof of the corresponding action; this proof uses the same consumption boundary as the proof issued after TOTP challenge completion. The Passkey step-up channel is protected by the independent switch `Auth:PasskeyStepUp:Enabled`, enabled by default; when disabled, begin/complete both return 503 + `PASSKEY_STEP_UP_DISABLED`, and must not generate challenge or mint proof. In anonymous identity mode, Recovery Key create/rotate, Passkey register/delete/rename, account delete and other production sensitive operations must not treat the old `MfaPasswordProofRequest` or the proof in the request body as proof; if the non-anonymous legacy password fallback is retained, it must be isolated to the compatibility path and cannot enter the anonymous production endpoint. Recovery Key passkey bind must not consume the recovery session before WebAuthn validation and database commit; the server must first atomically compare-and-set the session from `pending` to `completing` with a short lease; on failure, restore to `pending`, and provide concurrent single submission and same-request idempotent replay after response loss with a database unique marker of the recovery token hash + normalized completion request hash. The complete state, transaction, and fallback constraints are in [recovery-passkey-completion.md](../recovery-passkey-completion.md).

WebAuthn Level 3 Signal API is only used for best-effort synchronization of browser/provider after server-side account state commit, and must not enter success determination of authentication, registration, deletion, or public naming transactions. The complete credential list must come from the server-authoritative snapshot with monotonic account revision; the frontend coordinates cross-tab through capability cache, timeout/cancel boundaries, BroadcastChannel revision, and Web Locks, and refuses lists observed as expired. Missing API/provider is a normal no-op; the only allowed unknown-credential signal in unauthenticated state must come from the server-side fixed error classification, and cannot be inferred from free-form text, signature error, or risk rejection. The non-restart degradation path for Signal failure is to directly stop calling (capability false or client-side no-op); the server-side business chain remains unchanged.

The AEDS request of Recovery Key verify only carries the Recovery Key plaintext body and revocation option, and does not accept user-input account id. The new Recovery Key plaintext format is `frk_<lookupId>_<secret>`, where `lookupId` is a 128-bit hex random value; the server only uses the peppered `lookup_id_hash` to locate candidate records, then verifies the peppered PBKDF2 hash of the full key. Old keys without lookup id are not scanned across the table for compatibility, and are handled with general failure and rate limiting; the user must regenerate a new-format Recovery Key.

Anonymous account container boundary: `sys_user` does not carry login IP/time, TOTP secret, TOTP pending secret, or TOTP recovery-code hash. Login observations only enter the session/security event dimension; TOTP material only enters `user_mfa_profile`; `LegacyPasswordHash` / `LegacyProjectRole` can only exist as tombstone compatibility fields, and production endpoints must not read them to complete login or authorization.

Strong-anonymity credential issuance is a one-way blind signing boundary from logged-in state to anonymous state: the only issuance entry is `POST /api/binary/anonymous-credential/blind-issue`. The browser executes Prepare/Randomize/Blind/Finalize locally according to RFC 9474 `RSABSSA-SHA384-PSS-Randomized`; the server only verifies account claiming eligibility, epoch quota, and fixed-width blinded representative, and cannot see or recalculate the final RSA-PSS signature, credential commitment, revocation handle, nullifier, proof witness, or credential secret. `GET /api/binary/anonymous-credential/blind-issuer` publicly returns the 3072-bit RSA SPKI bound to root, SHA-256, and scheme id. The issuance response must be `no-store`; the quota table only saves epoch-scoped HMAC subject, epoch, status, and hour buckets, and does not save trace/path/identity kind. Success, eligibility rejection, quota rejection, and signature failure use the same error and controlled delay bucket. Runtime `BlindRsa:Enabled=false` can simultaneously close metadata and private key operations through configuration reload without restarting the process; obtained anonymous materials do not establish a server-side reverse lookup path for this reason.

Strong-anonymity root/circuit metadata is a public read boundary: `GET /api/binary/anonymous-credential/root` and `/circuit` only return public credential root, epoch, expiry, circuit id, verifying key hash, public input layout version, and ZK/verifier configuration bits. `verifierConfigured` only comes from the production `IZkProofVerifier.IsConfigured`, used to tell the prover whether the current server has a complete verifier adapter, and does not validate proof on this read path. This read path must be anonymous, `public_read` rate-limited, AEDS-only, and does not read Cookie, session, Authorization, or current account; when root is unavailable, it fails closed as AEDS `anonymous_root_unavailable`. The server-side cache object must be invalidated by root version/TTL; negative cache only briefly absorbs misses, and does not undertake root rotation worker responsibilities.

Strong-anonymity revocation uses a public offline distribution boundary. All clients only read the same epoch/version full snapshot or delta from the content-addressed URL fixed by root metadata; the request is fixed as a body-less `credentials: omit` GET, and the response uses `public, max-age=31536000, immutable`. Credential-specific `POST /api/binary/anonymous-credential/revocation-witness` permanently returns `410`, does not read body, frames 186/187 only retain retired numbers and must not be reused. The browser verifies epoch/version/root/content hash/hash-binding/expiry within the existing privacy worker and then locally generates the non-membership witness; revocation handle does not enter URL, body, header, log, or telemetry.

The strong-anonymity comment ticket is an unauthenticated admission boundary before anonymous comment writing: `POST /api/binary/comment/anonymous-ticket` only accepts the `AnonymousCommentTicketRequest` AEDS frame, must be `AllowAnonymous`, `public_read` rate-limited, and reject any Cookie/session/Authorization pollution. The server first performs cheap checks such as article/scope/hash/reply context/frame size, then uses the current root snapshot and `IZkAnonymousProofService` to pre-verify proof; after passing, only one opaque ticket is returned, the cache layer only saves the short TTL binary payload corresponding to the ticket hash, and is handed over to `POST /api/binary/comment/anonymous` with consume-once semantics. The anonymous submit only accepts `AnonymousCommentCreateRequest`, and similarly rejects logged-in state pollution; on success, it writes anonymous governance fields and regional compliance records, and the initial state is jointly determined by anonymous credentials, regional manual review/hiding, risk queue, and model switches, not fixed as `Approved`. Comments requiring the model first write `Pending`, and return the final state through `CommentCreateResult` after synchronous disposal is complete, without writing ticket/proof/credential original text into the comment. The strong-anonymity comment itself has no account attribution; when replying to public comments, the notification recipient is only determined by the target comment's effective public `user_id` projection, cannot be determined by the replier's identity, nor establish a mapping from the anonymous replier to the account. Public comment reading can only generate display name from the comment row's author snapshot: anonymous/strong-anonymous uses `anonymous_display_name` or anonymous fallback, public send uses `public_handle` or unsigned fallback, and cannot fall back to `sys_user.username`. Reply display can only be generated through the author snapshot of the comment pointed to by `reply_to_comment_id`, and does not depend on `reply_to_user_id` or `sys_user` join to restore the anonymous author. The ticket endpoint must not write comment text, must not establish a mapping from user id to nullifier/credential, and must not return proof failure details to the client.

Anonymous comment scope is generated and verified by the server according to `comment:v1:article:{articleId}:top` or `comment:v1:article:{articleId}:thread:{rootId}`. The top-level quota is 1 per anonymous credential cycle, per article; the reply quota is 3 per anonymous credential cycle, per discussion thread. Deletion, moderation rejection, hiding, or same-version policy adjustments do not return consumed quota; after credential rotation produces a new nullifier, it is counted according to the new cycle, and scope ownership changes must promote the version. Scope is always bound to the article, and cross-article stable values are prohibited; the client value is only used to construct proof, and cannot change the server-derived article/root association.

The comment policy Decoder is the frontend security boundary for the strong-anonymity entry. The API wrapper, ArticleDetail, privacy metadata adapter, mock, and fixture must consume the same complete type at the contract layer; the business layer must not extend optional ZK-Prod fields, force cast, or interpret missing values as usable. The Decoder generates an explicit client contract version based on the precise POD layout, and normalizes the server-controlled reason and the original readiness bit into a single low-cardinality state. Only `ready` can enable the strong-anonymity entry; any legacy/unknown/malformed/contradictory state fails closed, retaining the public read and user-explicitly-selected public comment capability, but never automatically rewriting this strong-anonymity submission method.

Public comment deletion uses the viewer-region aware tombstone chain: currently viewer-visible `Approved`, non-deleted nodes are public leaves; the server only fills in the ancestors of these public leaves. Ancestors that have been deleted, hidden by administrator, or not displayable in the current region are uniformly projected as "this reply has been deleted / deleted comment", and must not carry the original text, deletion reason, author snapshot, account, or anonymous governance identity; deleted leaves without public descendants are not returned. Region blocking only affects the hit region; `UNKNOWN` viewer conservatively applies all blocked-region rows; account cancellation does not query the account state back, but still displays according to the public author snapshot at the time of comment writing, unless the comment itself enters the deletion/hiding chain. The notification stream deletion event first performs the same local safety placeholder, then forcibly falls back to the current first screen, so that the real-time state is finally consistent with the same-region cold read.

Thread count and preview are two independent semantics: `ReplyCount` represents the total number of replies in the complete thread projection under the same viewer-region visibility rules; `RepliesPreview.Count` only represents the current inline preview count; `HasMoreReplies` only compares the two. The count must share a batch window aggregation with the tombstone recursive chain, and cannot perform an independent count for each root, nor disguise "preview + more sentinel" as the total count. When the article has no valid current publication, the comment thread and count cannot be publicly read together.

The recursive comment tree uses the server-saved `parent_id/root_id/depth` as the only structural truth; the client must not re-derive based on return order or fixed two-level. `GET /api/binary/comment/{articleId}` only paginates root nodes and inlines a small segment of direct child node previews; `/children/{parentId}` performs an independent keyset cursor on a single parent node; `/context/{commentId}` returns the ancestor path, target, and adjacent sibling window, used for precise positioning of `/article/{articleId}#comment-{commentId}`. The path endpoint uniformly returns `unavailable` for non-existent, deleted, hidden, and region-invisible targets, and must not use state or timing to leak their existence. Write depth and single-node direct reply count are constrained by server-side configuration, and the parent node quota is locked within the transaction; over-limit returns stable errors `comment_thread_depth_limit`, `comment_child_limit` respectively.

### Comment Creation Idempotency Identity

Comment creation is a safely retryable command. Logged-in state public requests must carry the canonical lowercase UUID `D` format (fixed 36 characters) `X-Fsus-Client-Mutation-Id`, and use `accountId + clientMutationId` as identity; strong-anonymity submissions use the SHA-256 commitment of the opaque ticket as identity. Both chains save the canonical request digest and idempotency identity in the comment transaction: same identity same digest returns the original `CommentCreateResult` and `idempotencyReplay=true`; same identity different digest returns `409 comment_mutation_content_conflict`; duplicate writing of region records, nullifier consumption, notifications, or cache side effects is not allowed. The idempotency window defaults to 24 hours; `Comments:MutationIdempotencyTtlHours` only allows 1..168 hours; within the window, response loss, double-click, concurrency, and page recovery must reuse the same identity.

Comment editing and deletion use an independent author management boundary, and cannot reuse the creation ticket, nullifier, or public display fields. Public authors are authorized by account ownership; strong-anonymity authors obtain an independent random capability in the first successful creation response, and the server only saves an irreversible commitment. Each edit/delete/status/appeal first issues a short-term one-time challenge bound to comment + purpose, then consumes within the transaction; editing also uses the current version CAS, rolling back challenge consumption on conflict. Strong-anonymity capability only exists in no-store AEDS body and page memory; it can neither enumerate comments nor be recovered through accounts. Runtime fallback without restart: tightening `Comments:AuthorEditWindowMinutes` to the minimum window can stop new historical edits; public read, notification stream, and admin moderation remain available; database changes are additive, and old clients continue to ignore the `isEdited` reserved bit.

## URL Naming Conventions

| Rule | Example |
| ------ | ------ |
| Binary endpoints uniformly prefix `/api/binary/` + lowercase resource name; public hot article uses artifact path without query | `/api/binary/article/list/home/1/10.aeds`, `/api/binary/comment/{id}` |
| Message system uses binary message path | `/api/binary/messages/conversations` |
| Admin side distinguishes with binary admin resource path | `/api/binary/admin/users`, `/api/binary/stats` |
| Author workspace production frontend uses native AEDS endpoint; does not retain legacy JSON runtime compatibility layer | `/api/binary/author/drafts`, `/api/binary/author/audit`, `/api/binary/author/moderation/overview` |
| Health check, deployment control, and notification are independent of business path | `/health/live`, `/health/ready`, `/api/ops/health/ready-detail`, `/api/ops/deployment/status`, `/api/ops/deployment/activate`, `/api/ops/deployment/drain`, `/api/ops/deployment/fence/**`, `/api/ops/deployment/notification-stream/**`, `/api/notifications/stream` |

The admin-side list of continuously growing tables must not depend on deep pagination OFFSET. The audit log list retains the `page/pageSize` compatibility field, but the server-side sorting and paging are based on the `occurredAtUtc + id` keyset cursor: the first screen does not pass `cursor`, and subsequent requests pass the `nextCursor` of the previous response. Summary/facet-type aggregated reads that refresh frequently must use normalized filter conditions for short TTL cache or equivalent rollup, and cannot let every UI refresh re-trigger multi-channel GroupBy.

Deployment control endpoints are host ops JSON protocol, not business API or AEDS fallback. Read/write must simultaneously pass the independent admin principal's `system.config` permission and loopback source restriction; the activate/drain body fixedly carries the running instance's `releaseId + slot + generation`, and CAS rejects requests sent to the wrong container or old generation. Candidate readiness only proves that dependency/runtime gate is complete, and does not mean it can accept traffic; the gateway must explicitly activate. Draining will cause readiness to fail immediately, but the public readiness body still only retains `status/checkedAt`. This group of endpoints does not change `ApiResponse`, AEDS frame, `X-Fsus-*` release header, PoW, or RiskControl semantics.

Author workspace cache action only exposes repeatable runtime maintenance actions, such as rebuild, invalidate, and recompute; one-time historical cleanup must enter `SchemaMigrationRunner` and be recorded by migration history, and is no longer exposed as an admin cache action for a long time.

### Message Conversation List Snapshot and Cursor

Account and admin conversation lists use stable `lastMessageAt DESC, conversationId DESC` keyset
sorting. The first screen does not pass `cursor`; subsequent requests must pass `ConversationList.nextCursor` back as-is, and cannot perform fake pagination based on first screen data in the browser. The account workspace requests 20 per request, and the admin workspace requests 30 per request; when filter conditions change, discard the existing cursor and loaded rows, and restart from the first screen of the new filter.

The server-side cursor is an opaque base64url value, internally bound to the first screen's non-internal maximum message id, the last item's `lastMessageAt`, and `conversationId`. Subsequent pages only select the latest visible messages within the message-id snapshot, so new messages inserted during paging will not move unread old conversations out of the snapshot, nor produce duplicates or silent omissions. The same timestamp must use `conversationId` as the deterministic order. When the frontend receives notification stream updates, it upserts by conversation id, deduplicates and reorders the already loaded rows, but retains the server-side cursor; the first screen refresh on reconnect must not truncate the already loaded subsequent pages.

Restart-free fallback pauses account and admin conversation lists through reload-capable `Messages:CursorPaginationEnabled=false`, uniformly returning `503 message_cursor_pagination_disabled`; details, message writing, and notification stream are not affected. Cannot fall back to `OFFSET`, old `page` parameters, or browser local slicing.

### Message Read Snapshot and Read Cursor

The admin shared queue's read facts are independently saved in `msg_admin_queue_state`, with only one row per conversation, containing `lastReadMessageId`, `unreadCount`, `lastReadAt`, and monotonic `version`. Non-internal messages sent by accounts increase the admin queue unread count in the same write transaction; admin and system messages do not increase. Admin list, detail, and `unread` filter only read this projection, and never aggregate the unread count of account participants. Opening the latest detail monotonically advances the shared queue with the `readSnapshotMessageId` of that response; reading history pages will not cause the cursor to move backward. Account participant state and admin queue state are not backfilled to each other.

Old conversations are conservatively backfilled by `20260719-post-message-admin-queue-state`: when there is no historical admin read fact, all account messages are considered as admin queue unread. `IMessageAdminQueueMaintenance` provides consistency check and idempotent rebuild, which will fix missing rows, unread count deviation, and invalid read cursors. reload-capable `Messages:AdminQueueProjectionEnabled=false` will cause the two admin read endpoints to fail closed as `503 message_admin_queue_projection_disabled`; account read/write and message persistence continue to work, and can be directly re-enabled after fix/rebuild, no need to restart, and cannot fall back to participant unread aggregation.

Admin-side list and detail use independent `AdminConversationList(206)` / `AdminConversationDetail(207)` projection, only adding the minimal `counterpartyAccountId` and account status (normal, restricted, deactivated, unavailable). The account side still uses the original `ConversationList(56)` / `ConversationDetailV3(204)`, whose DTO and wire layout do not contain counterparty account fields. Sender display is generated by viewer: account side only sees "you/admin/system", admin side sees "account #ID/admin/system". Admin-side real-time upsert reuses the same projection, and does not return public handle, punishment reason, admin principal, or session id.

reload-capable `Messages:AdminAccountProjectionEnabled=false` can cause the admin-side list/detail to return `503 message_admin_account_projection_disabled` without restarting the process and stop generating admin-side projection real-time upsert; account message protocol and account read/write are not affected. After fixing the account projection data, it can be directly re-enabled, and cannot fall back to guessing accounts from `senderName` or adding identity fields to account frames.

Account and admin message details use `ConversationDetailV3`, which by default only returns the latest 50 non-internal messages. The response's `previousCursor` is the oldest message id of this page; when `hasOlder=true`, the client passes this value as-is as `beforeMessageId` to initiate the next forward read. The client must deduplicate by message id and maintain ascending order; notification stream new messages and history pages arriving concurrently must not overwrite each other. Any page on the account side must not return internal notes.

The account inbox reports replay miss in the notification stream, and reads the delta with the current detail's last known message id as `afterMessageId`; the delta pagination continues along the response cursor until the database authoritative snapshot catches up. Reconnect recovery refreshes both the conversation list and the total unread count simultaneously. The detail request must be bound to selection generation/AbortSignal; when HTTP returns, it merges real-time messages, read cursor, and status patch that are newer than the request, and cannot overwrite the entire object. Message id, read cursor, event id/time, and `lastMessageAt` are respectively the comparable versions of the corresponding projection; older patches can only be deduplicated, and cannot cause state rollback.

Message content must not depend on HTML `maxlength` or UTF-16 `String.Length` as a persistence gate. The shared policy simultaneously calculates Unicode scalar, grapheme, and UTF-8 byte length, and verifies again after AEDS decoding; account manual messages, admin replies, and system governance notices all follow the same policy. Over-limit must fail explicitly with `Validation` and retain the caller's original text, prohibiting substring/slice and continuing to write. Only the list preview can generate independent truncated projections by grapheme boundaries; the stored body and detail response must not be affected by the preview.

`ConversationDetailV3` also returns the `readSnapshotMessageId` of the current visible result. Account-side mark-read must submit `readThroughMessageId` of `ConversationReadRequest`; account reply must submit `AccountConversationReplyRequest`, carrying both the body and the explicit read position. The server must not replace the snapshot seen by the client with the database's current `MAX(message.id)` in the mark-read or reply transaction.

Read advancement verifies within the participant row lock that the target message belongs to the current conversation, is not an internal note, and is not less than the persisted cursor. Unread count only counts messages after the cursor, visible to the account, and not sent by the account itself; internal notes cannot be used as read targets, nor advance or increase account unread. The old `ConversationReplyRequest` is only used for admin replies; the account endpoint is not compatible with the body-only fallback.

Restart-free security degradation pauses account mark-read and reply writing through reload-capable `Messages:PreciseReadCursorEnabled=false`, returning fixed `503 message_read_cursor_disabled`; detail and list remain readable. Degradation must not restore body-less mark-read, transaction point `MAX(id)`, or the old semantics of "account reply equals reading the current database".

Account and admin replies share a PostgreSQL transaction write kernel. The transaction first locks the conversation with `FOR UPDATE` and re-validates the state; `closed` conversations uniformly reject replies, and can only continue after explicit state change back to `open/pending`. Message insertion, conversation activity, counterparty unread projection, and this delivery event must all succeed before commit; delivery event is only published after transaction commit, and must not expose ghost messages to the notification stream on rollback. Replies do not use PostgreSQL `xmin` as a precondition; state lock and expected state update conflicts return `409`.

reload-capable `Messages:ReplyWritesEnabled=false` can simultaneously pause account and admin replies without restarting the process, fixedly returning `503 message_reply_writes_disabled`. List, detail, state change, and explicit reopen are still available; database failures should be handled and projection consistency verified before recovery, and cannot be degraded to non-transactional writes.

Admin state writing uses an explicit state machine: `open -> pending/closed`, `pending -> open/closed`, `closed -> open`. Requests must carry an audit reason; same-state requests return `no_change` and do not generate audit or real-time events. Valid transitions use row version CAS, and append immutable audit and account/admin two types of outbox delivery in the same transaction; both ends consume `InboxConversationStatusChanged`, delivery saves the exact state of this time, and prohibits worker re-reading the latest row causing event distortion. `Messages:StatusMutationsEnabled=false` can hot-pause this writing and return fixed 503; restore directly when recovering, cannot bypass audit, CAS, or outbox.

### Message Write Idempotency Identity

Message real-time events only bear the reference notification of "new facts can be read", not body replication. `InboxMessageAppend` retains conversation/message id, sender type, time, and unread count, but `body` is fixed to empty; `InboxConversationUpsert.lastMessage` is fixed to `null`, and must not carry body preview. After the account client receives the reference event, it must call the authoritative delta read from the current last known message id and merge; the admin client re-reads the list/detail. In this way, backlog, log dump, or metric collection will not form a second copy of the message body. Pausing the notification outbox consumer only delays the prompt, and HTTP binary list and detail are still the fact read path.

Account creation work order, account reply, and admin reply must all carry `X-Fsus-Client-Mutation-Id`. This value is generated by the client at the beginning of a user intent and remains unchanged in double-click merge, request timeout, and retry after response loss; the server establishes a global write identity by `subject type + subject ID + ClientMutationId` (original contract fields: `subject type + subject ID + ClientMutationId`), rather than local deduplication by endpoint or conversation. System messages use stable `X-Fsus-Source-Event-Id`, and use `msg_conversation.sourceMessageId` as the unique source coordinate.

The server first obtains the subject-level PostgreSQL advisory transaction lock in the existing message transaction, then simultaneously checks the conversation/message idempotency record. Same identity and same normalized request digest returns the original conversation/message id and marks replay in the response's `idempotencyReplay`; same identity but different digest fixedly returns `409`, and cannot overwrite, append message, or increase unread. Message, activity/unread, outbox, and idempotency identity must be committed in the same transaction.

reload-capable `Messages:MutationIdempotencyEnabled=false` can fail closed the creation, two replies, and system message writing without restarting the process, fixedly returning `503 message_mutation_idempotency_disabled`; list, detail, read, and state change are still available. After fixing the schema or write chain, directly re-enable, and cannot fall back to the write path without idempotency identity.

System messages cannot treat foreign key exceptions as target account policy. New source events lock the target account within the message transaction: ordinary admin/transaction notifications only receive active; ban/restore governance notifications are explicitly allowed restricted through strong-type policy; both types reject missing/deleted/unknown state. The committed same-digest replay returns the original result before locking the target, to ensure that the retry semantics do not drift when the target is subsequently cancelled. `Messages:SystemMessageTargetValidationEnabled=false` can hot-pause new system messages while retaining replay, directly re-enable after fixing, prohibiting fallback to unlocked check or relying only on foreign keys.

Unread state uses the one-way projection of "message fact + monotonic read cursor -> rebuildable count -> discardable Redis total". Account count excludes own messages and internal notes; admin count only includes visible messages sent by accounts. The database rejects negative count, cross-conversation/internal cursor, and cursor rollback. Maintenance operations can recalculate by conversation, account, or admin queue, and repair historical bad cursors within controlled transactions; `Messages:UnreadRepairEnabled=false` can hot-pause maintenance, does not change normal message read/write, and cannot let Redis reverse-overwrite the database.

Detail pagination can pause account and admin detail reading through reload-capable `Messages:ThreadPaginationEnabled=false` without restarting the process, and return fixed `503 message_thread_pagination_disabled`. This degradation only blocks detail reading, does not restore full query, browser local fake pagination, or text API fallback.

## HTTP Method Semantics

| Method | Usage |
| ------ | ------ |
| `GET` | Read resource, idempotent, cacheable; AEDS read request frame must use `Flags = 0` |
| `HEAD` | Only read HTTP metadata; only used for L0 artifact / static distribution probe, does not return AEDS body |
| `POST` | Create resource or execute action (login/challenge/send) |
| `PUT` | Full update of single resource attribute (rename) |
| `DELETE` | Delete resource |
| `OPTIONS` | Not as business API; PublicHotRead classifier only accepts `GET`/`HEAD`, `OPTIONS` and CORS requests with `Origin` return to regular CORS/endpoint pipeline (unmapped methods are usually `405 Method Not Allowed`) |

Browser CSP violation report is standard HTTP security telemetry boundary, not business JSON API, nor generates AEDS frame. `POST /api/security/csp-report` only accepts CSP/Reporting API JSON media type, fixed 16 KiB upper limit, anonymous fixed-IP rate limiting, and `no-store`; success returns empty body `204`. The server only extracts directive, disposition, and blocked-resource category, and does not save or echo the full URL, query, DOM sample, source sample, Cookie, Authorization, or account information.

Binary endpoints use `GET/POST/PUT/DELETE` according to resource semantics; authentication, MFA, Passkey, upload, and admin-side writing must not fall back to old text paths.
The HTTP validator of public HTML distributes according to whether the entity is stable: static artifact without nonce can use variant-aware strong ETag/304; nonce changes the entity per request, must return `private,no-store` and not issue ETag, `If-None-Match` must not turn the nonce page into 304. The `HEAD` of both types of responses calculates headers/Content-Length consistent with GET, but does not write body. Nonce HTML only accepts identity streaming; if the client explicitly rejects identity, returns 406, cannot reuse static br/gzip bytes.

Public HTML must also express the real resource status in the first server response. Dynamic SEO paths only accept complete single-segment matching: `/article/{positive-int}`, `/category/{positive-int}`, `/tag/{positive-int|valid-slug}`; additional fragments, zero values, and invalid encoding fixed as 404. Non-existent, unpublished, scheduled not yet reached, archived, or deleted content must not fall back to 200 SPA; only when explicitly permanently deleted can 410 be used. Provider/DB gate and other temporary failures return 503 + `Retry-After`, and cannot be disguised as 404. 404/410/503 HTML fixed `noindex,follow`, `Cache-Control: no-store`, without success page canonical, Open Graph URL, `BlogPosting`, or SPA boot script, nor schedule/write ordinary Public AOT cache. GET and HEAD have consistent status and key headers; HEAD does not write body.

The trailing slash policy is canonical without trailing slash: except `/`, any HTML path ending with `/` first jumps to the trailing-slash-removed path with a single 301, and retains the query string. SPA-only `/search`, authentication entry, and account workspace continue to return the application shell; other unregistered paths are directly returned 404 by the server, no longer relying on Vue catch-all to establish error semantics.

`/search` is a crawlable but never indexed SPA-only HTML route. The first server response of GET and HEAD fixedly carries `X-Robots-Tag: noindex, follow`, and the HTML head simultaneously carries `noindex,follow`; Vue navigation can only take over and maintain this state, and cannot be created for the first time after hydration. Search URL only accepts query sorted by `q`, `sort`, `page`: `q` uses Unicode NFC, removes leading and trailing whitespace, folds consecutive Unicode whitespace into one space, max 128 UTF-16 code units; `sort` only accepts `relevance|latest|hot`, where default `relevance` is omitted; `page` is `1..100`, default `1` is omitted. Empty value, duplicate item, unknown item, illegal sort/page, and non-canonical encoding single-jump 301 to the unique URL; raw query exceeding 2048 characters, over-long or with non-whitespace control characters in `q` returns 400 noindex HTML. Without `q`, the unique URL is `/search`, and sort/page are also removed.

Search HTML does not output canonical, JSON-LD, or Public AOT entry, nor enters sitemap; search results only link to the article's own `/article/{id}` canonical. `robots.txt` allows crawling `/search` to read noindex, only blocks search index binary/patch assets, and cannot use `Disallow: /search` to hide indexing instructions.

The long-term identity of the tag public URL is fixed as stable database id: only `/tag/{positive-int}` can return 200 and self-canonical. Historical `/tag/{name}` (including case or Unicode NFC equivalent forms) is only used as a migration entry, resolved through the current tag name or persisted `tag_url_alias`, and then single-jump 301 to `/tag/{id}`; tag renaming saves the old name alias in the same transaction, so it does not change canonical, nor turn old external links into another 200. When the name cannot be uniquely resolved, it returns 404, and cannot jump to the home page. sitemap, internal links, JSON-LD/Open Graph, navigation snapshot, and AOT manifest only output ID URL.
Binary write requests must use `Content-Type: application/octet-stream` and AEDS v2 request frame; the current production protocol rejects request non-zero flags, and future flags such as `Flags = 64` can only be enabled after being registered in `aeds-protocol.json`, negative contract matrix, TypeScript/Worker/Wasm decoder, and [schemas-and-errors.md#flags-registry](schemas-and-errors.md#flags-registry) synchronously.
The server uses request-level pooled buffer lease when reading non-empty AEDS request payload. The binder must return the lease immediately in its own `finally` on header/payload/CRC verification failure, cancellation, or exception; after successful verification, ownership is transferred to the `/api/binary/**` request pipeline, and the pipeline `finally` determines return after the endpoint and result execution are completed, and cannot rely on `HttpResponse.OnCompleted` to complete the main recycle. The consumer can `Dispose` early after completing synchronous decoding; all return entries must be idempotent, the buffer is cleared on return, and the payload view after return must not continue to be read. Client disconnection, incomplete response, and exception response all follow the same semantics; `OnCompleted` is only allowed as a fallback. The runtime observes lease balance through `fsus.binary_request.pool.rent_count`, `return_count`, `rented_bytes`, `returned_bytes`, and `outstanding`.

The binary read request frame must use `Flags = 0`; request non-zero flags are rejected, and future flags must be registered synchronously in `aeds-protocol.json`, negative contract matrix, TypeScript/Worker/Wasm decoder, and [schemas-and-errors.md#flags-registry](schemas-and-errors.md#flags-registry) before being enabled. In anonymous identity mode, new account onboarding must use `POST /api/binary/auth/anonymous/bootstrap` with request frame `AuthAnonymousBootstrapRequest`; this path only initializes the anonymous account container and current session, rejects user-provided login passwords, and may not reuse the old username/password contract. Old `/api/binary/auth/register` and `/api/binary/auth/login` password endpoints are no longer production APIs; old password-auth request numbers are retired from the AEDS frame catalog. AEDS numeric slots `40`, `43`, `44`, `45`, and `46` are retired legacy admin password-reset and username/password-auth slots and must not generate frame names, PODs, codecs, or OpenAPI contracts.

`GET /api/binary/auth/me` only outputs the `IdentityAccountSnapshot` anonymous account container: `accountId`, `identityKind`, `publicHandle`, Passkey/Recovery/TOTP status, anonymous credential status, and account ban/deactivation status. The success response must additionally carry `X-Fsus-Access-Expires-At-Utc`, whose ISO 8601 UTC absolute time comes directly from the verified access principal's `exp`; missing, illegal, or expired `exp` must return 401, and cannot fall back to the frontend fixed TTL. This response must not expose internal `sys_user.username`, `sys_user.role`, old compatibility `id`, or `internalUserId`; the client must not infer admin permissions from the normal account snapshot; backend permissions can only come from the independent admin principal and admin session Cookie.

`GET /api/binary/auth/sessions` only returns the session id that the normal account can operate, the coarse-grained device label composed of browser family / OS family / form factor, the creation/recent active time, the login source and strength, the optional Passkey friendly name, the Cookie persistence policy, and the current session marker. It must not expose internal credential row id, client device fingerprint, raw user agent, JWT/refresh token, long-term MFA state, precise IP, or internal risk HMAC to IdentityCenter or frontend adapter. The `UserSession` persistence layer also does not save these raw values: device/network only uses account-scoped rotating HMAC + epoch; UA only saves low-cardinality triples; signal absence does not block Passkey; signal change can only affect risk score, and cannot become the basis for authorization, account binding, step-up exemption, or cross-session revocation. See [user-session metadata privacy](../security/user-session-metadata-privacy.md).

The authentication success response does not put access/refresh token in the AEDS body; the HTTP layer only carries it through HttpOnly Cookie. The JWT issuance result is an atomic result of the access token string and absolute `ExpiresAtUtc`; login, MFA, Passkey, refresh rotation, and admin session write Cookie must use the same absolute time; the Cookie layer must not read the expiration minute configuration again or parse JWT, to avoid two sets of lifecycles from configuration reload boundaries. The browser schedules refresh based on the real absolute expiration time of `/auth/me` minus a fixed safety margin, and uses Web Locks or BroadcastChannel to elect a single leader; the follower only re-reads `/auth/me` after settlement. refresh POST is a non-idempotent action; when the network result is unknown, it must not be automatically replayed, and only bounded backoff retries of idempotent `/auth/me` are allowed. refresh rotation must also verify before and after Cookie append that the new hash/session is still the unique active truth; the same session submits old token within the short contention window after the most recent rotation and returns 409 without clearing Cookie or revoking family; replay beyond the window continues to revoke family and returns 401. These boundaries must not be described as atomic transactions across PostgreSQL, tabs, and HTTP.

Admin-side account location can only be done by querying the anonymous account search dimension of `/api/binary/auth/{id:int}` or `/api/binary/admin/users` through accountId; the old `/api/binary/auth/find/{username}` has been offline, and `sys_user.username` is no longer used as a regular admin API query key.

TOTP only serves as a sensitive operation step-up in anonymous identity mode. The TOTP issuer account label must use non-identifying `FsusBlog:account:{accountId}`; `/mfa/setup/start`, `/mfa/disable`, and `/mfa/recovery/regenerate` must consume the one-time proof of the corresponding action through `X-Fsus-Mfa-Proof`, and do not receive the old username/password body proof; TOTP recovery code must not be confused with the account `Recovery Key`.

`PUT /api/binary/auth/public-handle` is the only user-side public naming write entry, using `AuthUpdatePublicHandleRequest` + `StringMutationRequestPod`; empty string means clear. Comment public send can only read the persisted `public_handle`; when not set, public mode is rejected, and internal username or synthesized user id cannot be used as fallback.

The account-side `GET /api/binary/comment/me` is an attributable comment record, which only returns comments explicitly public/publicly sent by the current account; strong-anonymity comments do not enter this record, nor can they be self-deleted through account id. `comment.user_id` only allows serving public attribution in the final state of the comment, and must simultaneously bind `author_mode = public`; the old generic `idx_comment_user_id_desc` must not be restored as the default anonymous comment query entry. If strong-anonymity withdrawal needs to be supported, it must go through receipt, capability token, or nullifier proof scheme; before that, only administrators can delete according to governance permissions.

## Pagination Convention

The system uses two pagination modes:

### Page-based Pagination (`PageResponse<T>`)

Suitable for: article list, anonymous account governance list, and other scenarios that require total count.

```json
{
  "items": [...],
  "total": 100,
  "nextCursor": "AQAA...",
  "hasMore": true,
  "page": 1,
  "pageSize": 20
}
```

Query parameters: `?page=1&pageSize=20`

Article list pagination does not do silent correction: `page` must be greater than or equal to `1`; `pageSize` / binary `size` must be in `1..100`. The default value is still `page=1`, `size=10`; explicitly passing `page<1`, `size<1`, or `size>100` returns `400 Bad Request`, and cannot fall back to the first page or truncate to the maximum value.

Public HTML for home, category, and tag uses the same cursor-only list contract as the binary API. The first page canonical is the base path without query. A deeper URL contains both the logical `page=N` and the opaque cursor returned by the previous response; `page>1` without a cursor is invalid and is not redirected, replayed, or rendered from a static deep-page artifact. Public AOT and PublicHotRead generate only page one and expose a real cursor-bearing next link; deeper navigation is handled by the dynamic endpoint and SPA state. Explicit `page=1` or malformed first-page query may still canonicalize to the base path, but canonicalization cannot recover a missing deep-page cursor.

Cursor v3 is an authenticated, 15-minute Data Protection token that binds the last item's UTC `createtime`/`id`, the relevance or hot sort value when applicable, category, tag, normalized keyword, size, sort mode and `ArticleListVersion`. Missing, malformed, expired, tampered, or cross-query cursors return `400 Validation`; a cursor-less deep request is rejected before database or cache access, and a version mismatch is rejected after reading only the current version authority and before frame-cache or database access. Latest ordering uses the strict boundary `(createtime < cursorTime OR (createtime = cursorTime AND id < cursorId))`; relevance and hot ordering prepend their bound sort value to the same deterministic time/id tie-break. Public list frame/cache identity uses `cursor:first` or the full opaque cursor. There is no `legacy-page:{page}` identity, sequential replay, emergency cursor-less degradation, compatibility redirect, public `OFFSET`, or dual protocol. The admin article list keeps its independent page/offset contract.

### Cursor-based Pagination (`CursorResponse<T>`)

Suitable for: comment threads, message streams, and other infinite scrolling scenarios.

```json
{
  "items": [...],
  "nextCursor": "eyJpZCI6MTIzfQ==",
  "hasMore": true
}
```

Query parameters: `?cursor=<previous returned nextCursor>&limit=20` (original contract form: `?cursor=<previous returned nextCursor>&limit=20`)

### FPOW Proof Envelope

HTTP dynamic public APIs use `X-Fsus-Pow-Proof`; the legacy compatibility path for notification stream anonymous connections uses the `pow` query parameter; both carry the same base64 text-form binary FPOW envelope. The frontend implementation is in `src/frontend/src/services/powProofCodec.ts`.

The FPOW envelope field order is: `magic[4] = "FPOW"` (bytes `46 50 4f 57`), `version:uint8 = 1`, `difficulty:int32LE`, `timestamp:int64LE`, followed by several `uint16LE length + utf8 bytes` fields. The HTTP header proof fields are `salt, nonce, signature, browserFp`; the notification stream proof fields are `salt, nonce, signature, fp`. The legacy PoW server verifies according to the timestamp, nonce, signature, device fingerprint, and `ForwardedHeadersMiddleware` normalized client IP bound by the proof; the RiskControl `sha256PowV1` provider's HMAC additionally binds the context hash of challengeId, action, routeKey, subjectHash, clientIpHash, deviceFpHash, and policyVersion. Old text PoW answer/challenge headers are not accepted, nor does the PoW verification layer fall back to raw remote IP, localhost, or Docker bridge IP.

RiskControl new challenge providers must not customize parallel assignment structures. PoW, Perception, PoSpace, HumanReadProof, Passkey step-up, anonymous credentials, and ZK anonymous comment proofs must all use `SecurityChallengeAssignment` / `SecurityChallengeEnvelope` AEDS frames, uniformly carrying challengeId, traceparent, tenantId, kind, action, routeKey, subject/client IP/device fingerprint hash, issued/expires, and escalationLevel; the provider only extends its own proof verification payload.

PoSpace capability does not belong to client authorization input. When the client cannot execute the already issued PoSpace, it can only reference the original assignment in the bounded attributes of the next binary challenge issue and give an enumerated reason; the server must re-verify the original assignment binding and current policy, revoke the old proof, and then decide the remaining challenge, server-side allowed fallback, or rejection. The client must not submit target kind, parameter downgrade, or allow intent, and re-signing must have a strict number of times limit to avoid capability negotiation forming a downgrade or loop oracle.

Protocol known is not equal to client executable. The server and browser must release `SecurityChallengeCapabilityCatalog` / `challenge-capability-registry` (manifest version `2026.07.22.1`) with the same build, distinguishing `kind_known`, `provider_available`, `executor_available`, `host_available`, and `policy_eligible` by kind. PoSpace uses the same universal executor to simultaneously serve UI and `notification.subscribe` headless host; before issuing, it must still fail closed according to the surface corresponding to the action; lack of executor, lack of host, or manifest incompatibility returns controlled capability reason respectively, and cannot enter placeholder components or permanent pending. This manifest only describes low-information build capability and must not contain device fingerprint, identity, token, or proof.

Business requests protected by RiskControl must not send provider proof or multiple independent tokens directly to the business endpoint. Each `challenge|stepUp` ruling establishes a UUIDv7 `envelopeId`; the server stably sorts and saves the complete required plan by `credential -> cheap-proof -> memory-proof -> scarce-artifact`. The first issue only materializes and returns the first actionable assignment and payload; the remaining members are saved in the authoritative state as `planned`. The client submits in this order to `/api/binary/security/challenge/verify`; the current item first reserves from `issued -> verifying` with envelope version CAS, and only the winner can consume provider proof; after success, the next item is advanced from `planned -> issuing -> issued`, and the verify response carries the next assignment/payload. A single challenge is the same state machine with `memberCount=1`, and does not maintain a second set of mint/consume logic.

`PerceptionCharacterV3` does not reuse dictionary/JSON provider payload, but uses a typed binary union distinguished by assignment kind in the same envelope frame. The server only delivers the final PNG/Ogg Opus and opaque state; the client cannot control generation parameters, nor echo media, recipe, or solve duration. When the artifact pool has not yet taken over or the current generation has not passed full verification, it fails closed and must not issue any V3. Login/admin device authority comes from the server-issued `sid/admin_sid`; anonymous device authority is the Redis authoritative UUIDv7 lease and `__Host-Fsus-Perception-Device` HttpOnly/Secure cookie; when the cookie is missing, the existing lease is reused for the same IP; forgery or arbitrary rotation of identity will fail closed; client fingerprint can only be used as a non-authoritative risk signal. Normal policy publication does not rewrite the policy version of the already issued envelope; verify reads and uses the issued version; when immediate deactivation is required, the hot policy stops new issuance and explicitly revokes the active identity, without requiring restart.

The browser composition only selects one representation before the first issue (default visual), and subsequent ones only accept a single deferred member in strict order in the verify response; it must not prefetch visual/audio simultaneously, nor automatically rent a new artifact after ambiguous send. The typed adapter must complete bounded final-media verification before Blob allocation. The final PNG is directly handed to the FsusUI image-url primitive as an `image/png` object URL; Opus is handed to the accessible audio control as an `audio/ogg; codecs=opus` object URL; canvas reconstruction, PNG security decision, or client-side generator is not allowed. Replacement, completion, cancellation, expiration, and unmount must all stop media and revoke URL. Proof, opaque state, and media are only allowed to exist in the in-memory state machine and must not be written to any browser storage.

V3 is a scarce server resource; business endpoints, providers, and the frontend must not each choose capacity fallback. The server-owned planner first returns allocation/disposition according to action, identity assurance, risk, pool watermark/health, and budget; when Passkey/user-presence has already satisfied assurance, credential step-up is preferred; public read does not consume V3 for "the frontend can display". Comment exhaustion only enters the moderation queue when the policy explicitly indicates; enrollment, recovery, and admin security exhaustion fail closed. The planner's internal `throttle/block/queue/cheaper-proof/unavailable` continues to map to existing RiskControl/AEDS coarse errors or business queue semantics, and does not add JSON, text reason, or `allow` responses.

The same-representation refresh and visual/audio switch of V3 must both go through the replacement contract of the issue request; the client must not asynchronously cancel first and then issue. The active-index uses a domain-separated stable digest derived from server-authoritative device material, unrelated to answer/token key rotation; the answer-key HMAC only binds a specific challenge; when replacement verifies the old challenge, it uses the recorded old answer key version. The server completes the new media, token, and typed payload verification before touching the old state, then uses a Redis Lua linearization point to verify the old binding/active-index, set the old state to `revoked`, write the complete new state and absolute TTL with NX, and switch the active-index to the new challenge. On failure before commit, the old identity remains active; after commit, the old identity is never restored. Redis reply loss only uses the current operation result readback, does not replay mutation; when the readback is still uncertain, the identity remains in an ambiguous fence and fails closed.

Representation replacement must simultaneously submit old challenge id, old envelope id, and old opaque state token; the provider constructs the old state binding with the current authoritative action/route/subject/server-device/IP and the policy version, token hash already issued by the old challenge, and atomically verifies and revokes through Redis Lua; after successful replacement, the new challenge again binds the currently released policy version. Only knowing the challenge id, cross-subject, forged old policy, or replacing any binding cannot revoke the old challenge; the old challenge that has been explicitly revoked or expired also cannot be authorized for replacement again.

Refresh, explicit cancellation, identity or route generation change, and component unmount must first tombstone the local generation, and best-effort revoke the server envelope through the binary-only `POST /api/binary/security/challenge/cancel`; late issue/verify results must not restore local state. The cancellation request re-binds action, route, subject, and client IP; ordinary providers continue to bind the current device fingerprint/policyVersion. V3 cancel must first parse the server-issued device authority from the current request, derive the device HMAC using the answer-key version of the old challenge, and then atomically revoke through the complete Redis Lua binding of envelope/action/route/subject/device/IP/issued-policy/media/representation/token hash; it must not use the stored device value to authorize the current caller. Binding mismatch maintains opaque success externally; V3 infrastructure failure only returns coarse `unavailable`; specific success, terminal state, binding failure, or Redis reason is only written to low-cardinality audit. Restart-free degradation still uses hot policy to prohibit new combinations; cancel transport must not become JSON fallback or bypass proof one-time consumption.

Any member's verification success only advances the envelope and does not issue proof usable for business; only when all required members are verified can an aggregate `X-Fsus-Challenge-Proof` be minted. The final business header still uses the last ordered member's `challengeId` / `kind` for compatibility with existing transport, but the opaque proof claims must additionally bind `envelopeId` and ordered `requiredKinds`, and continue to bind action, routeKey, subject, client IP/device, policyVersion, expiry, and one-time nonce; the server verifies these claims simultaneously when consuming; the client cannot declare completion by selecting the last item or rearranging kinds. Any required member failure, expiration, revocation, replay, order disorder, or envelope replacement fails closed and cannot enter completed.

The aggregate verify success response returns the server-authoritative `expiresAtUnixMs`; the client must not fix-derive five minutes. Proof Store only allows in-memory `available -> reserved/in_flight -> consumed|expired|replayed|rejected`; reservation can only be restored when it is certain that the request has not been sent; once the request may reach the server, timeout, connection reset, and business rejection must terminate the token and re-issue. If old clients cannot execute `memberCount>1`, they must receive explicit version/capability incompatibility results and cannot only execute `assignments[0]` and then continue business. UI challenge host and notification headless flow must call the same envelope runner; the runner allows sequential execution or bounded parallelism explicitly indicated by policy, but expensive Worker has a fixed concurrency upper limit; refresh, cancel, identity/route generation change, and unmount/dispose will terminate the entire envelope and discard late results.

V3 artifact lease is only allowed in the request that wins the `issuing` transition; the first issue and any request that has not yet authoritatively completed the preceding member cannot reach the V3 provider. The preceding proof can also only call the provider for the request that wins the `verifying` transition, to avoid concurrent losers of consume-once proof breaking the winner. Concurrent losers, Redis CAS uncertainty, or process interruption all fail closed; retrying provider issue or renting a second artifact is not allowed. Visual/audio representation is written into the authoritative envelope at the admission initial issue; delayed providers do not re-infer from subsequent verify requests; switching representation must revoke the original envelope and establish a new chain.

Restart-free fallback can only hot-update the RiskControl policy to disable multi-challenge band, switch affected actions to `observe|disabled`, or roll back the last-known-good policy; already issued envelopes remain fail closed until TTL expires. Fallback must not be split into multiple proofs, restore `assignments[0]`, allow client self-report completion, or add JSON fallback; authentication, admin step-up, notification stream, binary-only, and legacy PoW boundaries remain enabled.

Ordinary business commands must first be submitted to the server; only after receiving a structured 428 does the transport hand `X-Fsus-Risk-Decision`, action, routeKey, policyVersion to the unified challenge runtime. The runtime must verify that action/routeKey is exactly the same as the original command, and then select the executor according to the capability issued by the server this time; the frontend must not pre-issue, maintain `securityBusinessChallengeGates`, or cache action→kind mappings. When the policy switches during the flow, the latest 428/LKG server ruling shall prevail; old challenges are re-issued or fail closed; comment mutation retains the same payload closure and fixed mutation identity; unknown network results are not automatically replayed.

The `notification.subscribe` action of the notification stream anonymous subscription uses the same ordered envelope runner and aggregate proof lifecycle, but the final proof only enters the preflight `X-Fsus-Challenge-*` headers. After the preflight atomically consumes the aggregate proof, it sets a path-bound, HttpOnly, SameSite=Strict short-lived opaque grant session cookie; the formal WebSocket only consumes this grant; the URL, log, and reconnect do not carry the original proof. The grant is also one-time: disconnection reconnect must re-preflight; when the server returns challenge required, the client explicitly issues a new envelope; the same token must not be retained by concurrent connections. The compatibility path of legacy FPOW `pow` query does not change. Passkey assertion failure can only write risk signals and does not change the login response frame; Passkey assertion success can write negative risk signals and continue to use Passkey as the login credential that MFA has satisfied.

The attempt count limit of `/api/binary/security/challenge/verify` is the server-side hot-path security control and does not change the AEDS request/response contract. The endpoint only depends on `ISecurityChallengeVerifyRateLimiter`; the rate limit state must fall under the unified cache `SecurityChallengeVerifyRateLimit` policy, counting by 1-minute window, client IP hash, device fingerprint hash, normalized action, and challengeId hash; when exceeding 3 times, it still returns general `challenge_failed`, and writes `SecurityChallengeRejected` risk signal.

## Status Code Convention

| Status Code | Meaning |
| -------- | ------ |
| `200 OK` | Operation successful |
| `204 No Content` | Preflight or body-less operation successful, such as notification preflight successful |
| `304 Not Modified` | L0 artifact's variant-aware `ETag` hits the current `Accept-Encoding` variant |
| `400 Bad Request` | Parameter invalid, business verification failed |
| `401 Unauthorized` | Bearer Token not provided or invalid |
| `403 Forbidden` | Insufficient permission (logged in but role does not satisfy) |
| `404 Not Found` | Resource does not exist |
| `405 Method Not Allowed` | Method not allowed; L0 artifact only accepts `GET` / `HEAD` |
| `406 Not Acceptable` | `Accept` does not match artifact type |
| `409 Conflict` | Resource conflict (such as username already exists, state change concurrent conflict) |
| `416 Range Not Satisfiable` | L0 artifact does not support Range; `.aeds` hit declares `Accept-Ranges: none` |
| `423 Locked` | Logged-in user is in banned/restricted state; notification stream uses `account_blocked`; normal business write lock uses Binary `ApiError.Details = ACCOUNT_BANNED_WRITE_LOCKED` |
| `429 Too Many Requests` | Rate limit triggered, response contains `Retry-After` header |
| `500 Internal Server Error` | Server-side exception, error details not exposed to client |
| `503 Service Unavailable` | L0 snapshot has not entered `Ready` state, default carries `Retry-After: 1`; unless fail-open to regular pipeline is explicitly enabled |

L0 artifact's `400` / `404` / `405` / `406` / `416` / `503` negative responses are fixed `Cache-Control: no-store`, to avoid intermediate layer caching of not-ready or negotiation failure results.

## Version Management Strategy

The current runtime business API does not use unified URL version prefixes such as `/api/v1/`, `/api/v2/`; new modules continue to fall under `/api/binary/**`, `/api/notifications/stream`, or explicitly registered standard protocol paths. Regular business **Breaking Change** is preferentially expressed through new frame types, payload layouts, explicit route segments, or new endpoints, and is synchronously registered in [aeds-only-policy.md](aeds-only-policy.md) and [quick-reference.md](quick-reference.md).

The AEDS wire protocol is the transport layer version, not equivalent to the URL version. The current runtime only accepts AEDS v2 header; AEDS v1 frame, unknown version, and wrong header length are directly rejected; the server and frontend do not retain v1 fallback. Future wire-level breaking compatibility must first enter `aeds-protocol.json`, `schemas-and-errors.md`, golden fixtures, TypeScript/Worker/Wasm decoder, and negative contract matrix.

Anonymous identity and comment author mode extensions use new AEDS frames instead of rewriting the published payload layout. Production new comments only allow two modes: logged-in state `/api/binary/comment`'s explicit `public`, and unidentified state ticket + `/api/binary/comment/anonymous`'s `zk_anonymous`. `CommentCreateRequest` must simultaneously declare `authorMode=public` and `publicSendExplicitlySelected=true`; old `authorMode=anonymous` explicitly returns `anonymous_author_mode_retired`, and stops before content filtering, risk recording, region determination, and business writing. When ZK verifier, root, proof, ticket is unavailable, expired, or invalid, it all fails closed and cannot be degraded to public or server-visible pseudo-anonymous. The comment composer only displays two choices of public/ZK; public cannot be automatically selected. AEDS byte `1` is only used to read historical records as `legacy_server_visible_pseudonymous` and cannot re-enable writing; migration retains historical quantity, hierarchy, visibility, moderation status, body, and display name, while clearing old nullifier, moderation subject, credential/reputation projection, and isolating from active governance aggregation. Passkey and Recovery Key still reuse existing frames; anonymous identity must not add a parallel Passkey protocol stack.

Changes not considered as Breaking Change:

- Add response field (client should ignore unknown field)
- Add optional request parameter
- Add endpoint

Changes considered as Breaking Change:

- Remove or rename existing field
- Modify field type
- Remove endpoint
- Modify authentication requirement (except downgrade)

## Notification Channel Design Convention

Source of truth: [`NotificationStreamHandshakeService.cs`](../../src/backend/Infrastructure/NotificationStream/NotificationStreamHandshakeService.cs), [`NotificationStreamHandler.cs`](../../src/backend/Infrastructure/NotificationStream/NotificationStreamHandler.cs), [`NotificationStreamSessionService.cs`](../../src/backend/Infrastructure/NotificationStream/NotificationStreamSessionService.cs).

### Channel

- Formal notification endpoint: `GET /api/notifications/stream`, only accepts WebSocket upgrade.
- Subprotocol: `Sec-WebSocket-Protocol: fsus-aeds.v2`; preflight fallback can use `X-Fsus-Notification-Stream-Protocol: fsus-aeds.v2`.
- Each business message is an AEDS binary frame; event frame uses `AedsFrameType.NotificationEvent = 69`, heartbeat frame uses `AedsFrameType.NotificationHeartbeat = 70`, error uses `ApiError = 251` (see [schemas-and-errors.md#aedsframetype-enum](schemas-and-errors.md#aedsframetype-enum)).

### Handshake Preflight

`GET /api/notifications/stream/preflight` reuses authentication, anonymous RiskControl / legacy PoW, cursor, and protocol verification, but does not require WebSocket upgrade; success returns `204`, failure returns AEDS `ApiError` frame, and writes `X-Fsus-Notification-Stream-Error-Code` / `X-Fsus-Notification-Stream-Status-Code`. Preflight only receives and atomically consumes the `notification.subscribe` RiskControl proof through the `X-Fsus-Challenge-*` header; after success, it sets a short-lived one-time HttpOnly grant; the formal WebSocket only consumes the grant; the original proof does not enter the URL. The legacy `pow` query parameter continues to be compatible. Public events do not bypass anonymous subscription admission.

### Anonymous vs Authentication

Anonymous connections only receive public events (GlobalNotice, CacheControl, etc.), but anonymous does not equal zero threshold: `NotificationStreamHandshakeService` accepts effective legacy `pow` first when `!isAuthenticated`, otherwise requires proof, escalates PoSpaceV1, or blocks according to `notification.subscribe` RiskControl ruling; failure maps to handshake failure codes such as `risk_challenge_required`, `risk_challenge_rejected`, `risk_control_blocked`. Authenticated users additionally receive private events (MessageReceived, InboxConversationUpsert, etc.); if the request carries authentication header but authentication fails, the handshake returns `auth_failed`. After the server confirms the Passkey signature counter rollback, it first revokes all normal sessions of the account, then publishes `SessionRevoked` to the still-connected account channel. The client receives this event and must immediately clear the normal account state and mark `user-expired` across tabs, and must not simultaneously log out the independent admin principal.

### Error Code and Persistence Mapping

| Failure Code | Persistence Source | Cache Layer | Miss Fallback | HTTP status | AEDS frame |
| -------- | ---------- | -------- | ----------- | ------------- | ------------ |
| `websocket_required` | WebSocket upgrade semantics | None | None | `426` | `ApiError` |
| `protocol_mismatch` | `fsus-aeds.v2` subprotocol | None | None | `409` | `ApiError` |
| `auth_failed` | JWT / cookie auth result | Inside auth stack | Auth stack handles | `401` | `ApiError` |
| `pow_failed` | PoW challenge / replay proof | SecurityPowProof / risk cache | PoW service verifies | `401` or `400` | `ApiError` |
| `risk_challenge_required` | RiskControl `notification.subscribe` ruling | SecurityChallengeProof / risk cache | RiskControl policy verifies | `428` | `ApiError` |
| `risk_control_blocked` | RiskControl `notification.subscribe` ruling | SecurityRisk | RiskControl policy verifies | `429` | `ApiError` |
| `account_blocked` | `sys_user.Status` / `BanReason` | Redis blacklist fast path | Must fall back to DB and backfill | `423` | `ApiError` |
| `account_deleted` | `sys_user` does not exist, deleted, or disabled | admission cache | Must fall back to DB | `401` | `ApiError` |

After a banned account is authenticated successfully, it can hold a restricted session to complete security closure, but normal business writing must be returned by the server as `423 Locked` + `ACCOUNT_BANNED_WRITE_LOCKED`; the client's disabled control can only be used as experience optimization and cannot replace the backend write lock. The complete failure code table is in [schemas-and-errors.md#notification-stream-handshake-failure-codes](schemas-and-errors.md#notification-stream-handshake-failure-codes).

### Heartbeat and Reconnection

The server uses `AedsFrameType.NotificationHeartbeat = 70` to send `int64 timestampUnixMs` heartbeat; the connection pump serializes business frame and heartbeat writing through the send lock to avoid concurrent WebSocket writing. The client should store the last received cursor value; on disconnection and reconnection, it is passed through the `cursor` query parameter; `Last-Event-ID` is only used as compatibility reading, not the preferred browser API.

### Test Drill Entry

`POST /_fsus/testing/notification-stream/publish` is only mapped in `Development` / `Test` environments, and must carry `X-Fsus-Notification-Drill-Secret`. It publishes `CacheControl` test events through the real `INotificationStreamPublisher`, returns the published event id and route key, used for resilience lane verification of slow consumer closing, heartbeat not starving, normal connection business frame delivery, and cursor backlog replay. This path does not belong to the production business API; it is not mapped in the production environment, and returns `404` when the secret is not configured.

## AOT Public Page Convention

Public pages (home, article detail, category, tag, archive, about, privacy policy, user guidelines, copyright statement) preferentially hit static HTML + AEDS payload from the AOT volume. The bundle format follows [`PublicAotShellEntryContract`](contracts.md#aot-public-page-contract); after SPA takes over, the hydration layer uses the same bundle data to initialize state, without the need for a second network request. SPA navigation without available public filter seed initiates a `TaxonomyExactMetadata` precise read for the current target (category id, tag id, or tag name/alias) through `useFilterView`, no longer using `CategoryList`/`TagList` to resolve a single filter target; when the effective seed already contains taxonomy metadata, this request is not added. Search does not call the taxonomy metadata endpoint. The article list still goes through `getArticles`/`searchIndex`.

Each public HTML request is resolved once by the pure `ILocaleResolver` before renderer, backfill, and cache key: effective `fsusblog.locale` cookie > highest q and catalog-supported range in `Accept-Language` > `zh-CN`. The resolver only consumes the shared locale catalog, and does not query account, database, or network profile. Canonical locale atomically binds SSR bundle/visible copy, payload `renderLocale`, document lang/dir, `Content-Language`, OpenGraph/Intl, and Public AOT/PublicHotRead key; missing or any inconsistency refuses to publish. The cache only allows ten canonical locale partitions; the original header and user identity do not enter the key. Successful HTML declares `Vary: Accept-Language, Cookie`; requests carrying other cookies still exit L0.

The same Public AOT render captures the unique authoritative UTC instant before reading the snapshot, and passes it as canonical `renderTimestamp` to the Node/Vue renderer, bootstrap, and hydration simultaneously; the `GeneratedAtUtc` of the backfill artifact must reuse this instant. When the renderer request is missing, blank, illegal, or non-canonical UTC timestamp, it must fail before SSR, seed writing, and any date formatting, and cannot fall back to the process clock, Unix epoch, `generatedAt` alias, or default locale.

The canonical page number of home page, category, and tag simultaneously enters AOT `routeKey` (page N suffix `:page:N`), document cache key, navigation snapshot `fullPath/canonicalPath`, hydration route seed, payload hash, and ETag. `scope=all` manifest enumerates all valid paginations; article visibility or taxonomy ownership change invalidates all page numbers according to the Home/Filter page prefix, and then preferentially backfills the first page, to prevent deep pagination from continuing to return the old list. Runtime emergency fallback can disable Public AOT/SPA micro-navigation, letting the real `<a href>` directly navigate the whole page; no need to restart or restore button pagination.

Code evidence: [`PublicAotDocumentComposer.cs`](../../src/backend/Infrastructure/PublicAot/PublicAotDocumentComposer.cs), [`PublicHotReadFastPath.cs`](../../src/backend/Infrastructure/PublicReadArtifacts/PublicHotReadFastPath.cs), [`PublicAotEndpoints.cs`](../../src/backend/Modules/Endpoints/PublicAotEndpoints.cs).

### Page Input and SSR Source of Truth

The public footer compliance information comes from the `SiteComplianceConfig` AEDS frame. Empty configuration must not output the filing number placeholder; after admin saves the compliance configuration, the system compliance cache, SEO/distribution cache, and Public AOT static page must be invalidated at the same time, so that sitemap/RSS/footer converge without restart.

Unified SEO and brand assets come from the same `SeoConfig` AEDS frame, and no parallel main endpoint of `/system/brand` is added. `/api/binary/system/seo` simultaneously carries basic SEO, OpenGraph preview image, favicon/browser icon, Apple Touch Icon, PWA manifest name/icon/theme/background, public site logo/wordmark, backend logo/collapse icon, and login logo/icon. After saving, the HTML head, dynamic `manifest.webmanifest`, Public AOT shell, public shell hydration, backend, and login page brand display must be refreshed through the SEO configuration invalidation chain; when the old configuration is missing new fields, default static path or empty value is used to fill in. Asset URLs only accept in-site absolute paths or `http/https` absolute URLs, and do not accept `javascript:`, `data:`, or protocol-relative URLs. The setting page can backfill the upload result to the field by `ogImage`, `brandLogo`, `faviconSet` target semantics; favicon/PWA icon group generates ICO and multi-size PNG from PNG/JPG/WebP source images, without introducing new brand configuration endpoints, nor performing automatic vectorization from raster images to SVG.

The public head does not output `meta keywords`; the historical `keywords` wire/storage field is only used for old configuration compatibility and cannot be used as a publishing gate or ranking optimization signal. Description must come from the real content of the current page: article prefers summary; without summary, first convert Markdown to plain text and then converge according to Unicode, entity, and sentence boundaries; if category and tag have taxonomy `filter.description`, the plain text is sent to the same set of `Summarize` / 160 character summary path and written to meta, Open Graph, Twitter, and JSON-LD; when missing, the existing category/tag generation fallback is retained, and `SeoDescription` or `MetaDescription` is not added; archive and fixed static pages use their own stable and visible semantics, and do not fall back to the same paragraph of site description. JSON-LD has only one `WebSite` global entity, ordinary pages use `WebPage`, archive/category/tag use `CollectionPage`, and articles use `BlogPosting`. Structured data is used to help machines understand the page and obtain display eligibility, not a ranking score, nor does it guarantee rich results.

Article time only uses content projection: `datePublished` is the actual first public time; `dateModified` is the substantive body modification time of `article_body.updated_at`. Visible text, Microdata, JSON-LD, Feed, and sitemap must share these two sources; when body time is not later than publish time, "updated on" is not displayed repeatedly. Comments, view count, templates, and footer changes must not advance `dateModified`. Legitimate article cover preferentially becomes the same absolute `og:image`, `twitter:image`, and `BlogPosting.image`; when missing or protocol/format invalid, the site social image is used as fallback.

### feed / sitemap / robots Cache Constraint

Feed, sitemap, and robots and other open distribution text endpoints are only responsible for generating standard format body, declaring `Cache-Control: public, max-age=60, stale-while-revalidate=300`, `Vary: Accept-Encoding, CF-IPCountry, X-Fsus-Region`, and attaching OutputCache ArticleList/Seo tag; the endpoint itself must not hand-write ETag according to response body, parse `If-None-Match`, or bypass the unified cache invalidation chain. They are the explicit public whitelist of general HTTPS response compression; metadata only grants these secret-less, non-request-reflective GET/HEAD responses; Cookie/Authorization/CSRF requests, non-public cache responses, or error states will fall back to identity at response start. Public integrity manifest uses the same strategy; failed/no-store manifest is not compressed.

Feed and sitemap are two independent projections: Feed only reads the latest 50 articles sorted by actual publish time; sitemap cannot reuse this limit, and must read all public canonical article identity. Both only join `article_body.updated_at` to get the substantive body update time, and do not read the body; Feed's `date_published` uses the first public time; `date_modified`/Atom `updated` and sitemap article `lastmod` all use the body update time; when the body time is missing, the publish time is used as fallback. Home/archive use the latest substantive change of the public article collection; category/tag use the latest substantive change of their respective public collections; about/privacy/guidelines/copyright only use their own `page_content.updated_at`; when there is no reliable time, `lastmod` is omitted, and using the current time to fill is prohibited.

A single urlset carries up to 45,000 URLs; when exceeded, `/sitemap.xml` outputs sitemap index, and sub-documents are provided by `/sitemap/{page}.xml`, reserving a safety margin for the protocol upper limit. Diagnostic counts must parse the final RSS/sitemap XML (including index sub-documents), and cannot use independent database COUNT to impersonate product coverage. sitemap does not output `priority`; this field is not a ranking signal.

The unique authoritative origin of the public URL is the same origin after the runtime `Seo:BaseUrl` and persistent SEO configuration are verified by `PublicOriginPolicy`. AOT canonical, Open Graph/JSON-LD, Feed, sitemap, and robots Sitemap declaration must use the same result; when non-placeholder persistent value or artifact value conflicts with the configuration, production startup and product generation fail closed, and cannot silently output multiple domain names.

Public Binary read model is governed by artifact boundaries like HTML AOT. Anonymous hot paths include:

- `/api/binary/article/{id}.aeds`
- `/api/binary/article/list/home/{page}/{size}.aeds`
- `/api/binary/article/list/category/{categoryId}/{page}/{size}.aeds`
- `/api/binary/article/list/tag/{tagId}/{page}/{size}.aeds`
- `/api/binary/article/hot/{size}.aeds`
- `/api/binary/category.aeds`
- `/api/binary/tag.aeds`

These paths are read by `PublicHotReadFastPath` in the memory snapshot before the regular application pipeline and directly write out the complete pre-encoded frame; the hit path does not query PostgreSQL, Redis, IMemoryCache, OutputCache, or file system. Artifact miss only returns a degradable status code; DB fallback can only appear in the background projector, repair task, or admin/private read path. L1/L2/OutputCache is still an acceleration layer, not equivalent to CQRS read model. The route list uses [`quick-reference.md#open-distribution-and-authoring-workbench`](quick-reference.md#open-distribution-and-authoring-workbench) as the manual quick-check source of truth.

Public GET does not default to require PoW, to avoid harming SEO, RSS, share cards, and JS-free reading; but public comment reading, public taxonomy, related-reading, and other dynamic APIs will enter `public_read` rate limiting and `RiskAwarePublicReadFilter`. Risk score is written by Shield, RateLimiter, PoW, and ReadProof rejection events; when the threshold is reached, dynamic APIs require `X-Fsus-Pow-Proof`, and continuous high risk returns 429. PublicHotRead artifact hit maintains zero DB/zero Redis/zero filter fast path.

The L0 classifier is deny-first + allowlist: under `/api` and `/api/binary`, the complete namespaces `auth`, `admin`, `author`, `manage`, `internal`, `billing`, `audit` do not create fast-path feature; only the article/category/tag artifact registered in this document and the Public AOT HTML route can enter L0. Only anonymous requests without authenticated principal, without Authorization/Cookie/CSRF header, without `X-Fsus-*` header that anonymous gateway guard will reject, without `Origin`, and method is `GET`/`HEAD` can attach feature; login requests, CORS requests, non-secure methods, admin/author, notification stream, and unregistered dynamic binary all return to the regular authentication/authorization/CORS/audit pipeline. Sensitive namespaces continue to go through the regular pipeline and are not counted into L0 hit/miss/bytes/rejected metrics; the independent `fsus.hotread.classifier.sensitive_bypass` is only used as gateway/classification regression alert, and does not carry path or identity tag.

PublicHotRead cross-cutting control is declared by `PublicHotReadCrossCuttingControlCatalog` as three categories: `global-before-branch` (release/security headers, deployment tracking, Shield/exception/binary boundary, trace correlation) is only executed before branching; `early-replayed` splits placement: lightweight request audit context runs before L0, and the `public_read` limiter runs only after an L0 miss (before fallback restore) so allowlisted hits are not charged the costly miss/DB budget. Request execution state prevents repeated acquisition of limiter lease or repeated establishment of audit context in the endpoint pipeline after artifact miss; authentication, banned-user, authorization, CORS, antiforgery/CSRF, and anonymous gateway header guard belong to `endpoint-only/not-applicable`, and their inapplicability evidence must be bound to the executable classifier predicate of the above anonymous, secure method, no Origin. Application startup verifies that required control is covered exactly once, both-end stage, guard uniqueness, route policy, synthetic endpoint metadata, and the actual probe of each route before registering any stage; missing items, duplicates, or relaxation stop startup. `tools/check-public-hot-read-cross-cutting-controls.mjs --self-test` performs drift and negative self-check on the same two-end source in CI; new cross-cutting control must first enter the catalog, and simultaneously supplement the global/early/endpoint applicable methods and behavior tests.

### L0 Artifact HTTP Semantics

When an article is deleted, permanently deleted, the recycle bin is cleared, or updated to a non-public state, the write path must first establish a tombstone with monotonic `generation` in Redis, and first publish an unconfirmed marker to let the edge fail closed immediately; after CDN purge succeeds and the receipt state is persisted, the confirmed marker is then published, allowing each edge to asynchronously rebuild the artifact. Any active tombstone will cause the public artifact route to immediately return `410 Gone`; the response is fixed `Cache-Control: no-store, no-cache, must-revalidate`, `X-Fsus-Generation`, and `X-Fsus-Revoked`, and does not return body, `ETag`, or `Content-Encoding`. The rebuild worker of each edge only compare-deletes the shared tombstone by generation and clears the local marker after the local new snapshot is atomically published; it cannot broadcast a global clear to let the edge that has not completed the rebuild resume prematurely. CDN purge or rebuild failure both remain fail closed. Unrevoked artifact response carries the current `X-Fsus-Generation`, which is convenient for CDN/edge reconciliation.

The revocation gate is an independent pipeline stage, independent of `PublicHotRead:Enabled`. When restart-free degradation of the fast path is required, this switch can be hot-updated to `false`, and the request returns to the regular endpoint, but the active tombstone still returns 410 first, and the revocation cannot be bypassed by closing L0. The CDN provider supports `PublicArtifactRevocation:CdnProvider=Cloudflare` directly connecting to the zone purge API, or using `Generic` + `CdnPurgeEndpoint` to access other HTTPS purge gateways; the configuration will be verified during the startup phase when enabled. The bearer token only enters the Authorization header, and does not enter the marker, response header, Pub/Sub payload, or log.

L0 artifact only accepts `GET`/`HEAD` of anonymous same-origin semantics; `OPTIONS`, other methods, and requests with `Origin` return to the regular endpoint/CORS pipeline at the classification stage, and the fast path does not inject CORS. Binary artifact accepts empty `Accept`, `*/*`, or `application/octet-stream`; HTML artifact only accepts empty `Accept`, `*/*`, or `text/html`; when not matching, it returns `406`. When the snapshot has not entered the `Ready` state, it returns `503` + `Retry-After: 1`, unless `PublicHotRead:FailOpenWhenNotReady` is explicitly enabled to degrade to the regular pipeline. List/category/tag (and diagnostic HTML) Serving misses are not a single `404`: last-good or fresh resident hits are `200`; not-resident / rebuild-pending misses are `503` + `Retry-After: 1`; true not-found (unpublished, deleted, or never existed under this snapshot's public visibility) remains `404` without `Retry-After`. See [PublicHotRead serving miss outcomes](../operations/public-hot-read-serving-outcomes.md). L0 negative responses such as `400`/`404`/`406`/`416`/`503` are fixed `Cache-Control: no-store`; `Range` request returns `416`. `.aeds` hit declares `Accept-Ranges: none`, and can return `Content-Encoding`, `Vary: Accept-Encoding`, and variant-aware `ETag` according to the artifact's pre-generated raw/br/gzip variant; when `If-None-Match` hits the current variant, it returns `304`. HTML artifact compiles the CSP nonce UTF-8 template during the release phase; the request only writes pre-calculated segment/slot, does not retain the original placeholder, nor re-scan the entire page.

L0 snapshot release is an atomic operation protected by budget. The candidate calculates raw/br/gzip, HTML/template, key/index, object/array/LOH, and current snapshot overlap before visibility; when any item exceeds the configuration, all reasons are aggregated and the old snapshot is retained. `runtime.publicHotRead` is the protected diagnostic contract, and anonymous readiness does not publicly expose capacity details. Article detail admission uses the segmented Top-K of access heat and recent release, and is constrained by resident bytes a second time; articles not admitted or evicted still go through the original binary endpoint/cache fallback, and cannot become text API or semantic degradation. The request writes directly from the snapshot's `ReadOnlyMemory<byte>` slice, and does not increase body copy due to statistics or eviction.

Publication sanity also binds `visibilityPolicy=published-visible-at-cutoff-v1`, `sourceVisibility=public`, the same `sourceVersion` as the candidate, `visibilityCutoffUtc` age, AEDS v2 schema/CRC/frame type, compression representation reversibility, and in-process HMAC. The repository does not have an independent `Private` article state; the private/non-public boundary is proven by "only `Published` can enter"; the real frame materializer of the projector must exclude `Draft`, `Scheduled`, `Archived`, `Deleted`, `IsDeleted=true`, future `PublishedAt`, and future `ScheduledPublishAt`/embargoed input before encoding. The candidate first performs cheap publication evidence/age checks, then performs resident budget rejection, and finally verifies all binary raw/br/gzip, HTML body, and actual CSP nonce template bytes; HMAC context includes route/list key, artifact/frame/version, ETag/cache/encoding, and HTML renderer/template metadata. After success, each binary request only verifies the variant to be written; HTML verifies body/template simultaneously. When exceeding `PublicHotRead:MaxSnapshotAge`, future cutoff, schema error, or HMAC mismatch, artifact bytes are not sent, the existing request feature is restored and then enters the original canonical endpoint; the background queues refresh at half of the age upper limit. Focused request testing must compare the fast response with the production mapped canonical endpoint response byte-for-byte. This check maintains L0 zero PostgreSQL/zero Redis: DB mutation holds runtime-scope/article owner advisory lock before commit and establishes `TransitionPending` tombstone; durable outbox CAS-promotes the same generation after commit; and `public-artifact-revocation` stage is fixed before the fast path; active tombstone returns 410 until a new snapshot is released and the corresponding generation is completed. The recovery after writer crash must first successfully obtain the same PostgreSQL advisory lock, and cannot use timeout to guess that the transaction has ended. The process-local HMAC only protects the memory integrity of the backing array after release, and does not claim cross-instance signature or WORM; Redis Pub/Sub has no subscriber ACK, so cross-node propagation linearization and snapshot convergence are still authoritative acceptance with #399 and #400 respectively.

Status code and frame catalog are in [`schemas-and-errors.md#aedsframetype-enum`](schemas-and-errors.md#aedsframetype-enum).

### Revision and Publication Coordinate

`article.current_revision_id` is the author-side currently editable revision; `article.current_publication_id` is the public-side currently immutable publication record. `article_publication` fixedly associates revision number, rights snapshot, optional responsibility snapshot, publication number, transition type, and publish time. Public list and detail must carry `currentRevisionId/revisionNo/currentPublicationId/publicationNo`, and body, tags, rights, and responsibility must be able to point back to the same publication record.

Immediate publish, first-time scheduled publish, scheduled update of published article, archive, restore, and rollback uniformly go through `ArticlePublicationTransitionWriter`. When a published article schedules future update, the article continues to maintain `Published` and uses `pending_publication_at` to record the switch point; before the point, the old publication remains readable; after the point, the worker creates a new publication, switches the pointer, and writes outbox with precise coordinates in the same PostgreSQL transaction. Any step failure rolls back and cannot expose half a set of new content. The complete model and restart-free fallback are in [article revision and publication coordinate](article-publication-revisions.md).

### Draft and Local Cache

Code evidence: [`AuthoringEndpoints.cs`](../../src/backend/Modules/Endpoints/AuthoringEndpoints.cs), [`AuthoringUseCasePorts.cs`](../../src/backend/Services/Authoring/AuthoringUseCasePorts.cs), [`useAdminArticleWrite.ts`](../../src/frontend/src/composables/useAdminArticleWrite.ts).

The server-side draft isolates with `ownerAdminPrincipalId + draftKey` and persists body, category/tag, publish status, scheduled publish time, Rights V3 `rights` policy, `clientRevision`, stable `serverRevision`, and `baseRevisionId` at the beginning of editing; this owner comes from the `admin_id` of the independent admin principal, and does not reuse the normal anonymous account `sys_user.id`. The first write must submit `expectedServerRevision=null` and create-only with `serverRevision=1`; subsequent auto-save submits the read `expectedServerRevision`, and the server only atomically updates and increments when equal. Retry with the same `clientRevision` and normalized content returns the current version but does not increment repeatedly; old tab or out-of-order save returns `409 draft_conflict` and does not overwrite. Conflict `ApiError.details` only contains the current version, update time, and truncated title summary; the client stops auto-retry and re-reads the server-side draft for manual comparison. Discard performs conditional delete through the `expectedServerRevision` query, and cannot delete drafts that have been updated by other tabs. Delayed auto-save and cross-device recovery must continue to carry `baseRevisionId`, and cannot be replaced with the subsequently read new article revision when recovering.

Browser short-term recovery uses bounded IndexedDB journal to save the latest unconfirmed body; records are isolated by irreversible admin identity hash, create/edit article key, and tab owner, and carry the original `baseRevisionId`, `serverRevision`, `clientRevision`, and body SHA-256. Body input first requests journal flush, then enters the server-side auto-save debounce; hidden `visibilitychange`, `pagehide`, `beforeunload`, and bounded periodic retry only request the same asynchronous IndexedDB owner, do not send synchronous network requests, and do not promise that transactions will be completed after power failure. Server-side success only confirms the corresponding record precisely with record id, `clientRevision`, and body hash; old response must not clear newer input. Journal only provides 168 hours, single record/single scope/global capacity-limited same-browser recovery, and does not replace admin-authenticated server draft; the at-rest payload is unencrypted plaintext UTF-8 and has local profile readable risk; no WebCrypto confidentiality claim is made; publish, delete, log out, change account, and private state cleanup will delete applicable records. When discovering that journal coordinates lag behind the current article/server revision, auto-save remains paused; the author must first compare, then explicitly recover or discard; recovery only replaces the body and continues along the existing revision conflict process. The retired `fsus:article-draft:create` and `fsus:article-draft:edit:*` localStorage metadata are only deleted during editor initialization and private storage cleanup, without decoding or displaying their values.

### Revision and Rollback

Article create is a safely retryable command within the admin principal scope. The request must carry the canonical lowercase UUID `D` format `X-Fsus-Client-Mutation-Id`; the server establishes a unique identity with `(adminPrincipalId, clientMutationId)`, and writes article, revision/release, outbox, and request SHA-256/complete result in the same PostgreSQL transaction. Same identity and request digest returns the original coordinate and marks `idempotencyReplay=true`; same identity but different content returns `409 article_mutation_content_conflict`; double-click, concurrency, timeout, and response loss must not repeatedly generate article or notification. `Articles:MutationIdempotencyEnabled=false` can hot-reload and only fail closed the new create as `503 article_mutation_idempotency_disabled`; read, update, rollback, notification stream, and binary infrastructure remain available. The table structure is additive; the table is retained when rolling back code; migration completion should be confirmed before re-enabling. The 48B response requires front-end and back-end coordinated deployment; old clients cannot be used for new server-side writes when they only accept the old length.

Historical rows must not be re-enabled; when the historical package lacks necessary rights, it fails closed, and cannot use the current policy or default policy to fill in. The editor only compares the current form with the historical version within the author workspace; rollback cannot write directly to the table.

Revision body uses immutable content blocks rather than saving Markdown repeatedly in each row of revision. `article_revision` saves content block reference and complete metadata; content blocks are addressed by SHA-256 of normalized Markdown; metadata-only and copyright-only revisions reuse the original block; body changes only create blocks. Each revision is rebuilt through its own reference, and no diff chain is introduced. A completely identical update returns the current coordinate and `no_change` after locking and confirming the base revision, and must not generate revision, publication, outbox, or notification. Old revision migration must first backfill and verify reachability, then clear the inline copy; orphan block cleanup must carry a time cutoff and check references again with `NOT EXISTS`.

The author-side article detail uses `currentRevisionId/revisionNo` as stable editing coordinates. Ordinary update's `ArticleWriteRequest V5` and rollback's AEDS JSON request must both submit the `baseRevisionId` obtained when reading; rollback does not provide force bypass. The server verifies the baseline in the article row CAS of the same transaction, and mismatch uniformly returns `409 article_revision_conflict`; its `ApiError.details` only contains the current `currentRevisionId/revisionNo/status/updatedAt`, and must not write body, tag, rights, publication, or outbox. PostgreSQL `xmin` is only retained as internal contention detection, and does not enter business request or response. After conflict, the frontend retains the unsubmitted form and requires reloading for comparison, and does not automatically replay; this also covers double-tab, delayed submission, and retry. Content import is fixed as create-new, and does not overwrite existing articles according to the source article ID of the exported metadata, so there is no need to forge base revision.

Each revision can bind the append-only `article_responsibility_snapshot` version chain. The admin side performs CAS with `expectedVersion`; saving only appends `responsibilityVersion` and retains `previousSnapshotId`; conflict returns `409 article_responsibility_version_conflict`; historical snapshots cannot be overwritten. When the currently published revision updates the responsibility information, the transaction creates a new immutable publication and explicitly references the snapshot, and simultaneously writes the `responsibility-updated` outbox carrying the precise coordinates of revision/responsibility/publication; AOT, AEDS, public sidecar, and notification are only updated by outbox replay. Admin-side `GET .../responsibility` returns the complete version history of that revision. Public current/historical sidecar must read along the explicit responsibility snapshot of the corresponding publication, and cannot leak the backend actor. Old public articles earlier than the revision table return deterministic site author inheritance in the current sidecar, using `revisionNo=0`, `proofStatus=unavailable`; specified non-existent or unpublished historical revision returns 404. Pre-publish governance rules remain unchanged, and cannot be transformed into keyword density or SEO/GEO/E-E-A-T score gates.

## Public Article Read Projection

The public contract and security chain of `GET /api/binary/article/{id}.aeds` remain unchanged: the request still first goes through `public_read`, RiskControl/PoW, and existing L0 artifact rules. After file/L0 article detail artifact miss, the application only allows executing a single prepared query of `public_article_projection(article_id PK)` and directly returning the encoded AEDS frame; this read must not join article/category/tag/rights/proof, nor re-estimate reading time or encode the complete projection at request time. The projection frame must simultaneously pass AEDS v2 header, supported ArticleDetail payload (currently newly written `ARD5` V5, read-only compatible with `ARD4` V4 and `ARD3` V3), CRC, and strong ETag verification; after hit, it only backfills the file/L1 path once.

Projection missing or corruption is a recoverable consistency fault: the request can enter the old source query fallback, but must queue repair; 30 seconds in-process negative cache suppresses repeated DB miss, and create/publish/restore/update/outbox replay synchronously clears this negative cache. `Database:PublicArticleProjection:Enabled=false` is a reload-capable restart-free fallback switch, which only stops direct projection reading, does not stop outbox projector, old query, authentication, `X-Fsus-*` headers, PoW, or unified AEDS error semantics.

Category/tag rename, rights/proof, scheduled publish, revision/content, and the full lifecycle mutation of the article must write `article_mutation_outbox` in the same transaction as the primary write. The event columns and payload must both save the precise revision/publication coordinate; replay only allows loading that coordinate, and expired publication events must not overwrite newer public projection. `article-detail-aeds` is still the required replay edge: when DB projection, shadow parity, and file artifact fail at any step, the edge/outbox cannot be marked as completed. The complete migration, backfill, gate, and fallback description are in [public article read projection](../performance-public-article-projection.md) and [publication coordinate consistency verification](../testing/article-publication-consistency.md).

Article mutation envelope v2 must also carry rights snapshot id, responsibility snapshot/version, `occurredAt`, `publicUpdatedAt`, and the before/after scope of category/tag/visibility; `releaseId` is the event field alias of `article_publication.id`. The dispatcher fails closed on column and payload alias/coordinate inconsistency. Superseded event does not send old notification nor rebuild old search/AEDS/AOT/HotRead, but persists the same explicit skip reason for each unfinished edge. Each irreversible consumer re-verifies the coordinate at its own read/release boundary: search query also constrains `article.current_publication_id=event.releaseId`, HotRead queue retains the event release coordinate, notification re-verifies before sending and carries `revisionId/releaseId` in `ArticleChangedPayload`. This schema does not add old text API, nor does it change AEDS frame layout; the new coordinates of the notification stream JSON payload are nullable backward-compatible fields, and legacy v1 remains empty.

## First Passkey Atomic Enrollment

New account creation is not synonymous with login. `anonymous/bootstrap` only establishes an explicit `provisional` account and short-term single-purpose enrollment authority; before the first Passkey verification, account `active` projection, and formal `UserSession` succeed in the same transaction, the system must not expose normal account capabilities or long-term cookies. AEDS continues to reuse `AuthLoginFlow`, explicitly expressing client state with `enrollment_required`, rather than guessing with `passkeyEnabled=false`.

Concurrency semantics uses server-side enrollment state/request hash as the authority: the same request can be recovered idempotently after response loss, and different requests or double-tab competition get conflict; cleanup can only delete expired provisional, and cannot delete already migrated active accounts based on "no Passkey". The second and subsequent Passkeys belong to the security credential change of the logged-in account, and continue to require formal session and action-bound step-up.

## Published Article Body Health Gate

Public article detail only treats non-empty `article_body.markdown_content` as publishable body. When a published article lacks the body row or the body is blank, the read chain returns stable `article_body_missing`, and cannot use `summary` to fill the body, nor write this result to ArticleDetail cache, AEDS, Public AOT, public-hot, or search body projection. Draft's empty body is still legal incomplete content, and does not reuse public corruption semantics.

After corruption is detected, the read chain only submits the article id and low-cardinality source to the local bounded repair queue. Repair must recover from the revision corresponding to `current_publication_id` and belonging to the same article, and require that `current_revision_id` does not point to an unpublished draft; after success, the cache and public artifact are uniformly invalidated and then rebuilt. When the revision/publication coordinate consistency cannot be proven, it remains fail closed, and the body is not guessed. The detailed runtime boundaries are in [`issue-1208-article-body-missing.md`](issue-1208-article-body-missing.md) and [`issue-1208-article-body-repair.md`](../architecture/issue-1208-article-body-repair.md).

## Article and Thread Comment Policy

Comment write policy is combined according to `site default -> article override -> thread state`. The public AEDS endpoint `GET /api/binary/comment/policy?articleId=&rootId=` still returns the existing `CommentPolicySnapshot` frame, but the author-mode switch and `snapshotHash` are the effective snapshots of the current article/thread; closing writing does not affect comment reading. `POST /comment/anonymous-ticket` and the final public/strong-anonymous submit must re-read the effective policy respectively; old tickets cannot bypass the closing or thread locking that occurred during the period.

Admin write is only located in the authoring API: article policy uses optimistic `expectedPolicyVersion`; thread lock only affects the target root tree. The slow mode uses the existing privacy-safe moderation subject hash as the key, and atomically advances within the comment transaction; stable device fingerprint is prohibited. Policy changes write append-only audit events, and broadcast through the existing comment-policy cache invalidation to make each node and composer re-take the snapshot.

## Cluster membership diagnostic boundary

`GET /api/ops/cluster/nodes` is an operational diagnostic route rather than a runtime business API. It returns the current membership, assignment, lease/checkpoint summary, lifecycle events, health and metric view as JSON and requires an independent admin principal with `system.config`, the `fixed_ip` rate-limit policy, and `no-store`. Anonymous users, normal signed-in accounts, and admin principals without that permission cannot read node identity, capabilities, load hints, active responsibilities, lease identity, or task progress.

The same response carries an additive `scheduler` object instead of adding another
operational route. It exposes the immutable assignment generation, observed time, mode,
enabled state, responsibility/replica-to-node edges, bounded placement score/reason,
optional fencing token, and unassigned causes. Lease diagnostics expose the opaque lease
ID, holder, fencing token, TTL and renew/expiry times. Checkpoint diagnostics expose only
version, byte count and SHA-256; they never return payload content. Redis key material,
network addresses, queue payloads, exception stack text and module request data remain
private. The complete graph has the same authorization, fixed-IP and no-store boundary.

The route does not add an AEDS frame, change `/api/binary/**`, or affect notification stream envelopes. `Runtime:Mode=single` returns a synthetic local healthy node and never registers the process in Redis. `static-role` and `adaptive` register the same stable capability catalog in Redis; business code cannot introduce arbitrary capability strings.

`POST /api/ops/cluster/nodes/{nodeId}/state`,
`POST /api/ops/cluster/scheduler` and
`POST /api/ops/cluster/leases/{leaseId}/release-expired` additionally require trusted
same-site origin/referer and a consumed `X-Fsus-Mfa-Proof` for `admin-sensitive`.
Operators can place a node in `Draining` or `Maintenance`, resume it as `Alive`, stop new
scheduling, or remove only an already-expired lease. They cannot force-release a live
lease, set `Suspect`/`Dead`, clear fencing counters, or expose checkpoint payloads.
Failure detection preserves operator states. Public reads, binary endpoints and
notification stream continue while scheduling is disabled. Returning to `single` is a
startup-mode rollback for the next process generation.

## Plugin Admin Control Plane Supplement

The plugin control plane belongs to the admin authoring API, and can only use AEDS v2 frames of `/api/binary/author/plugins/**`. The browser must not judge the capability risk level by itself, nor infer unreported remote nodes as loaded; permission classification, isolation state, and `not-reported` node status are all subject to the server-side snapshot. Installation, permission, configuration, and lifecycle write must stack independent admin principal, `system.config`, fixed IP rate limiting, and one-time admin step-up.
