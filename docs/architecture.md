## Overview

FsusBlog is a single full-stack system with "first-screen speed of public content + runtime consistency + security link integrity" as the core constraints.

```text
Intra-project performance baseline (Kestrel-only/single process)
Browser
  ├── First visit to the public page → Kestrel → Public AOT HTML shell / SPA index.html + client hydration
  ├── SPA Routing → Vue Router → Pinia Store → API/Binary/Worker
  └── Service Worker               → Local search index (available offline)

Kestrel (ASP.NET Core 10)
  ├── Auth / Rate Limiting / CORS
  ├── Redis L2 cache
  ├── PostgreSQL（SqlSugar ORM）
  └── Static file service (AOT cache volume)

Optional deployment tiers (not counted in project QPS baseline)
Browser
  → Nginx / Caddy / CDN / Reverse proxy (TLS, edge caching, carrier compression, etc.)
  → Kestrel
```

By default, the performance evidence only declares the baseline within the project: single process, Kestrel-only, no nginx/CDN/reverse-proxy cache, and no external compression layer. Production deployment can place nginx, Caddy or CDN in front of Kestrel, but this belongs to the operator deployment layer; if the stress test passes through this layer, the evidence must be marked separately and shall not be counted in the QPS conclusion of FsusBlog's internal optimization.

## Module boundaries

| Modules | Responsibilities |
| ------ | ------ |
| `FsusBlog.Server` | HTTP API, authentication, Rate Limiting, cache management, secure link, AOT output, notification stream |
| `FsusBlog.Client` | SPA, public page hydration, Wasm decoding, Service Worker search, status management |
| `FsusBlog.Shared` | Front-end and back-end shared binary protocol model (AEDS frame structure, contract structure) |
| `FsusBlog.Core` | POD encoding, decoding, mapping, and projection logic (pure computing layer independent of HTTP) |
| `FsusBlog.Server.Tests` | xUnit unit and integration testing, stratified by cleanliness level |

**Boundary Rules**:

- Both `Server` and `Client` can reference `Shared`, but each cannot directly reference the other.
- `Core` does not reference any HTTP, caching or authentication related dependencies.
- The `Client` side Wasm module (`wasm/`) does not reference any JS/TS code.
- `Shared` only carries cross-process stable DTO, AEDS/NotificationStream/POD contracts and response envelopes; endpoint request context, service commands, cache keys, and authentication intermediate states must stay in `Server`.
- The `Server` endpoint layer only does routing, input verification and response assembly. The binary header, frame name, device fingerprint, viewer identity, admin step-up proof and read-proof adaptation are injected through infrastructure services such as `IBinaryEndpointRequestContext` and `IHumanReadProofEndpointAdapter` respectively.

`UseResponseCompression()` for regular links is gated twice by `EndpointAwareResponseCompressionProvider` and does not represent global compression. The endpoint must explicitly carry `PublicResponseCompressionMetadata` and `AllowAnonymous`, the request must be HTTPS GET/HEAD without Cookie/Authorization/CSRF header, and the response must also be `200 + Cache-Control: public`, secure `Vary`, no cookie/content-disposition/existing encoding, and fall into the public text media type whitelist. Currently, only `DistributionEndpoints` and `IntegrityVerificationEndpoints` are registered; auth/admin/account/notification/WebSocket/dynamic binary/HTML/errors and personalized responses are failed closed by multiple layers of path, route-kind, auth/antiforgery metadata, principal, header, status/cache/media even if metadata is added by mistake. The provider determines when the response starts, so `Set-Cookie`, `private/no-store` or sensitive `Vary` written after the handler can still prevent compression; the inner provider only appends `Vary: Accept-Encoding` after passing it, retaining the existing country/region vary token. `ResponseCompressionPolicy:Enabled=false` instantly shuts down this universal compression branch via the reload-capable configuration source without changing the pipeline sequence or restarting.

The nonce HTML of Public AOT/PublicHotRead is compiled into an immutable UTF-8 segment template when the artifact is generated or deserialized; the request only writes the same random base64url nonce to the precomputed slot, and does a flush for `BodyWriter`, without performing full-page bytes→string→bytes conversion or placeholder scanning. The writer checks request cancellation at the first byte and at each segment/slot boundary, and pre-cancellation requests must not perform any `BodyWriter` to `Advance`. The publication parser fails closed on illegal self-closing markers, illegal unquoted attribute characters and executable closing tags carrying attributes, and cannot compile malformed HTML into publishable templates. Nonce entities are fixed to identity streaming, `Cache-Control: private,no-store`, and `ETag`/`304`; only static nonce HTML retains the pre-generated br/gzip variant and strong validator. The template is bound to renderer/frontend/artifact digest and exchanged with the immutable snapshot; the old snapshot can be recycled after it has no active references. Both security header middleware and PublicHotRead select the same CSP through `ShouldUseDevelopmentCspPolicy`; local release acceptance uses `Testing:EnforceProductionCsp=true` to retain Development fixture endpoints but verify the production policy. Non-Development cannot be downgraded by this switch. Template UTF-8 bytes, slot table, and the static inline SHA-256 feasibility list generated by the build are included in `PublicHotReadSnapshot.ResidentBytes`. By default, `PublicHotRead:MaxResidentBytes=0` automatically derives a budget based on the available memory at runtime. Publication fails if it exceeds the budget. See [CSP nonce UTF-8 templates](performance-csp-nonce-template.md) for design, compression choices, and verification commands.

PublicHotRead capacity is calculated based on the `independent-readonly-arrays-upper-bound-v1` physical model, rather than just frame count. snapshot records raw AEDS, br, gzip, HTML/template, key/index upper bound, artifact/object/array, LOH eligible, base/overlay/removed and article/list/taxonomy/HTML bytes by category; `MaxResidentBytes`, `MaxRawBytes`, `MaxCompressedBytes`, `MaxHtmlBytes`, `MaxSnapshotOverlapBytes`, `MaxArticleResidentBytes` and `MaxArtifactObjects` are in publish All over-limit items are verified and summarized at one time. A value of zero defaults to derived from `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes`'s container/cgroup visibility limit and does not read the total host RAM. When the candidate/current overlap is unqualified, the old snapshot remains active; after atomic exchange, use a collection that does not hold strong references to observe all retiring versions. The next publication will include N-1/N-2 still held by the reader into the overlap, waiting for the natural release of the old reader. `MaxRetiringBytes` is always executed within the publish lock and dynamically derives the default value from the container memory; `MaxRetiringSnapshots=0` and `RetiringSnapshotDeadline=0` indicate that publishing is not rejected based on the number or age of weak references that have not been cleaned up by the GC. Only explicit positive numbers enable the corresponding hard gate. In this way, the full refresh of the stale active snapshot will not be permanently blocked because GC has not occurred, and all surviving retiring bytes will still be included in the overlap/bytes hard budget. Snapshots still held by readers cannot be safely forcibly released by the LRU container, so when bytes or explicit count/deadline is reached, the new publication fails closed and retains the current active version. Only weak references released by the target will be cleared in retirement order. The in-process hot cache of the Public AOT shell uses an independent real LRU, which is limited to count/bytes/age according to `PublicAot:MaxMemoryCacheEntries`, `MaxMemoryCacheBytes` and `MemoryCacheEntryDeadline`; the zero value is also dynamically derived, and capacity or deadline elimination does not affect the disk shell and SPA fallback. HTML delta merges base/overlay/removed after reaching the bounded threshold; article detail is interleaved with views popularity and two recently released segments to form a deterministic Top-K. Then, subject to the article resident bytes limit, cold miss rolls back the existing versioned L1/L2/DB path. Precompressed variants are only admitted during the publish/backfill phase based on minimum size, compression gain, and client share; the request path is still a read-only slice, not a copy. The current evidence is to choose independent read-only arrays instead of packed/mmap: it already provides zero body copy, forcing pack to introduce full merge copy in every snapshot build; switch release-scoped pack only when object management/LOH/GC gatekeeping proves that it becomes the main bottleneck. See [PublicHotRead residency](performance-public-hot-read-residency.md) for details.

PublicHotRead sanity gate and capacity gate share the same publication lock: candidates first check publication evidence and visibility age/future cutoff, then reject raw/compressed/HTML/overlap budget, and finally check AEDS schema/CRC/frame type, br/gzip reversibility and complete snapshot HMAC. If any failure occurs, the current snapshot is retained. The seal of each immutable binary variant is bound to the route/list key, frame/version, and ETag/cache/encoding; the HTML body and the real CSP nonce template bytes are sealed and bound to the renderer/template metadata respectively. The hit path only recalculates a binary HMAC that will be written out, and the HTML also verifies body/template; when the tamper exceeds `MaxSnapshotAge`, `fsus.hotread.sanity.fallback` is recorded and restored to the canonical endpoint, and PostgreSQL/Redis sanity query is not performed. `PublicHotReadStartupWarmupService` queues a full refresh at half the age limit, and the projector scope is released immediately after the first build. When fresh `PublicHotReadStore` has no published baseline, the article/view delta obligation restored by the worker must be upgraded to a full snapshot and completed according to the full revocation and distributed reconcile coverage semantics. It is not possible to first publish a Ready snapshot of the missing category/tag artifact or wait for age refresh. DB mutation consistency is not impersonated by HMAC: the write path holds the scope-bound PostgreSQL owner lock and establishes Redis `TransitionPending` tombstone before commit, the durable article mutation outbox advances the same generation after commit, the pipeline fixes `public-artifact-revocation -> public-hot-read-fast-path`, and returns 410 during the transition; the new snapshot is successfully released and the generation is confirmed before compare-delete tombstone. The main risk is that consecutive refresh failures cause L0 to be downgraded to a regular endpoint and increase latency, without continuing to return stale or overwritten bytes. The fallback without restarting is still hot update `PublicHotRead:Enabled=false`, and the revocation stage remains enabled. Redis Pub/Sub itself still does not have subscriber ACK; cross-node invalidation is converged by the PostgreSQL durable per-node ACK ledger. For the complete contract, see [Distributed cache invalidation](architecture/distributed-cache-invalidation.md).

The single-node span representation coordinates of public artifacts only use `src/shared/Contracts/Validation/public-representation-coordinate.json` as the machine-readable authority. The manifest does not copy the release ID or AEDS wire constants, but instead references `release-id-contract.json` and `aeds-protocol.json` respectively; the generator `tools/contracts/generate-public-representation-coordinate.mjs` only projects the fields/transition surfaces required by Shared C#, frontend TypeScript and Wasm C++. Coordinates are sealed in route/source/revision/publication/visibility, renderer/release/assets, AEDS schema, document/sidecar digest, SEO and hydration page kind in the canonical projection, AOT build, HotRead snapshot build or artifact publish phase; request hits only compare the values ​​carried with the artifact, and new PostgreSQL/Redis queries for completion or verification of coordinates are not allowed.

The transport map fixedly covers `canonical -> PublicAOT entry -> HTML`, `hydration payload -> sidecar`, `canonical -> PublicHotRead AEDS/HTML`, `cache/file -> runtime entry`, `HTML/sidecar/AEDS -> browser hydration` and `Service Worker shell -> navigation`. `tools/contracts/public-representation-coordinate.mjs` consumes the same manifest, compares the `preserves` field of each transition, and uses length-prefixed UTF-8 + SHA-256 to form a stable identity; the local closed-loop harness compares the same business invariants of the two paths AOT/sidecar/hydrate and HotRead/AEDS/decode. Renderer/assets/source/digest, incorrect sidecar URL, old release shell or snapshot source mismatch always return the deterministic fallback declared by the manifest and must not continue to hydrate semi-compatibility state. Evidence only allows fixed layer/transition/counter, route, digest, release and asset identity are prohibited from becoming metric labels; each artifact rebuild of a mutation rebuild is counted as amplification.

This coordinate contract does not change the middleware order, AEDS v2 wire, existing release authority, or extend the multi-node convergence commitment of #428. When a coordinate checker or build surface problem occurs, the current application commit can be rolled back; old running artifacts continue to be managed by the existing renderer/assets/hash gate. There is no need to restart when an actual mismatch occurs: AOT/cache entry executes evict-and-rebuild, HotRead retains the last qualified snapshot or returns to the regular endpoint, and the browser/Service Worker uses network canonical navigation; if necessary, `PublicHotRead:Enabled=false` can still be hot updated to close L0, but hydration, AOT or Service Worker must not be disabled to fake consistency.

The above application-level and endpoint-level sequences are still directly driven by `s_applicationPipelineStages` / `s_endpointPipelineStages` in the pure assembly type `WebApplicationCompositionExtensions`. The runtime registration is only delegated to the explicit runtime module and does not implement route decision, HTML output or business state machine. The order must be maintained `trace correlation -> classifier -> early request audit context -> dedicated rate limiter -> security gate -> writer -> fallback restore -> endpoint pipeline`; the runtime catalog fails closed before stage registration, the middleware sentinel will prove that the L0 hit does not reach the inapplicable endpoint-only stage, and the source checker is responsible for preventing drift at both ends. See [Composition root boundary](architecture/composition-root-boundary.md) for boundary and return gates.

JWT bearer cookie entry is done within `UseAuthentication()`. `OnMessageReceived` only parses the admin cookie preference once for the same request, and reuses the admin raw access token to `OnTokenValidated` through `HttpContext.Items`; the endpoint metadata/path decision must not be scanned repeatedly within the same request, and the admin session checksum and host-prefixed cookie selection remain unchanged. legacy plain cookie fallback removed: production only reads `__Host-*` cookies, development environments only read current non-host-prefixed cookie names if `AuthCookies:AllowInsecureTransportCookies` is explicitly enabled.

When writing a cookie in the authentication response, the ordinary account `SessionId` cookie is explicitly passed into `AuthCookieService.SetTokenCookies` from the session id known by the login/refresh issuance path. The issuance result of the JWT helper carries both token and absolute `ExpiresAtUtc`. Normal login, MFA, Passkey, refresh rotation and admin session paths all pass this value to the Cookie writing layer as it is; the Cookie layer must not re-read `Jwt:AccessTokenExpiresMinutes`, reversely parse the access token, or maintain an independent period. When the session id is missing, only the session cookie is skipped and the access/refresh cookie policy is not changed. The first Passkey uses independent `EnrollmentToken` / `__Host-EnrollmentToken` cookies, the Path is fixed in `/api/binary/auth/enrollment`, and Access/Refresh/SessionId is not reused; bootstrap only writes provisional account + enrollment row, `AccountEnrollmentService` completes credential + active + formal session in one transaction, and `AccountEnrollmentCleanupWorker` only deletes expired provisional data through scoped service. Both `JwtHelper` and the normal login workflow refuse to issue official tokens for non-active registration states.

Refresh rotation's database CAS and HTTP cookie delivery are explicitly arranged by the endpoint: after commit, the new hash/session is checked through `IUserSessionCommandService.VerifyRefreshRotationAsync`, then three ordinary account cookies are added, and then the same check is repeated, and finally the `EmptySuccess` frame is executed. When the pre/post check or Cookie append fails, the response has not yet started. The endpoint appends the common account Cookie deletion header and returns 401; the admin principal cookie plane is not affected. This sequence does not introduce old token grace, nor does it pass `HttpResponse` across layers to domain services. There is still a non-transactionable window between final verification and network delivery, and the client only performs one network retry.

Route assembly is layered by `MapFsusOperationalRoutes`, `MapFsusApiRoutes`, and `MapFsusPublicRoutes` to avoid touching health probes, notification streams, SPA fallbacks, and static file strategies at the same time when adding new APIs.

The runtime DI composition root is split by boundary: Infrastructure registrations are hosted by `AddBinaryRuntime`, `AddNotificationRuntime`, `AddCrawlerAndSearchRuntime`, `AddFileAndAuthRuntime`, `AddAuditRuntime`, `AddMessagingRuntime`, `AddCacheRuntime`, `AddIdentityRuntime`, `AddBackgroundRuntime`, `AddSpaRuntime`, `AddObjectPools` segments; realm registrations are hosted by `AddContentRuntimeServices`, `AddUserRuntimePorts`, `AddGeneralDomainServices`, `AddCoreBridgeServices` are carried in segments. New services should be given priority to fall into the corresponding groups to avoid turning Bootstrap into a borderless registration list again.

When factory or keyed descriptor cannot be restored by reflection alone, it is conservatively included in `opaqueFactories` and is still covered by container build and Roslyn source code access control. Background tasks must not inject scoped DbContext/business services into the constructor; the scope created through `IServiceScopeFactory` must be `await using`, and the key DbContext scope uses `DependencyInjectionScopeTelemetry` to form `di.scope` Activity, and is closed after scope dispose. See [DI lifetime validation](architecture/dependency-injection-lifetime-validation.md) for complete rules, metrics and fallbacks.

The audit lexicon runtime is hosted by `ModerationDictionaryService` and is registered in the content domain service group. It builds immutable snapshots from `config/moderation/dictionaries/**` and `config/moderation/region-policies/**`; the global lexicon goes into `ContentFilterService` for hard interception, and the regional policy combination goes into `RegionLegalModerationService` to calculate submit/viewer action, `blocked_regions` and replay diff. Continue to use the old snapshot when reload fails and write to `dictionary_reload_failed` / `region_policy_reload_failed` through the audit channel. See [configuration layout](configuration-layout.md) for configuration root and project ownership.

The optional anti-spam model is carried by `AntiSpamModerationService`, with default `Moderation:AntiSpamModel:Enabled=false`, disposal mode `score-only`, and `FailOpen=false`. Comments that require a model are first submitted with `Pending` and call the built-in `FsusAntiSpamModel` portable runtime scorer after writing regional compliance; runtime reload only loads the model data package and verifies `manifest.json`, digest, signature, runtime format, threshold policy and `test_vectors.jsonl`. After the verification is passed, the active snapshot is atomically replaced with the immutable scorer snapshot. The model first writes the `comment_moderation_signal` risk signal, and then `CommentModerationDispositionPolicy` decides whether to automatically pass or hide it in explicit mode. The model must not automatically pass when the regional policy priority is higher than the model: `RegionCanPublish=false`, `RegionRequiresManualReview=true` or `RegionHideUntilReviewed=true`; if the runtime is missing, times out, loads or fails to score, write `unavailable/error/contract_invalid` signal and retain `Pending` by default. It can be converted to `Approved` only if the operation and maintenance explicitly turns on `FailOpen=true` and the region/anonymity policy allows it.

`BannedUserMiddleware` is the only implementation of runtime ban checking and old filter compatible aliases are no longer retained; new call points must be named using Middleware. This middleware must first be shunted according to `identity_kind`: `admin_principal` does not read the ordinary `sys_user` status or blacklist, and directly hands it over to the subsequent admin authorization/session semantics; only ordinary accounts enter the delete/ban write lock. Ordinary account access tokens must carry `account_subject_hash` read from `sys_user.account_subject_hash`, and the L1 account-state key of the middleware is fixed to `account:state:{accountSubjectHash}`; missing or malformed claims directly return 401, and account id, handle, or old cache snapshot derivation is not allowed. The account snapshot cache namespace is fixed to `account:subject-v1:{accountId}:v{version}`. When the old payload is missing physical fields, it must be missed and checked back in PostgreSQL. The admin access token must be checked back by `admin_session` and `admin_principal` in the `AdminSessionValidationService` request period after JWT basic verification. Revoke, disable, idle/absolute expiration, token hash mismatch or session/principal inconsistency must fail closed, and admin cookies must be cleared. The root admin bootstrap is the only initialization write of the admin principal plane. The complete path must take PostgreSQL xact advisory lock, recheck active root, write principal/credential/session/audit in the same DB transaction, and be concurrency covered by the active-root partial unique index. Admin passkey login, step-up and session revoke are written to independent `admin_audit_log`, and the request path only enters the bounded queue through `IAdminAuditLogChannel`; when the queue is full or the background batch write fails, fallback direct write must be performed without changing the existing admin audit query output.

Endpoint-level policies such as restricted account security closure and authentication response `no-store` are only allowed to be declared through endpoint metadata. `Infrastructure/Policies/EndpointPolicyMetadata.cs` provides `AllowRestrictedAccountAction(RestrictedAccountAction.*)` and `RequireNoStoreResponse()`. The runtime middleware reads the routing metadata execution strategy to prevent `/api/...` string matching from becoming invalid during routing migration. Ordinary messages, comments, content and other business writes must not declare restricted account release metadata.

Production startup verification is incorporated into the DI lifecycle via `ProductionStartupValidationHostedService`. When the production environment verification fails, `productionStartupValidation=degraded` of `StartupRuntimeState` is written and logged, and the process remains observable; the readiness probe is still determined by DB/Redis connectivity. Non-production environment reports `skipped`.

The cross-instance startup mutual exclusion of Schema migration uses the same PostgreSQL session advisory lock, but the waiting party can only poll `pg_try_advisory_lock` for short transactions and cannot use blocking `pg_advisory_lock` to hold virtual transactions for a long time. The migration plan contains `CREATE INDEX CONCURRENTLY`, and the virtual transaction blocking the waiting party will reversely block the lock-holding instance from completing the index and form a deadlock. The polling connection holds the session lock after success and is not explicitly unlocked until all PreCodeFirst, CodeFirst, PostCodeFirst and model verification are completed; cancellation or exception must close the connection to release the lock. There is no need to change the schema for runtime rollback: keep one instance to perform migration, and the remaining instances wait or are paused and started by the orchestration layer. Mutexes cannot be bypassed to execute DDL in parallel.

Safe operation policy by `ISecurityAdminPolicyService` exposes an in-process immutable snapshot, exposing read, PoW, RiskControl and background overview read-only of this memory state. When background `/api/binary/admin/security/**` modifies the AntiCrawler/PoW policy, additional `security_policy_snapshot` versioned records are written within the original admin principal, `system.config`, `X-Fsus-Mfa-Proof` and high-value audit boundaries; `SecurityPolicySnapshotHostedService` must be ranked after `LifecycleHostedBootstrapService` during the startup period, and the memory snapshot is loaded from the active policy. When active deserialization fails, it falls back to the latest last-known-good version. The request hot path must not query PostgreSQL synchronously for the read policy; a persistent write failure will cause the management write request to fail and retain the log diagnosis, and the next startup will still restore the runtime policy with the last available active/LKG persistent snapshot.

The end-to-end readiness of the RiskControl challenge is closed by the versioned capability registry and cannot be replaced by provider DI registration numbers. The back-end catalog and front-end registry record provider, UI/headless executor, host, cancellation capability and action surface for each `SecurityChallengeKind`; orchestrator presses action fail closed before calling provider, and production readiness also verifies each kind of active policy. The management side displays provider/executor/UI host/headless host/policy respectively, and does not display the PoSpace/Passkey placeholder component as ready. There is no need to restart when rolling back: use reload-capable policy to switch unqualified kind subsystems to disabled/observe or roll back LKG; the manifest itself can only be changed along with the verified static resource build.

The combined RiskControl challenge is aggregated by a UUIDv7 `envelopeId`, and `SecurityChallengeOrchestrator` solidifies the original sequence of `RiskDecision.RequiredChallenges` into up to 8 member bindings; a single challenge is just the same envelope state machine of `memberCount=1`. Redis saves the ordered challengeIds/requiredKinds/verifiedMembers/version hot state with TTL, which must not be later than the shortest required member expiry; each verify advances `completedCount` after passing versioned CAS atomic verification envelope, next ordinal, member state, action/route/subject/client/device, and policyVersion. PostgreSQL `security_challenge` / `security_challenge_attempt` still undertakes auditable source and recovery diagnosis based on member challengeId, and cannot replace envelope state release when Redis miss, disconnection or CAS conflict occurs. member verify only returns progress; mint an aggregate proof after all required members are verified, and claims are additionally bound to envelopeId and ordered requiredKinds. Among the final three compatible headers, challengeId/kind still takes the last ordered member. The business filter must also verify the complete ordered requiredKinds according to the current RiskDecision. The last member cannot be regarded as the client to complete the declaration.

The front-end composition only registers one envelope runner. Both the UI challenge host and the `notification.subscribe` headless host submit envelopes to it, and do not copy the assignment loop, provider payload lookup, verify progress or proof-store logic respectively. The runner executes sequentially by default; when the policy explicitly allows parallelism, it must also limit expensive workers such as PoSpace and perception through fixed small semaphore, and keep cheap executors and expensive executors pooled to avoid unbounded CPU/memory occupation by a maximum 8-member envelope. refresh, cancel, identity changes, route generation changes, component unmount, and notification dispose all advance the runner generation, terminate the entire envelope, call the binary cancel transport to undo the server state and reject late result submissions. Downgrades without restarting only hot update the policy to disable multi-challenge band, switch affected actions to observe/disabled or roll back LKG; the signed envelope remains fail closed until the TTL expires, it is not split into multiple independent proofs, and `assignments[0]` is not restored.

PoSpace parameters are generated from Shared authoritative source `src/shared/Contracts/Validation/Security/pospace-v1-contract.json` through `tools/contracts/generate-pospace-v1-contract.mjs` to Shared and frontend, provider and runtime do not each hold a number. Weak devices are unsupported and re-signed but still reused. `/api/binary/security/challenge`: endpoint parses bounded attributes. `PoSpaceUnsupportedReissueService` verifies persistence facts through an independent assignment store. First clear the `SecurityPoSpaceChallenge` one-time cache and revoke the old challenge, and then select an alternative ruling based on the current RiskControl snapshot. This boundary does not put database queries or client capabilities into the composition root, nor does it change the AEDS frame layout. Runtime downgrade can disable PoSpace/rollback LKG through hot update policy; when fallback is unavailable, fail closed and no restart is required.

Runtime observability is managed centrally by `Infrastructure/Observability`. `FsusObservability` exposes `ActivitySource=FsusBlog.Server` and `Meter=FsusBlog.Server`, and limits custom properties to the low-cardinality `fsus.*` whitelist. ASP.NET Core, HttpClient, runtime, Npgsql, notification stream meter, cache, PublicAOT, search and scheduled-publish workers all enter the same trace/metric plane; `ObservabilityCorrelationMiddleware` writes `Activity.TraceId` back to `HttpContext.TraceIdentifier` and `X-Fsus-Trace-Id` so that error responses, Serilog/audit and standard collector traces can be associated by the same ID. `RecordSecurityEvent` is the Shield/RiskControl high-frequency hot path. The fixed `(operation, reason, result)` combination must reuse the preheated/bounded `TagList` cache. The enum source must go through `SecurityRiskReason` overload. The new cache hit rate, miss count and record elapsed indicators must not change the tag name and value of the original `fsus.security.event.count`. The OTLP exporter is closed by default and will be exported to the collector only after `Observability:ExporterEnabled`/`OTEL_EXPORTER_OTLP_ENDPOINT` is opened.

The cache management manifest is generated by `tools/cache/export-cache-governance.mjs` from `CachePolicyRegistry`, `CacheTag`, `HttpCachePolicyCatalog` to `docs/cache-governance.catalog.json`. `tools/check-cache-governance.sh` will verify the list in fast gate to prevent cache key/tag/catalog and document evidence from drifting.

The L1 lifecycle of the precoded AEDS frame is managed through the independent `IOwnedFrameCache` boundary, and the `ICacheRawReader` raw payload port maintains defensive-copy semantics. The cache miss directly writes the real POD writer to the final frame buffer of `OwnedAedsFrame`; the consumer can only hold a read-only lease. Redis serialization, concurrent response, replacement/eviction/invalidation, cancellation/exception and shutdown must all retain backing before the last lease is released; precise key and batch/prefix invalidation obtain a certain sequence of mutation gates by Redis key when deleting L1/L2 to prevent old L2 reads from being reinstalled after deletion. Owner retirement stops new readers immediately, but logical/capacity residency is not deducted until the backing is actually returned or cleared, so in-flight readers are not falsely reported as released. Fixed logical resources cannot only rely on I/O gate to determine source freshness: AdminStats generation reads with Redis `INCRBY 0` authority without going through process L1; the new generation simultaneously isolates frame, core aggregate, overview, recent and region source identity, so the old L1 across instances or the deletion window after release cannot install the old source into a new frame. Rebuild checks generation before and after source read, rereads when drifting, and only exports without installing when churn continues; invalidation cleans up previous-generation and legacy identity. Sensitive frames are cleared by `AedsFrameSensitivity` by default, and only explicit public-immutable allowlist can be skipped; L2 frames that cannot be verified are all cleared conservatively. This boundary only declares to eliminate the payload/frame application copy of miss/rebuild in this process. It does not assume zero copy inside StackExchange.Redis, socket or file system, nor does it change TTL, ETag or AEDS v2 wire contract; new generation only enters cache identity. PublicHotRead snapshot and file artifact continue to use exact array, but the projector writes the final frame directly to avoid the exact payload intermediate array. Measurements, owner state machines, and focus verification are available in [AEDS cache-miss owned-frame](performance-aeds-cache-miss-owned-frame.md).

## Front-end Binary combination boundary

Front-end AEDS links are organized by unidirectional boundaries of `contracts → codecs/adapters → composition`:

- `src/frontend/src/contracts/binaryApi.ts` and `binaryTransport.ts` are API/adapter/worker shared type boundaries and have no runtime dependencies;
- `src/frontend/src/codecs/binary/` is only responsible for the general POD reader and request encoder, and the business API does not import the response adapter;
- `src/frontend/src/adapters/binary/` only maps the verified payload to contract and does not import the API implementation;
- `src/frontend/src/services/binaryTransport.ts` is responsible for requests, errors and main thread/worker scheduling, and only accepts `BinaryFramePayloadDecoder` injection;
- `src/frontend/src/composition/binaryDecoderRegistry.ts` is the only combination root of a specific frame decoder. The browser request is injected by `composition/binaryTransport.ts`, and the worker directly consumes the same registry at its own entrance.

Therefore, when adding a frame mapper, you can only add explicit registration in the registry. You cannot restore the adapter barrel, let the transport import a specific business adapter, or let the adapter read the API response type in reverse. `check:binary-import-boundaries` scans the static import graph and gates this constraint with strongly connected components. When rolling back, you can point the composition root to the previous version of the registry without modifying the request path, frame number or transport behavior; JSON/dual transport is not allowed to be used as fallback.

### Public AOT single rendering chain

`Home / ArticleDetail / Filter / Archive / About / Privacy / Guidelines / Copyright` on the public page uniformly follows a rendering pipeline:

```text
IPublicAotRouteRegistry
  → strict route identity（Complete path + positive integer/valid single segment slug)
  → cold-miss status classification（Success / NotFound / Gone / TransientFailure）
  → IPublicAotBootstrapProvider（output typed PublicPageSnapshot)
  → PublicAotRenderRequest + PublicAotRendererPayloadMapper
  → IPublicAotEntryRenderer（Node/Vue SSR worker pool）
  → src/public-renderers/renderPublicPage.ts（Entry) + src/public-renderers/publicEntryRegistry.ts/pageAssemblies.ts/scaffold.ts

  → versioned AOT HTML document cache + hydration `.aeds` sidecar
```

Key constraints:

- `src/frontend/scripts/server-public-ssr.mjs` is permanently resident in AEDS line protocol worker mode and supports `buildEntry` / `validateBundle` / `health` / `shutdown`; `PublicAot:SsrWorkerMode=PerRequest` can be used as emergency fallback.
- `PublicAotSsrRuntimeState` aggregates backfill queue scheduled/dropped/completed/failed counters, worker restart/stderr warning, timeout/renderer/DB gate/document compose/cache write failure classification, circuit breaker, route quarantine and SSR worker resource snapshot. `/internal/public-aot/health` reuses `X-Fsus-Public-Aot-Token` and outputs resource check snapshot, Node probe, `validateBundle` sample probe and runtime snapshot; `tools/operations/public-aot-health.mjs` is the release/ops diagnostic entrance.
- `PublicRouteIdentity` performs a complete match on the article/category/tag dynamic path and no longer intercepts the first segment from the prefix; unknown, zero value, extra segment and non-existent taxonomy return 404 in the first server response. Trailing slash except `/` single hop 301 by public route composition to no trailing slash canonical.
- `PublicSearchRequestPolicy` normalizes before SPA fallback reads the template. `/search`: shared `PublicSearchRoutePolicy` generates the length, enumeration and page number boundary of q/sort/page to the front end. The server single-hops 301 for duplicate/default/illegal combinations and returns 400 for dangerous over-limit input; noindex is set for both success and failure first responses. The search route does not enter the Public AOT registry/sitemap/JSON-LD, the front-end router only mirrors the same policy and atomically replaces the search noindex head in the SPA navigation.
- Label route identity only has `tag:{id}` / `/tag/{id}` as indexable success identities. `tag-name:{name}` is a read-only migration identity: the shell calls the provider before reading any old name AOT cache, and single-hops 301 the current name or `tag_url_alias` to the ID; the name route does not enter the manifest, backfill, or successful navigation snapshot. The label update transaction first persists the old name alias and then writes the new display name, so the canonical does not change with the rename.
- `PublicAotShellService.RenderClassifiedAsync` calls the corresponding provider to establish the real state before cold miss queuing backfill; only `Success` can be queued. `NotFound`/`Gone`/`TransientFailure` map 404/410/503 independent noindex HTML respectively. Negative responses do not enter the AOT cache, do not carry successful SEO metadata, and do not start SPA. This classification only occurs in AOT miss/dev-source bypass; fresh artifacts still use the original hot path and mutation invalidation to avoid degenerating each hit into a database read.
- `IAotSeoConfigSnapshot` is the SEO/compliance read entry of AOT bootstrap, using 30 seconds TTL to limit `GetSeoConfigAsync` / `GetSiteComplianceConfigAsync` DB round trip; snapshot refresh reuses scoped `ISystemService` / `ISqlSugarClient` within a DI scope, so the two cache-miss reads must be serial and cannot overlap commands on the same Npgsql connection. Different requests are still merged by the snapshot refresh gate. When saving SEO or compliance configurations, the snapshot must be synchronized and invalidated by `ICacheInvalidationDispatcher`, so admin modifications can be converged without restarting.
- SSR worker circuit breaker only protects the backfill lane: after continuous worker-level failure is opened, the new backfill is short-circuit; after cooldown, only one half-open probe is allowed, and it is closed only after success. Repeated failures of route-level renderer/document compose will be quarantined by `PublicPageKind + routeKey` and cleared after route/content/settings invalidation or TTL expiration. The public read path must continue to return fresh/stale AOT or SPA fallback, and anonymous reading must not be blocked by breaker/quarantine.
- Public AOT backfill obtains `page kind + route key + frontend asset version + optional test session` lease before entering snapshot/SSR. `single` runtime uses the in-process local handle and does not access Redis; `static-role` / `adaptive` runtime uses `PublicAotBackfillLease` Redis key, 30 seconds TTL and 10 seconds compare-renew, and release only allows token owner compare-delete. In case of lease competition, temporary unavailability or loss of renewal, only the background work will be canceled and the SPA fallback will be retained, and will not be included in renderer failure/circuit breaker; the route that has been quarantined will be rejected again before grabbing the lease. After the node crashes, the lease is automatically released by TTL, and other nodes can take over on the new miss. Before writing artifacts, verify the frontend asset version and invalidation version when queuing, and verify again after active-release commit guard. The old lease/render cannot overwrite the new asset generation. The safe downgrade of Redis lease failure does not require restarting: the new backfill automatically stops writing, and public reading continues through the existing fresh artifact or SPA fallback; after restoring Redis, new misses naturally compete again, and forced writes are not allowed to bypass the lease.
- The AOT document cache is only allowed to be written by the server `server-ssr` backfill; clients, managers and scripts are not allowed to upload AOT bundles.
- AOT document cache writes the versioned artifact path according to the frontend asset version; old version artifacts can only be cleaned in the background or rejected due to version incompatibility, and cannot be directly returned to the public URL.
- `PublicAotDocumentComposer` is only responsible for document packaging, SEO headers, bootstrap scripts and hydration sidecar marker injection, and is not responsible for page business structure repair; `PublicAotDocumentService` writes the hydration AEDS frame as raw `.aeds` sidecar to `wwwroot/aot-cache/payloads` in the compose cycle. The sidecar URL is derived from the payload SHA-256 content hash, and the static response uses `application/vnd.fsus.aeds` and `public,max-age=31536000,immutable`, so the new HTML always points to the new payload, and the old payload only needs to be cleaned asynchronously in the background.
- AOT document cache artifact records the URL, SHA-256 and relative path of the hydration sidecar; old artifacts are read back from the HTML marker when metadata is missing. Before the file cache is hit, you must confirm that the sidecar exists and that SHA-256 is consistent with the URL hash. Otherwise, delete/eliminate the HTML entry and use miss reconstruction. key/prefix/all invalidation deletes the HTML document entry, but retains the content-hash sidecar; the sidecar does not have stable URL reuse semantics, so the expired document will not continue to be reachable. The authority of the invalidation coordinate is a single state in Redis isolated by runtime scope with content digest; startup and lookup must verify the scope, digest, key/prefix coordinate that is non-negative and does not exceed the global watermark, and the reserved all coordinate. Fail closed when the read fails or is tampered with, and cannot be recovered with in-process zero values, file name scans, or local counters. The first empty deployment will first write the scope-bound `initializing` witness in `public-aot/.generation-authority` of the current release, create generation 0 with Redis `SET NX`, and then complete the witness atomically; witness only proves that the authority has been initialized and does not provide a generation value. When the Redis key is missing, any retained release has completed witnesses, witness is damaged, or existing Public AOT artifacts will refuse to start. Only empty storage that can be proven to have not been initialized and has no artifacts can continue the first bootstrap. Each key/prefix/all mutation uses compare-and-set to monotonically advance the global watermark and record distributed invalidation apply evidence. Therefore, restart and node local mirrors that are older cannot re-hit the old `:iv:0` artifact. Background compaction is only executed when the durable artifact registry is readable, and always retains the global watermark, all coordinates, and the key/prefix coordinate referenced by the current artifact in the registry; the authority is not rewritten when the registry is missing.
- The public paging of Home/category/tag writes the specification page number into `routeKey` (`:page:N`) and the specification query, so each page has independent document cache, navigation snapshot, hydration seed, payload hash and ETag. The article mutation no longer only bumps the first page key, but clears the Home/Archive/Filter page prefix and all hot HTML to ensure that changes in category ownership or sorting will not leave deep paginated old products; the first page is backfilled first, and the remaining pages are reconstructed by full manifest or access miss. Turning off Public AOT/SPA takeover during rollback allows the paging `<a href>` output by the server to navigate the entire page, and the page itself does not rely on click scripts.
- AOT file shell cache also maintains path -> `(LastWriteTimeUtc, length, decoded entry)` metadata cache in addition to memory hit; repeated file reading and binary decoding can be skipped when the same artifact does not change. `PublicAotCacheEntryBinaryCodec` reserves a 256-capacity decoded entry cache, and the compose/SEO snapshot/codec/file cache is exposed to hot paths through `fsus.aot.compose.elapsed`, `fsus.aot.bootstrap.seo_snapshot.hit_ratio`, `fsus.aot.cache.codec.hit_ratio`, and `fsus.aot.shell_cache.file_hit_ratio` respectively.
- Multi-node deployment must allow `wwwroot/aot-cache/frontend/**` and `wwwroot/aot-cache/payloads/**` to use the same shared artifact storage or shared volume; otherwise, the current Public AOT cache only supports single-node/shared storage consistency. Before v1.3, Nginx/CDN or cross-node replication delay was not considered as a prerequisite for correctness. Local node loss or hash mismatch would fail-closed as a cache miss.
- Only `PublicPageSnapshot` / `PublicAotRenderRequest` is passed between Provider, shell service and renderer. `PublicAotRendererPayloadMapper` does the unique dictionary payload mapping before entering the Node worker; it is forbidden to restore the anonymous object graph or each provider to spell the payload by itself.
- Filter AOT takes out `Name` and nullable `Description` at the same time in the same round of search when parsing taxonomy identity, and writes `PublicFilterPageSnapshot` and renderer `filter.description`. Missing description remains `null`. Category/Tag is still `PublicPageKind.Filter`, Search does not enter AOT; AOT HTML and hydration share the Filter header contract, and a second query or new Category/Tag page kind cannot be added to Description.
- `PublicAotDocumentService.ResolveDescription` reads the hydration `filter.description` for Filter first, and falls back to bootstrap when missing; the non-empty taxonomy description follows the existing `Summarize` and `MaxDescriptionLength = 160` paths, and writes the same set of meta/OG/Twitter/JSON-LD description. Retain existing category/tag generation fallback when there is no description. Search still maintains non-AOT/noindex according to the existing route policy, and article details and static page SEO analysis remain unchanged.
- Category/Tag **update** first normalizes according to the mutation contract and compares the persistent Name/Description. If both sides are unchanged, it will be returned successfully without enqueue/invalidate. `nameChanged` maintains existing rename semantics: article taxonomy projection/outbox, full taxonomy list-frame bump, `CacheTag.ArticleList` and RequiredTaxonomy PublicHot. Only when Description changes, do not insert `ArticleMutationOutboxEvent`, do not bump `CategoryList`/`TagList` frame, do not invalidate `ArticleList`, do not change `TagUrlAlias`; still invalidate the exact metadata cache of the entity, and accurately invalidate `category:{id}` / `tag:{id}` and its `:page:N` variants (including shell HTML, bootstrap, hydration and dependence on `filter.description` through `IPublicAotInvalidationService.InvalidateFilterRouteFamilyAsync` SEO) and may not be extended to unrelated Filter routes or Home/Archive.
- `PublicAotDocumentService` only decodes the entry bootstrap/hydration payload once in the compose cycle, and reuses the same decoding result for subsequent title, description and script injection.
- The internal structure of the page, hydration props and Markdown HTML use Vue public renderer/helper as the only source of truth, prohibiting the coexistence of C# Markdown/props and Vue components.
- `PublicPageRegistry` (C#) is the only source of truth for cross-language page identity metadata; the front end reads and generates results through `src/frontend/src/public-renderers/generated/publicPageManifest.ts`, `publicPageModel.ts` only supplements routeName/activeNav, and it is prohibited to maintain a second set of `pageId/canonicalSlug/seoEligible/aotShellReady/deferSpaBoot` in TS.

- `ISpaAssetManifestService` is responsible for entry script, CSS, preload and frontend asset version; AOT documents must not use regular patches to rewrite the dev/prod asset path.
- The `/assets/fsus-spa-entry.js` generated by the release build must be a stable redirect module that only imports the manifest hashed entry, and cannot copy the content of the hashed entry. Split chunk's circular import of hashed entries thus always returns to the same ESM module identity, avoiding application bootstrap, service-worker registration, and module-private Trusted Types policy from being executed twice; switching the entire set of frontend manifest/AOT documents when rolling back, and aliases must not be changed back to content copies or `allow-duplicates` enabled.

### API reading (article/comment)

```text
Client
  → AEDS Binary（Accept: application/octet-stream）
    → Kestrel → Forwarded/Security/Core/EndpointPipeline
```

Article/comment binary endpoints are only for the application facade: the article endpoint obtains article list/detail/hot/featured and write operations through `IArticleEndpointService`, and the comment endpoint obtains thread/reply/user cursor and delete operations through `ICommentEndpointService`. Pending deduplication covers queued and in-flight work (256 queued plus at most one worker request). The worker still completes the current pending ID before retry admission, limits processing to three attempts, and preserves shutdown cancellation.

Article Vault execution is a server-only adapter over that same article authority. ### Authentication write request (registration/login)

```text
Client
  → Rate Limiter (fixed_ip) → PoW verify
  → Password/Passkey verification
  → JWT Access Token（`Jwt:AccessTokenExpiresMinutes`，Issuing `exp` has the same origin as Cookie `Expires`) + HttpOnly Refresh Token Cookie
  → MFA Challenge (if enabled, Passkey login is MFA-free)
```

The registration/login binary endpoint is layered according to `AuthBinaryRequestReader -> AuthBinaryApplicationFacade -> AuthBinaryResponseWriter`: the reader is only responsible for decoding the AEDS request frame, the application facade is only responsible for registration, credential verification, MFA login branch and final session token result, the endpoint retains the cookie and writes this HTTP side effect, and the writer is only responsible for the AEDS `AuthLoginFlow` / `ApiError` frame.

Front-end authentication broadcast is also layered by transport and composition: `authBroadcastRuntime` only has browser broadcast channels, event verification, deduplication, dispose and subscription tables, and does not read Pinia; `authBroadcastComposition` is installed by `authSessionRuntime.init(pinia)`, and ordinary account login/logout/expired, independent admin changed and notification `SessionRevoked` are explicitly mapped to their respective Store callbacks. The user/admin/notification Store only exposes the narrow publisher/handler injection point and does not import the broadcast implementation. The bootstrap reconstruction first disposes the old composition and then binds the new Pinia, so Public AOT → Full SPA takes over, public renderer and notification runtime no longer own the BroadcastChannel through the Store.

The cache of the authentication store is layered by page epoch: the ordinary account snapshot and independent admin principal returned by the server can be reused in memory according to their respective TTL; `guest`/`missing` negative results only exist in the current page memory and do not enter Pinia persisted state, LocalStorage or Service Worker. New pages always initiate a session handshake from `unknown`, and old `fsus_user_storage` migration remnants are deleted when the Store is constructed. focus, visibility, login/account switching and login/admin-changed authentication broadcast will invalidate the user/admin two types of negative cache at the same time to cover the scenario of another tab login, Passkey completion and admin step-up rewriting the HttpOnly Cookie; the logout/expiry event can create a new `guest` after clearing the old cache, and the request network failure will not generate a new negative conclusion. Authorized reading only consumes the active server principal and does not consume the `missing` state projected by the UI for `unknown`.

The MFA challenge ticket belongs to the short TTL security cache, and only the account container `AccountId` and stable `AccountSubjectHash` are stored internally. The verification failure count uses `ICacheCounterStore.IncrementManyWithExpiryAsync(CachePolicyId.SecurityMfaChallenge, ..., s_failureWindowTtl)` to write the three dimensions of ticket, subject, and IP in a single Redis script, and only sets a 10-minute window when the count key is missing TTL to prevent the failure count and registry from becoming unbounded growth; the account dimension is fixed to `fail:subject:{accountSubjectHash}`, and `fail:user:{userId}` is not allowed; the high-value/security audit scope only writes `AccountId`, `AccountSubjectHash`, and hashed ticket/IP/UA. The runtime fallback path is to delete the corresponding `fail:subject:*` or challenge ticket key under `SecurityMfaChallenge` and let the client re-initiate the short TTL MFA challenge; there is no need to restart the service, and it is not allowed to downgrade by restoring the bare user id key.

Security challenge verify After AEDS frame decode, required field and kind verification, only the cheap byte/char upper limit check of provider payload JSON is allowed first, and then `ISecurityChallengeVerifyRateLimiter.TryAcquireAsync` is executed. Only after the rate limit is passed, the bounded `Utf8JsonReader` is used to parse the provider payload and call provider verify; the malformed/attack payload that is current-limited returns a generalized challenge failure and does not consume JSON dictionary materialization. The fallback path is to delete the short TTL key corresponding to `SecurityChallengeVerifyRateLimit` and allow the client to retry within the new current limiting window without changing the challenge wire contract or provider verify semantics.

The TOTP recovery code's persistent state is only in `user_mfa_profile`: `mfa_recovery_codes_hash` holds newline-delimited `v3$argon2id$m=65536,t=3,p=4$...` entries, and `hash_version` marks the current collection version. Schema migration will supplement `hash_version=1` for the old profile; the runtime only accepts the current v3 or bare SHA-256 legacy migration input before the deadline. The old hash must not be retained as a usable recovery code after it is consumed or the normal TOTP verification is successful. The fallback path is to let the user re-use `/api/binary/auth/mfa/recovery/regenerate` to generate v3 recovery code without restoring PBKDF2 or the old consumption API.

## Cache tiering

Mode selection for cross-node invalidation, Redis transport, publish/apply order, replay identity, retries, no loopbacks, and degraded semantics are only defined by [Distributed cache invalidation](architecture/distributed-cache-invalidation.md). This section only describes the storage and local failure boundaries of each cache layer itself and does not replicate the distributed bus protocol.

| Hierarchy | Type | Purpose | Expiration Strategy |
| ------ | ------ | ------ | ---------- |
| L0 — Hot read snapshot | `PublicHotReadSnapshot` immutable in-process snapshot | Public article/category/tag `.aeds` and public HTML high-frequency hits | Articles, page views, category tags, scheduled publishing and AOT changes are only queued and refreshed; the background projector debounce/coalesce is then rebuilt and published atomically |
| L0 — AOT volume | Static HTML file | Public page first visit shell | Actively clear when content changes |
| L1 — Memory | policy-sharded bounded residency store / owned-frame leases | In-process high-frequency reading objects | Per-policy entry/logical/capacity budgets + LRU + absolute expiration + manual revocation |
| L2 — Redis | typed/raw/string/CAS/counter/one-time/invalidation ports | Persistent hotspots across reboots | TTL + manual revocation |
| CDN (Future) | Edge Caching | Static Resources & Public Pages | Cache-Control + Version Prefix |

> L1 warm-up strategy: backfill L1 immediately after L2 hits to avoid the next L2 round trip.

Redis connections are owned by a single process-level life cycle: `RedisConnectionMultiplexerHolder` exposes a lazy, concurrency-safe asynchronous creation task, and uses `AbortOnConnectFail=false` and `ConnectRetry=5` to preserve the initial connection for retries. `RedisMultiplexerHostedService` starts that task without waiting for network readiness, so a disconnected Redis does not synchronously block host startup; production readiness performs the classified Redis probe and remains non-ready until the shared connection works. Other hosted startup maintenance is best effort and defers on its classified deadline. Runtime services resolve `IRedisOperationExecutor`, never `IConnectionMultiplexer`; the executor joins the one holder task, and `ConnectionMultiplexer.ConnectAsync` can be called at most once in the complete `ServiceProvider` life cycle. `SharedRedisDistributedCache` retains the existing `IBufferDistributedCache` call surface, `FsusBlog_` instance prefix, `absexp` / `sldexp` / `data` hash, byte payload and TTL/sliding refresh protocol, but does not own or replace the connection. Disconnection and reconnection are completed internally by the same multiplexer, and any cache/health path must not call `ConnectionMultiplexer.Connect/ConnectAsync` again. Hosted stop does not dispose in advance so that other hosted services can complete the closing; successfully created objects are only disposed by DI at the end of the complete `ServiceProvider`. A failed creation remains observable through the holder task and readiness rather than triggering a second client or a synchronous DI fallback.

Every Redis operation enters the versioned machine-readable contract in `config/runtime/redis-operation-budgets.json`. The seven fixed classes (`security-atomic`, `coordination-lease`, `content-cache-read`, `content-cache-write`, `optional-projection`, `distributed-delivery`, and `background-maintenance`) independently own connect, command, end-to-end, retry, idempotency, fail-action, concurrency, and circuit budgets; every declared port must map exactly once or startup fails. The class bulkhead is acquired inside the caller deadline and the circuit is checked again after admission, preventing a concurrent miss wave from crossing the failure threshold unchecked. Security and lease operations remain single-attempt/fail-closed; content reads become observable misses that may enter only the existing bounded database gate; content writes retain the authoritative business result while recording degraded cache state; optional projections return a local/base value; delivery and maintenance defer to their durable replay or later maintenance owner. Metrics expose port/class/fail-action tagged command count, queue/server/end-to-end time, timeout, cancellation, circuit state, and fallback action. StackExchange.Redis transport timeouts are only ceilings derived from the largest class budget and are not request semantics.

The runtime cache enters narrow ports according to capabilities: `ICacheTypedReader`, `ICacheRawReader`, `ICacheStringReader`, corresponding writer, `ICacheCompareExchangeStore`, `ICacheCounterStore`, `ICacheOneTimeStore`, `ICacheInvalidationStore`, `ICacheLeaseStore`, `ICacheDiagnostics` and `IOwnedFrameCache`. Production code does not provide a façade that aggregates these capabilities; the consumer constructor only declares the actual calling port. Key/policy is provided to storage by `ICacheKeyResolver` / `ICachePolicyRegistry` in one direction; in-process single-flight and owned-frame mutation gates are independently owned by `CacheSingleFlightCoordinator`; metrics are output through `ICacheTelemetry`; payload serialization is passed to explicit decoder/encoder by the caller, so Redis storage does not reference JSON, POD or AEDS business codec. `TryGetRawAsync` maintains caller-owned defensive copy semantics; read-only public payload uses `TryGetRawReadonlyAsync`, the caller can only write out the immutable buffer to the response synchronously, and cannot expose the backing array as a writable state.

Redis connection ownership continues to strictly follow #1259: all cache ports and `SharedRedisDistributedCache` receive the same classified executor backed by one holder; this layer does not create, copy, reconnect or dispose a second connection. `CacheSingleFlightCoordinator` only has in-process keyed semaphore and does not rely on Redis or `IMemoryCache`; `SharedRedisDistributedCache` only carries the `IDistributedCache` hash/TTL protocol and does not rely on owned frame or coordination in reverse. Rollback without restart does not restore the huge façade: you can use reloadable cache policy to adjust the L1 TTL of a specific policy to zero and maintain Redis L2/invalidation semantics, or switch the corresponding function switch to the existing DB-only path; the same multiplexer and key/TTL contract remain unchanged during rollback.

Ordinary byte/string L1 residency is owned only by `PolicyShardedCacheL1Store`; it does not use `IMemoryCache` placeholders or a second payload-owning index. Each `CachePolicy` declares machine-readable entry, logical-byte and capacity-byte ceilings plus LRU eviction, and the effective per-policy capacity is also capped by a fair share of `min(256 MiB, GC available memory / 20)`, so the sum cannot exceed the process-derived global budget. Oversize values are rejected before eviction. Accepted publication transfers the one materialized byte array to the store; typed decoders borrow the immutable resident array only within a controlled read lease, while raw ports return explicit caller-owned snapshots. Security-critical replace, eviction, invalidation and shutdown retire the entry first and clear the owned backing after its final read lease returns.

Each policy owns its own mutation gate, LRU and Redis-key-to-structured-key index; reads and unrelated policy writes never acquire a global lock. The structure key remains `(runtime/test scope, CachePolicyId, identity kind, identity, version)`. String identities keep the `default/trim/version` Redis-key rules, while integer identities retain independent fields and avoid `int -> string` on L1 hits. Exact invalidation is O(1); Redis scan results probe only a fixed number of policy partitions, and full reconciliation is the explicit all-partition recovery operation rather than the normal distributed event path. Admin diagnostics expose effective budgets, entries, logical/capacity bytes, hit/miss, expiration/capacity/replacement/invalidation eviction, admission rejection and contended lock wait per policy.

Article-detail view counts use a bounded process-local monotonic projection keyed by article ID. A detail-cache hit decodes the persisted payload and returns `max(payload.Views, projection.Views)` without Redis or PostgreSQL access and without rewriting the body payload. A successful five-second view flush applies the returned authoritative count locally and publishes one versioned `article_view_projection` batch through the durable per-node distributed-invalidation ledger; each target applies only the projection and schedules the existing PublicHotRead fragments. Duplicate and out-of-order deliveries cannot lower the count. Entry, logical-byte, and capacity-byte limits are mandatory; eviction or expiry falls back to the persisted payload and never performs a synchronous source read. Redis ranking or derived-delivery failures after the PostgreSQL count update are recorded as degraded and must not requeue the already committed delta. The old per-request `ZSCORE blog:top_articles` overlay, shadow read, and runtime rollback flag do not exist.

The cache activity is only created when `ActivitySource.HasListeners()` and the listener is actually sampled. Ordinary L1 `hit` / `hit_negative` telemetry resolves an enum-indexed state whose metric tags are prebound at startup: `fsus.cache.l1.hit.count` remains an exact cumulative count, while `fsus.cache.l1.hit.duration` reads the clock only for the deterministic duration sample selected by `tests/performance/cache-l1-telemetry-policy.json`. The companion sample-count and weighted-count instruments expose the estimator denominator and calibration explicitly; weighted samples never replace the exact count. Unknown policy or operation enum values fail instead of creating a dynamic series. Miss, reject, decode failure and Redis error paths continue through the full operation metric and duration path. Release evidence records this machine-readable policy under `operations.runtimeTuning.telemetryPolicies.cacheL1Hit`; there is no legacy L1 counter mode, alias or dual recording. Redis read exceptions still set sampled Activity errors, write structured logs, and record `redis_error`; only `content-cache-read` converts the classified failure to an observable miss, while security, lease, and other fail-closed classes propagate it. Performance optimization cannot be used to swallow errors.

Write/change operations of cache writer, counter, one-time and invalidation ports must first remove L1 before submitting Redis L2 changes; `IncrementAsync`, `IncrementClampedWithExpiryAsync`, `ConsumeOnceAsync`, `ConsumeOnceAndGetAsync`, `RemoveAsync` and batch invalidation all follow the L1-first order to avoid concurrent reads from re-raising the stale L1 value before and after L2 has been changed. The one-time challenge that needs to retrieve the payload uses `ConsumeOnceAndGetAsync`, and the value is obtained and deleted by Redis GETDEL semantics in the same L2 operation; the caller must not first `GetStringAsync` and then `RemoveAsync` to splice the one-time semantics. L1-first allows a safe direction stale miss, but must not allow old values ​​to be resurrected within the same process.

The ownership of RiskControl proof maintains the same single transfer in the front and back ends: the browser memory store ensures that the same token has only one holder through reservation; cancellation before sending can be restored; after marking in-flight, it will enter the final state regardless of success, business rejection, timeout or unknown network results. notification preflight uses a single Redis Lua to move the original proof atom into a one-time grant bound to the same action/route/subject/IP/device/policy and with a maximum duration of 30 seconds; the deterministic grant identity allows the recovery of the same unconsumed grant after the HTTP response is lost, and does not allow secondary mints. The grant only holds the proof token hash and envelopeId, and checks the completed envelope after recovery and WebSocket GETDEL; cancel/revoke will therefore cause the unconsumed grant to fail closed immediately. WebSocket does not retain the original proof, reconnect and challenge again. Hot rollback does not require restarting: call the relevant RiskControl action or `globalMode` back to `observe`, and the client will stop obtaining new proofs; the existing short TTL proof/grant will expire naturally, and the legacy notification PoW path remains available.

There is only one physical runtime of PoSpace: `securityPoSpaceChallengeExecutor`: it holds the Worker client, parses the assignment/provider payload, executes the capability/solve, calls the unified challenge verify and writes the proof into the same memory store. `FsusPoSpaceChallenge` and notification headless adapter do not implement the second set of algorithms or timeouts; both use generation/cancel/dispose to isolate refresh, component uninstallation, stream stop and identity switching, and late Worker/verify results can only be discarded. When the notification receives unsupported, it only calls the server-authoritative refresh with a low cardinality reason and bounded reissue count. When the upper limit is reached, it fails closed; the fallback without restarting is to warmly close the PoSpace policy and retain the Sha256PoW and guest legacy PoW paths.

Ordinary binary business requests use server-first handoff: the original command is submitted without proof first, and the structured 428 of `RequiresRiskControlFilter` then carries decision/action/routeKey/policyVersion; the transport only parses low-cardinality headers, and the unified runtime verifies the identity of the original command before issuing the capability selected by the current server. The frontend does not have an action→kind policy shadow, nor does it make decisions from the admin policy or the old process cache. The only proof handoff after that is still `SecurityChallengeProofLease -> BinaryRequestOptions.riskChallengeProof -> binaryApiClient`; transport completes proof field verification, wire kind mapping, three request header writing and settlement, and API wrapper only passes lease. Recovery Key and Passkey are shared with public comments `useRiskChallengeCommand`: Only idempotent commands or the same payload closure with fixed mutation identity can be executed once after the challenge is completed; no replay when the server has responded or the network result is unknown. When the strategy is switched midway, the latest 428 will prevail, and the old assignment will be reissued or fail closed. The fallback without restarting is to switch the action/global mode to `observe` or roll back LKG. Client pre-determination cannot be restored.

Ordinary account session verification intentionally bypasses L1's secure dedicated path: `UserSessionValidationCache` directly reads the `SecurityUserSessionValidation` v3 snapshot of Redis L2, which includes session/account `xmin`, account status and `normal|restricted|revoked` mode. Hit is directly ruled; miss, Redis exception or payload damage enters the bounded concurrency/continuous failure circuit breaker of `IUserSessionDbFallbackGate`, and then presses the `sessionid` primary key to return to the source PostgreSQL. DB failure or budget rejection will fail closed. ## AEDS Binary Chain

The FsusBlog runtime API only maintains the AEDS binary chain:

| link | content type | decoding position | purpose |
| ------ | ---------- | ---------- | ------ |
| Binary chain | `application/octet-stream` (AEDS v2 frame) | TypeScript adapter / browser Wasm Worker | Production main chain, public reading and management side write operations |

**Failure logic**: When Wasm Worker decoding fails, the client can switch to the TypeScript binary decoder or display a protocol error; the text API request must not be resent.

**v2 write out and cache paths**:

New frames use `BinaryResults.Frame` to return `BinaryFrameResult` and are constructed with `AedsFrameBufferWriter`; complete cached frames use `BinaryResults.PreencodedFrame` to return `BinaryPreencodedFrameResult`. Typed POD writers such as `PodBinaryCodec.WriteArticlePage` own the payload boundary; do not replace these paths with generic JSON or stream reassembly.

- `src/shared/Contracts/Validation/aeds-protocol.json` is the only machine-readable source of v2 headers and active frame types; generators simultaneously produce Core/Shared C#, TypeScript and C++ `aeds_frame.hpp`. Core, Server, and tests uniformly reference the Shared packed header, and Core handwritten copies are no longer maintained. `check:aeds-protocol` fail closed checks all generated files. The cross-stack frame-schema check also compiles the real C++ decoder, iterates over all active frame types, and verifies the C++ decoding with a C# golden frame, so cross-language name, value, or 16-byte layout drift is blocked in CI.
- The frame header is fixed at 16 bytes. The dynamic response reserves the header through `AedsFrameBufferWriter` and writes the payload in the same pooled buffer. The header/CRC is backfilled after `Seal()` to avoid constructing the payload first and then copying it to the complete frame.
- `BinaryFrameResult`, `BinaryFramePayloadResult` and `BinaryPreencodedFrameResult` are submitted only once per response. `PipeWriter`: `WriteAsync` itself must not be unconditionally flushed when `FlushAsync` is completed; the payload path of direct `GetSpan/Advance` is only explicitly flushed once. request cancellation, aborted response and pipe backpressure are propagated unchanged.
- `AedsFrameBufferWriter` clears unknown, auth/session/MFA/Passkey, anonymous credentials, admin/private and `ApiError` frames by default and returns them to `ArrayPool`; only public immutable response frames explicitly listed by `AedsFrameSensitivity` can skip the final buffer clear. The expansion occurred before `Seal`, and the old buffer was always cleared as sensitive data.
- `/api/binary/**` directly enters the endpoint to write out the link after completing Accept and binary request content-type verification, and is no longer captured in the temporary buffer by the API binary response middleware.
- Non-binary `/api/**` requests only enter the capture/conversion path if the client explicitly accepts a binary envelope; plain JSON success responses are no longer buffered indiscriminately. Human reading proof runtime path has been migrated to `/api/binary/read-proof/*.aeds`.
- Non-upload binary requests use pooled frame buffer to read, and the default maximum frame size is 8 MiB; the decoded payload is passed to the endpoint in a buffer slice, and the buffer life cycle is hung to response completion, and there is no additional `ToArray()` for the payload.
- Continue to use raw stream to upload fragments. The endpoint uses request body backed `IFormFile` to hand it over to the file service. The entire fragment is no longer read into `MemoryStream` and then cloned into an array.
- Upload session cleanup is executed by `UploadSessionCleanupWorker` background, session init/status/part-map only sends merge signals; by default, repeated requests within the 45s signal window are recorded as dropped/coalesced, and no cleanup storm is triggered. `FileService` writes the expired index of `.upload-sessions/expires/yyyyMMddHH/{uploadId}` synchronously when saving the session manifest. The cleanup main path only scans candidate sessions in the expired bucket; complete/abort/expired deletion must clean up the index synchronously. The legacy manifestless/session root sweep is only used as a low-frequency backup and is not used as a regular cleanup path. The stale scan of the upload session lock is also hung at the end of the background cleanup. `AcquireSessionLockAsync` only executes the reference of a single uploadId and waits for the semaphore, and no longer scans the entire `s_sessionLocks` table for each shard request. Runtime metrics record `fsus.upload.cleanup.scanned_sessions`, `deleted_sessions`, `elapsed_ms`, signal accepted/dropped/coalesced, and `fsus.upload.session_lock.current_count`, `stale_scanned_count`, `stale_disposed_count`, `cleanup_elapsed_ms`, `acquire_elapsed_ms`.
- PostgreSQL/ORM entity/command service is a write model; Public AOT HTML, article detail `.aeds`, search index, list/category/tag/hot snapshot are artifact-backed read models; L1/L2/OutputCache is just an acceleration layer and cannot be used as a replacement for the CQRS read model.

After Publish Proof is written, local append-only [Transparency Log](integrity/transparency-log.md) is appended. `integrity_transparency_log.seq`, `prev_entry_hash` and `entry_hash` form a hash chain and are associated through the proof/log bidirectional field. This log only enhances local auditability and does not replace `audit_log`, security risk events, nor does it represent on-chain or external consensus proof. Merkle checkpoint uses `integrity_merkle_checkpoint` to generate daily/release root, manifest and site signatures for the transparency log range. For rules, see [Merkle Checkpoint](integrity/merkle-checkpoint.md); checkpoint only proves that a certain publish proof is included in the local log snapshot and does not replace release artifact signing or SBOM hardening.

The public article page does not have and must not add a separate public rights endpoint; the browser must no longer request `/article/{id}/rights.aeds`, `/rights` or other side channels to complete the copyright information.

- Browse counts are no longer generated by the read link, but updated by independent human read proof events.
- VisitLog flush only writes the `IHotStatsInvalidationCoalescer` dirty mark and does not directly broad invalidate AdminStats/HotArticles. coalescer uses 2s debounce for HotArticles and 10s debounce for Stats, and flush pending state at threshold or shutdown. Hot and featured binary misses use one generation-scoped whole-frame owner from seed read through the single visible-metadata projection, ordering, AEDS build, and atomic L2/L1 publication. A bounded active-key task flight shares only the build receipt among same-process callers before the existing distributed lease; each response reacquires its own frame read lease, so no caller-owned lease is shared and the generic 64-waiter/750ms miss-path contract remains unchanged. A Redis seed miss falls back to one complete ranked projection rather than publishing a separate seed. These frame policies do not use prefix registries; startup retires their historical registry sets, and old generations expire by TTL instead of broad `RemoveByPrefixAsync(..., string.Empty)` scans.
- `ICacheInvalidationStore` provides `RemoveManyAsync` and `RemoveByPrefixManyAsync`. If the write path fails, `CacheKeyIdentity` / `CachePrefixIdentity` batch requests should be delivered first. The cache layer merges L1 remove, Redis `KeyDeleteAsync(RedisKey[])`, and registry `SetRemoveAsync(RedisValue[])`, and only scans the registry once when the same policy has multiple prefixes; if the registry is missing, the fallback uses the common prefix of the same policy prefixes to perform a keyspace scan and then filter again.
- The compact payload uses shared UTF-8 blob + fixed value record as the lexiconization point of the currently compatible payload, reducing duplicate text packages for lists, categories, tags, conversation and stats.
- Notification stream payload writes a typed writer that gives priority to known contracts; only new and unregistered payloads are allowed to enter the reflection bag.
- The management side stats externally converge to the `AdminStatsQueryDto`/`AdminStats` aggregated query model. `/api/binary/stats` carries overview, recent comments and regions in the same frame. The dashboard first screen derives view blocks from a single request; the recent/region narrow endpoint is only used as a compatible entry.

- The front-end tool-type responsive state preferentially uses the event source itself: dashboard chart resize is driven by the chart container `ResizeObserver`, layout breakpoints are driven by `matchMedia`, and human-read-proof only schedules one-time submission checks according to the remaining dwell time to avoid global resize storms and fixed-interval dwell polling.
- JSON and Binary failure semantics share the same `ApiErrorSemanticMapper`, and only differentiate between JSON envelope and `ApiError` frame at the transport layer. The error code, HTTP status and default message must be consistent.

## Notification Stream Handshake and Observability

```text

  → GET /api/notifications/stream/preflight（Same as RiskControl/legacy PoW/cursor/protocol parameters)
  → 204 No Content：Then send WebSocket upgrade to /api/notifications/stream
  → Non-204: Read AEDS ApiError frame and X-Fsus-Notification-Stream-* header, mapped to front-end failure code
```

- WebSocket main channel is still fixed at `GET /api/notifications/stream` + `fsus-aeds.v2`.
- This channel is not standard Server-Sent Events, does not use `EventSource` or `text/event-stream`, each message is a full AEDS v2 binary frame.
- Preflight shares `NotificationStreamHandshakeService` with the formal WebSocket handshake. It first verifies the Origin allowlist, and then verifies authentication, RiskControl / legacy PoW, cursor and protocol semantics. Preflight does not require WebSocket upgrade and only verifies the existence and kind of the one-time RiskControl proof. The formal WebSocket handshake only consumes the proof. Origin/host allowlist is built by `NotificationStreamOriginSnapshotProvider` from `Seo:BaseUrl`, `CORS_ALLOWED_HOSTS`, `Fido2:Origins` and `AllowedHosts` and is refreshed through configuration reload token; the handshake hot path is a read-only snapshot and does not repeat the split/parse configuration.
- If the handshake fails, `X-Fsus-Notification-Stream-Error-Code` and `X-Fsus-Notification-Stream-Status-Code` are written uniformly, and the AEDS `ApiError` frame is returned.
- Both Preflight and formal WebSocket endpoints use the `notification_stream` fixed window policy; formal connections obtain global/IP/account atomic leases within `NotificationStreamConnectionManager.RegisterConnection` and before `AcceptWebSocketAsync` and per-connection channel allocation. The quota is controlled by `NotificationStream:MaxConnectionsGlobal`, `NotificationStream:MaxConnectionsPerIp`, and `NotificationStream:MaxConnectionsPerAccount`. When the limit is exceeded, `429 notification_connection_limit` is returned, and the lease is released in case of `RemoveConnection`, accept failure, backlog/heartbeat/pump exception, and request cancellation path.
- Notification handshake only orchestrates protocol, RiskControl / legacy PoW and handshake results. Account ban/logout access sinks to `NotificationStreamAdmissionService`, notification stream audience group sinks to `NotificationStreamAudienceResolver`, and the mapping of message domain to user/group route sinks to `MessageNotificationStreamPort`. Stream reconnect that has logged in to a normal account uses `NotificationStreamAccountAdmissionCache` to cache the short TTL account state to avoid reading `sys_user` every time it is reconnected; the ban state is still verified by `IBlacklistService.GetBanStateAsync` and reused in its subject-hash cache for each admission, so the ban convergence semantics do not fall back. Handshake records origin validation elapsed, origin cache elapsed/hit ratio, account state hit/miss, admission DB read count and rejected reason count indicators.
- `MessageCenterService` is the only application service for message center reading and writing and notification delivery projection. The account/admin inbox list must allow count and page queries to be executed concurrently. The last message preview uses a single `DISTINCT ON (conversationid)` SQL to return to the source; creation, account/admin reply, system message, explicit read and status change are all written simultaneously within their respective PostgreSQL transactions. Messages/activity, unread/read cursor and per-target `message_mutation_outbox` event. The request thread no longer directly publishes these real-time events; `MessageMutationOutboxWorker` exits after submission, publishes failure, and repeats consumption with stable delivery key, `FOR UPDATE SKIP LOCKED` claim, short lease, exponential backoff, and poison status recovery. It obtains single-process execution rights through `IBackgroundWorkerLease` in each round. Expired processing claims can be reclaimed, but unexpired claims are not preempted. Dynamically shut down `MessageMutationOutbox:Enabled` only suspends consumption and retains pending events, and continues replaying after re-enabling without falling back to best-effort direct push; backlog, failure, poison and stuck claim are observed by `fsus.message_outbox.*` low-base indicators. The account participant's read cursor/unread is stored in `msg_participant_state`, and the administrator shared queue is independently stored in `msg_admin_queue_state` for each conversation row; only account messages are added to admin unread in the same transaction, and admin/system messages are not added. admin latest details are monotonically advanced to the shared cursor by responding to the snapshot, lists, details, and unread filters are all read-only in this projection; old sessions are backfilled conservatively via migration and can be inspected/idempotently rebuilt by `IMessageAdminQueueMaintenance`. When `Messages:AdminQueueProjectionEnabled` is dynamically closed, the admin read fails closed, and participant aggregation is not rolled back; when `Messages:ReplyWritesEnabled` is dynamically closed, the account/admin reply fails closed at the same time, and reading and explicit status changes continue to be available. The relevant thermal paths are observed with `fsus.message.center.list.elapsed`, `fsus.message.center.reply.elapsed`, `fsus.message.center.fanout.refresh.elapsed` and `fsus.message.center.fanout.build_item.elapsed`.
- Message real-time projection only publishes conversation/message reference and unread count: append's body is empty, upsert's last-message preview is null, the account side restores the authoritative text along the existing delta paging, and the admin side refreshes the list/details. `MessageRetentionCleanupService` is called periodically by the existing cleanup leader, and uses UTC cutoff idempotent to clear expired open/closed/system content and logout account content, retaining the row ID, admin principal and irreversible audit reference; the log only records five types of change counts. `Messages:RetentionCleanupEnabled=false` can hot-suspend cleaning without adjusting middleware or restarting; no application-level recovery is provided for cleared data.
- Admin state changes use explicit transition matrix and `xmin` CAS; valid transitions update conversation, append immutable `msg_conversation_status_event`, and write to account/admin outbox respectively in the same transaction. The outbox saves the precise target state when the event occurs. The worker publishes `InboxConversationStatusChanged(15)` uniformly without reading back the latest conversation state; requests with the same state return `no_change` and do not write audit/outbox. `fsus.message.center.status.count` only uses limited pre-state, post-state, and outcome tags to observe transformation results. `Messages:StatusMutationsEnabled=false` can write to the hot pause state and resume directly after repair. There is no rollback, no auditing, no CAS or request-thread fanout.
- System message source-event replay is parsed before the target state is read to preserve the original result; new writes are followed by `FOR UPDATE` lock `sys_user` in the same message transaction. Ordinary message policy only allows active, ban/restoration management policy allows restricted, missing/deleted/unknown status all return stable field errors; foreign keys are only used for final coverage. `Messages:SystemMessageTargetValidationEnabled=false` retains existing replay and fail closed new writes after hot shutdown, and does not roll back out-of-transaction checks.
- The authoritative chain of unread is fixed to `msg_message + monotonic read cursor -> participant/admin count projection -> Redis account total cache`. The database trigger rejects negative count, cursor back, cross-session or internal cursor; the recalculation service can be repaired by single conversation, single account, single admin conversation or full admin queue. The difference log does not contain the message body. Cache miss/corruption/CAS failure returns to database count, Redis will never reversely overwrite the database. `Messages:UnreadRepairEnabled=false` hot-suspend maintenance writes only.
- Message creation, account/admin reply saves `principal kind + principal id + ClientMutationId + request hash` in the same transaction; system messages save stable `SourceEventId` as unique `sourceMessageId`. Use principal-level PostgreSQL advisory transaction lock before writing, and check idempotent identity across conversation/message: same key and same digest returns original ID and `idempotencyReplay=true`, same key and different digest returns `409`, cannot increase unread/activity/outbox repeatedly. Response multiplexing POD reserved byte without changing AEDS frame type or fixed size. After `Messages:MutationIdempotencyEnabled=false` hot reload, four types of write fail closed, and read, mark-read, status and notification stream continue to be available; re-enable after repair, and fallback to unidentified writing is not allowed.
- The admin account context is an independent read projection: `MessageCenterService` generates the same `account id + coarse status` for list, detail, and notification upsert, and transports it through admin-only frames 206/207; account frames, public handles, and admin principal/session do not participate in this projection. The server generates sender display for the viewer; the frontend cannot infer identity from a single name. `Messages:AdminAccountProjectionEnabled` supports hot-disabling admin reads and upserts while keeping the account protocol and message writes available.
- Notification stream backlog is written to Redis stream by route (`u:{id}` / `g:{group}`; multi-user target expands into multiple user routes), and multi-target backlog writing is submitted through Redis batch/pipeline at one time. The publisher no longer holds the process-level global gate; it only obtains the Redis ownership lock based on the actual storage route after sorting. Therefore, publishers with overlapping routes still append monotonically based on event id, and unrelated targets no longer queue each other unconditionally. The multi-user publisher obtains all route locks in the same order to avoid cross-writing or locking rings with single-user publishers. replay only reads the user/group streams visible to the current connection and then merges and deduplicates them based on event id.
- `NotificationStreamDeliveryPolicyCatalog` is the machine-readable authoritative directory for active events; unknown enum fails closed before encoding or enqueuing. The local fanout is divided into three independent shallow lanes: lossless, replaceable/coalescible state, and low, which are respectively subject to frame/byte/max-useful-age constraints; the state/low lane only retains the latest frame according to `event type + route + semantic key`, and the worker uses the rotation starting point for scheduling. Low-priority congestion does not occupy the lossless capacity, and any lane will not be permanently hungry.
- Each connection queue simultaneously constrains frame count, queued bytes and oldest age, and records send latency, coalesced/drop/resync count and the last event cursor. Silent drops are allowed only when the policy explicitly declares `diagnostic-drop`; other lane overflows, native fanout overflows, or frame expiration will close the connection of the affected target. `ReplayFromCursor` policy sends `4010 fsus_replay_required:<bounded-reason>` and retains the cursor; `FullResync` policy sends `4011 fsus_full_resync_required:<bounded-reason>` and clears the cursor. Redis retention gap continues to use `4009 fsus_replay_miss`.
- The connection is registered to the local fanout before the backlog replay; the live frame arriving during the replay is saved in the bounded queue of the connection. After the replay is completed, it is taken over by the same pump, so there is no silent window between replay/live. If the queue budget for this window is exhausted, the connection receives the replay-required instruction above instead of continuing to consume the gapped live state.
- The configuration budget is `NotificationStream:Fanout:{Lossless|State|Low}FrameCapacity`, corresponding to `ByteBudget`, `NotificationStream:QueueByteCapacity` and `NotificationStream:QueueMaximumAgeMs`. Observations include publish critical-section wait/route-lock count, lane depth/bytes/oldest age, coalesce/drop/expired, connection resync, send latency and existing fanout/replay metrics; labels only use lane, target kind and fixed reason.
- The downgrade path that does not require restarting is not to change the Redis backlog and AEDS frame. First, the gateway stops establishing a new stream to the candidate slot, switches the traffic back to the previous active slot, and uses the existing 1012 deployment restart protocol to allow the connection of the candidate slot to carry the cursor and reconnect. MUST NOT downgrade by restoring the global gate, growing to an infinite queue, or allowing lossless silent drops.
- Resilience drill drives the same `INotificationStreamPublisher` link through the Development/Test-only `/_fsus/testing/notification-stream/publish` entry; `drillSlowConsumer=1` only enables the send delay in the Development/Test WebSocket query. `drillQueueCapacity` can reduce the per-connection queue of the test connection to 32 to stably trigger the backpressure shutdown without changing the production pump behavior.
- The connection pump uses one `PeriodicTimer` heartbeat loop for each connection; the business frame and heartbeat write WebSocket serially by sending locks to avoid creating linked timeout CTS in each round of idle wait.
- The search index version fields of `CacheControl` and `SearchIndexUpdated` use `version / manifestUrl / generatedAt` as the only consumption semantics, and Service Worker no longer derives versions from multiple fields.

## Single-author publishing and open distribution

Article entities now explicitly log `Status`, `ScheduledPublishAt`, `PublishedAt`, `ArchivedAt`, `DeletedAt`. Public reading links, feeds, sitemaps, related-reading, search runtime fallback, search index rebuild, and category/tag counts must only read `Status=Published` articles whose release time has expired; `IsDeleted` continues to retain the original recycle bin semantics. The Core state strategy shares a strict matrix with `ArticlePublicationTransitionWriter` within the transaction: ordinary writes can only transition between four editable states, `Deleted` can only be entered by the delete process and transferred back to `Published` by restore, rollback can only go to `Published`, and scheduled workers only accept `Scheduled/Published → Published`. Unknown enumerations, missing/invalid plan times and illegal edges all fail closed to validation with stable details code and are no longer normalized to `Published`.

`ScheduledPublishWorker` scans expired `Scheduled` articles according to `scheduled_publish_at, id` every minute, converts the article to `Published` and writes the `scheduled-published` event of `article_mutation_outbox` in the same transaction; after the transaction is successful, it still tries to synchronize search index, PublicAOT, HTTP/cache failure and `PublicHotArtifactUpdateQueue` enqueue. If the transaction fails, the article remains and can be retried by subsequent scans; if the transaction is submitted but any derived side effects fail, the worker record is degraded, and the outbox dispatcher will press retry/backoff to replay cache/search/AEDS/PublicHot/notification stream derived updates. `article_mutation_outbox` still saves the event-level pending/processing/processed/poison and retry/backoff, and `article_mutation_outbox_edge` records the status, attempt count, last error and updated_at of public-aot, http-cache, search-projection, article-detail-aeds, public-hot-read, notification, integrity-proof and other edges; the dispatcher will skip the completed edge when re-running, and only mark the event as processed after all required edges are completed. `integrity-proof` is a non-required edge of publish proof, and is only scheduled after the required edges such as search, taxonomy, AEDS, and PublicHot are completed; proof generation failure only records the edge failed/pending/retrying status, and does not block publishing transactions, cache invalidation, search projections, AEDS, PublicHot, or notification streams. PublicHotRead enqueuing returns `Accepted`, `PersistedDirty`, `Coalesced`, `Cancelled`, `Closed` or `Failed` typed receipt; the first three all indicate that the monotonic generation has been persisted, and when the queue is full, `PersistedDirty` is returned and restored from the durable marker by the worker, without triggering the outbox retry. required public-hot-read edge only enters retry when persistence fails, is canceled, or the channel is closed. The failure result is written to the events retry count, next retry, and last error, and the failed edge is recorded synchronously. The worker writes `lastPublishedCount`, `lastFailedCount`, `dueBacklog` and the latest error to `ScheduledPublishRuntimeState` in each round. The runtime block of `/api/ops/health/ready-detail` will expose the snapshot. Creation, update, deletion, recovery, and permanent deletion must also be written to `article_mutation_outbox` within the same article transaction. Derived updates are still attempted synchronously within the request; if the process crashes after submission, `ArticleMutationOutboxDispatcher` will press retry/backoff to replay the derived updates and mark processed after success.

All new article mutation producers write `schemaVersion=2` and solidify revision, publication/release, rights snapshot, responsibility snapshot/version, event time, and before/after scope of taxonomy/tag/visibility within the same PostgreSQL transaction of the primary write. The dispatcher uses these coordinates to do version preflight before any edge; when the old release/revision has been replaced by the current pointer, the required/optional edge that has not yet been executed is recorded as `skipped`, `last_error` saves `superseded-by-release:*` or `superseded-by-revision:*`, and the new projection must not be overwritten after reading latest. Only the current version will enter search, AEDS, PublicAOT, PublicHotRead and notification; AEDS/HotRead will also pass the expected release to the source query, and the current artifact will be retained when the coordinates are no longer resolved. See [Versioned article mutation outbox](architecture/article-mutation-outbox-versioning.md) for details.

Responsibility disclosure updates are also authority transactions: the append-only snapshot, the current publication's explicit responsibility pointer, and the `responsibility-updated` outbox must be submitted together. The dispatcher first verifies the precise coordinates of article/revision/responsibility/publication in the event, and then updates Public AOT, AEDS, HTTP cache, search/PublicHot and notification; it is not allowed to query the latest guess responsibility version. Downgrade without restarting can suspend the derived claim of `ArticleMutationOutbox:Enabled=false`, and the authority writing will continue to retain pending events. After repair, re-enable it for idempotent replay. This migration only promises PostgreSQL single-process acceptance, schema switching with new code atomically; old writers cannot write in parallel after removing a single revision unique index, and rollback must not delete appended snapshots or publication pointers.

Comment writing, deletion, model/human review status transitions, and region visibility logging use independent `comment_mutation_outbox`. The authoritative row is submitted in the same PostgreSQL transaction as `CommentCreated`, `CommentModerationChanged`, `CommentDeleted`, `CommentEdited`, `CommentReplyNotificationRequested`, `CommentVisibilityChanged`; the payload is constrained by the database to `{}`, and the body, anonymous certificate, and nullifier are not copied to the event. `CommentMutationOutboxWorker` recovers process interruptions through short lease claims, divides consumer checkpoints according to model moderation, cache version, notification stream, site notification, and audit projection, and repeats delivery to skip completed consumers; the real-time stream uses event id to derive a stable idempotency key, and the intra-site message multiplexing uses message source-event to remove duplication. Out-of-order events reread the current comment status before sending, so old approvals cannot re-expose deleted or hidden comments. For detailed state machine and no-restart fallback, see [Comment mutation outbox](architecture/comment-mutation-outbox.md).

Category/tag public count projections are serialized at article granularity: `TaxonomyCountProjectionService` obtains the `(hashtext('taxonomy_projection'), articleId)` transaction advisory lock within a PostgreSQL transaction, then reads the old projection, calculates the count difference, and upserts the new projection. In-request side effects and outbox replay for the same article therefore cannot be accumulated repeatedly based on empty old projections at the same time; different articles can still be parallelized. If a transaction fails, the count and projection will be completely rolled back, and subsequent outbox retry can be safely replayed.

Article deletion, recovery and permanent deletion all use PostgreSQL `xmin` as row-version guard. Soft deletion only matches the currently undeleted row-version; recovery only matches the currently deleted row-version and is restored to Draft; for permanent deletion, press `isdeleted=true + xmin` to execute `FOR UPDATE` first within the same transaction, and then clean up comment/tag/body/article after the lock is successful to avoid stale restore/delete interleaving to delete subtables or issue duplicate outboxes.

Binary article list cache uses `core:v5:{public|admin}:...` identity isolation. The public identity contains `cursor:first` or the authenticated opaque cursor together with version, size and normalized filters; the admin identity retains its separate page/status contract. Anonymous reads only admit published, visible, non-deleted rows and use `(createtime DESC, id DESC)` keyset ordering. The first public request is exactly page 1 without a cursor; every deeper page requires the previous response cursor, and invalid input fails before PostgreSQL/Redis access. There is no public OFFSET, cursor recovery replay, legacy page identity or dual parser. The page projection and one batch tag projection use at most two commands on a count hit and three on a count miss. `ArticleListCount` is keyed by `ArticleListVersion + filter` and rebuilt through the same miss singleflight, so deep-page command count remains constant. PublicHotRead and Public AOT publish only page-one list artifacts carrying `nextCursor/hasMore`; requests with a cursor fall through to the dynamic endpoint, and stale `:page:N` AOT requests cannot read, schedule or write artifacts.

The open distribution layer is provided by `BlogDistributionService` and `DistributionEndpoints`:

- `/feed/rss.xml`, `/feed/atom.xml`, `/feed/feed.json` and History `/api/Article/rss`
- `/sitemap.xml`、`/robots.txt`
- `/api/binary/article/{articleId}/related.aeds` (main runtime AEDS)

`BlogDistributionService` no longer uses one snapshot to drive both feed and sitemap. The feed uses an independent minimum projection of the latest 50 articles; the sitemap uses the full identity/time projection without a feed upper limit, and aggregates category, tag and static page update times respectively. The text table only selects `updated_at` and does not read Markdown; the article text update time also drives sitemap `lastmod`, Feed modified time and AOT `dateModified`. URLs without trusted update time do not output `lastmod`, and the air station cannot use the current time to produce updates. The urlset is fragmented at 45,000 entries, the root document becomes the sitemap index when exceeded, and the diagnostics parse the root/child XML and RSS XML directly.

Sitemap artifacts use the process-local mirror of the durable PublicAOT invalidation generation as their sole L1 identity. A process-wide `SitemapArtifactCache` reads that immutable generation before its dictionary lookup, so a hit performs no SEO/version/static-page lookup, Redis command, database command, file read, or XML rebuild. A miss executes one four-command bounded projection for static pages, articles, categories, and tags behind whole-artifact singleflight; root and child documents are published as one generation snapshot only after a post-build generation check. Article, taxonomy, system-page, SEO/compliance, and public-origin changes advance the same durable generation through the existing distributed invalidation and replay path. Sitemap OutputCache entries carry `ArticleList`, `Seo`, and `SystemPage` tags so endpoint invalidation follows the same mutations instead of relying on the one-minute TTL.

`PublicOriginPolicy` is the common origin gate of AOT document, feed, sitemap, and robots: configure `Seo:BaseUrl` as the authoritative value, and the persistent SEO/artifact can only be the same or still the project placeholder value. `LifecycleHostedBootstrapService` reads and verifies persistent SEO after schema/account invariant and before AOT/search initialization; production conflicts immediately terminate the startup to avoid any apparent output of the second set of canonical origin.

`RelatedReadingService` is the only dynamic query entry for related articles, previous article, and next article. One PostgreSQL CTE/window command resolves every public title, summary, category and tag set through `article.current_publication_id -> article_publication.article_revision_id`, then returns the visible source, bounded candidates and both adjacent rows; mutable authoring fields cannot leak into this projection. Candidate scoring keeps the category/tag/keyword/publication-time weights and deterministic score, distance, publication-time and ID tie-break. The cache contains only the final immutable `ArticleRelatedReading` AEDS frame, keyed by article ID, publication generation, ranking algorithm version and AEDS frame/schema versions. The whole miss is keyed-singleflight: up to 1,024 distinct active keys are bounded in process, same-key callers share one build receipt, and each caller reacquires an independent frame lease after completion; a missing source uses the policy negative marker while an existing source with no recommendations still produces a valid frame. L1 hits write the leased frame directly and do not decode an object graph, access Redis or query PostgreSQL. Owned-frame admission and LRU eviction enforce the same policy entry, logical-byte and backing-capacity budgets under high-cardinality article traffic. Article mutation advances the publication generation and removes the affected prefix; taxonomy mutation advances the same generation and removes all registered related-reading identities. This dynamic route remains outside PublicHotRead L0 and PublicAOT snapshots.

These endpoints use the ArticleList/Seo tag of the output cache, and the response headers use `Cache-Control: public, max-age=60, stale-while-revalidate=300` and `Vary: Accept-Encoding, CF-IPCountry, X-Fsus-Region`. Conditional caching and 304 semantics are only responsible for the OutputCache/upstream cache layer. `DistributionEndpoints` does not hand-write ETag according to the text or parse `If-None-Match`. Public comments, public taxonomy and related-reading AEDS endpoints are additionally linked to `public_read` current limiting and `RiskAwarePublicReadFilter`; public HTML and PublicHotRead hot binary artifact candidates also enter `public_read` current limiting, and `PublicHotReadSecurityGateMiddleware` executes the same set of public read risk rulings before the artifact is written out: ordinary users read directly, verified crawler uses independent high quota, social preview bot cannot access API, high-risk IP requires first PoW, persistent high risk returns 429. `VerifiedCrawler` is only set by CIDR/rDNS verified search crawlers; AntiCrawler `observe` mode counterfeit crawlers are allowed to be observed, but are not allowed to enter the verified-crawler partition. PublicHotRead risk admission reads only `PublicHotReadRiskProjection` synchronously; it never calls `ISecurityRiskScoreReader`, Redis, PostgreSQL, filesystem, or HTTP and never shadow-reads or falls back to the old score path. `ISecurityRiskSignalSink` / `ISecurityRiskScoreReader` remain the strong Redis-backed path for non-public operations, while `SecurityRiskEventSink` maintains that path, queues the pseudonymized event to PostgreSQL `security_risk_event`, and updates the local projection for Pub/Sub delivery and durable replay. When Redis miss occurs, `RiskScoreEngine` linearly decays and aggregates PostgreSQL events according to the remaining TTL and backfills the hot cache for those non-public strong reads. When persistence fails, only the structured fallback log is written, and the public read, auth, comment or notification stream judgment is not allowed to become 500; when the background `/api/binary/admin/security/**` changes the AntiCrawler/PoW policy, the native security binary endpoint directly executes admin authorization, MFA, fixed_ip current limiting and audit boundaries and updates the singleton snapshot. The external `/api/admin/security/**` JSON has been removed, the policy hot path only reads the memory snapshot, and the DB is not synchronously queried. The PublicAOT backfill request will record the expired version when queued; if the same route or page is mutated and invalidated by an article after being queued before writing to disk, this backfill will be discarded to prevent the old category/tag documents queued during draft/scheduled/archived from overwriting the new status after the published expiration. When test isolation is turned on, the PublicAOT cache key and backfill query must carry the same `X-Fsus-Test-Session`. The background generation reads the corresponding test schema through temporary `HttpContext` to avoid writing test articles into the global AOT cache. `check:distribution-version-coherence` will warm up the public cache and verify that draft/scheduled/archived is hidden, published is visible, and update/delete/restore/permanent-delete is consistent on public binary list/detail, admin status list/recycle bin, feed, sitemap, AOT article/category/tag pages and search index alias.

## Author workbench and private content boundaries

The text of the article revision is uniformly saved by the immutable `article_revision_content_block`. `article_revision.content_block_id` and the complete metadata of the revision form a historical package that can be directly reconstructed. Similarly, Markdown only retains one SHA-256 content block; metadata-only, copyright-only and rollback reuse blocks, and blocks are allocated only when the text changes. Exact unchanged update returns the current coordinates, does not create a revision/publication/outbox, and therefore does not enter cache, AOT, search, integrity or notification stream side effects. The migration first deduplicates backfill and checks reachability before clearing old inline content; the cleanup task only deletes blocks that exceed the safe cutoff and are still unreferenced at execution time. In case of an exception, the gateway hot switch suspends admin article write/rollback and stops orphan block cleaning; anonymous, login, admin read, notification stream and binary read remain online, and writing is resumed after verifying that missing/orphan is zero. No restart is required, and inline/diff-chain writing is not allowed to be restored.

The author workbench table contains `article_draft`, `article_revision`, `content_asset`, `content_asset_reference`, `content_asset_cleanup_queue`, `site_subscription`, the comment moderation field is saved in `comment`, the regional compliance results are saved in `comment_region_compliance`, and the publicly read regional mask lookup is saved in `comment_blocked_region`. The production front-end calls the author's workbench through the native `/api/binary/author/**` AEDS endpoint; authorization, admin step-up, fixed_ip current limiting, auditing, cache invalidation and business semantics are all executed directly in this binary endpoint. The external `/api/author/**` JSON entry and internal bridge compatibility layer have been removed. `article_draft` uses `owner_admin_principal_id + draft_key` to isolate and persist the text, abstract, cover, category, tag, `status`, `scheduled_publish_at`, `client_revision` and `server_revision`; new creation is create-only, and existing drafts are updated with `expected_server_revision` conditions and atomically incremented in the same SQL mutation. If the version does not match, the asset reference will not be updated. Requests with the same client revision and normalized content are considered idempotent retries after the response is lost and will not be incremented again; other stale/out-of-order saves return `draft_conflict`. DELETE also requires version preconditions to prevent old tabs from deleting updated drafts. The editor writes the latest unconfirmed text into the bounded IndexedDB journal before the server-side draft debounces; the record is isolated from the tab owner by irreversible admin identity hash, create/edit article key, and retains the `baseRevisionId`, `serverRevision`, `clientRevision` and text SHA-256 at the time of writing. Normal input, hidden visibility, pagehide, beforeunload and bounded period retry only request the same asynchronous journal owner; the event processor does not send synchronous network requests, nor does it promise that the IndexedDB transaction will be completed after a power outage. If the server saves successfully, it will only delete the corresponding record accurately according to the record ID, client revision and text hash. Older responses cannot delete newer inputs; if the server fails, is offline or has a revision conflict, the journal will be retained. When the conflict coordinates fall behind, the journal will be automatically saved and paused. The author will first compare and then explicitly restore or discard. The journal is a 168-hour (7-day), single-record/scope/global capacity-limited same-browser recovery interface. The unpublished plaintext UTF-8 IndexedDB payload is unencrypted and still has the risk of being readable by the local profile. It does not replace the long-term or cross-device admin-authenticated server draft; publishing, deletion, logout, number change, and private status cleanup delete applicable records. The retired `fsus:article-draft:create` and `fsus:article-draft:edit:*` localStorage metadata only deletes the key during editor initialization and private storage cleanup, without decoding or displaying its value. The mixed-release window of all drains after `server_revision` Expand to the old slot must be in the gateway fence draft POST/DELETE, leaving only GET; the CAS-less upsert of the old code does not belong to N-1 write-compatible. This fence is also a restart-free degradation path: existing drafts can still be read, and the client continues along the current `serverRevision` after write traffic is restored. The writing page calculates the title/description/canonical/OG image/slug preview from the site SEO configuration, and calls `/api/binary/author/prepublish-check` to check SEO, dangerous HTML, Markdown structure, text links and image alt before publishing or scheduled publishing; error items block submission, and warning requires the author to fill in the skip reason in the confirmation pop-up window and write `prepublish-warning-override` for audit. `/api/binary/author/preview` does not read or write the public article table, and directly renders the current form payload into restricted Markdown/AOT-like HTML, and displays it in a sandboxed iframe on the writing page. `article_revision` records the title, body, abstract, cover, category, label, revision number, diff summary, `created_by_admin_principal_id` and time when creating, updating and rolling back; revision writing executes `FOR UPDATE` on the `article` row within the article transaction and is covered by the `(article_id, revision_no)` unique index to avoid duplicate revision numbers generated by concurrent updates. The editor uses `/api/binary/author/articles/{articleId}/revisions` and a single revision detail to compare the current form with the historical version in the sidebar. After rolling back, the article update link is reused to trigger AOT/search/feed/binary cache invalidation and write audit. `content_asset` is the only asset metadata fact, and `content_asset_reference` is the only article/draft/revision reference fact; they are related by `AssetId` and not by URL or physical path as identities. `/api/binary/author/articles/{articleId}/assets/reindex` only returns the aggregated projection of the authoritative ledger, without scanning Markdown or rebuilding the second index. After the comment is created, the default is `Pending`. ### ZK-prod Anonymous comments on cryptography selection

[ADR-Anonymous-Credential-Blind-Issuance.md](architecture/decisions/ADR-Anonymous-Credential-Blind-Issuance.md) defines the current issuance: Credential collection uses RFC 9474 randomized blind RSA, the browser holds the finalized signature/opening/secret, and the issuer only handles blinded representatives. Comments prove that contract is fixed to `fsus.anonymous.comment.v5` / layout `6`. Currently, only the real blind issuance primitive, AEDS cross-stack and browser Finalize verification are completed; the current circuit-specific ceremony, proving key, verifying key and Wasm prover have not yet been run, so `production_usable=false`, blind signer and ZK ticket are closed by default. Credential possession and all stable credential material can only be current circuit private witnesses; ticket/public transcript still only allows scope-bound nullifiers. Any issuer/root/circuit/ceremony/verifier/prover gate that is not ready will fail closed and may not splice non-current artifacts, roll back deterministic verifier, or call the managed signature network.

The nullifier anti-replay of strong anonymous comments is divided into two stages: ticket issue only reads `comment_anonymous_nullifier` after proof verification to do blocked/scope-limit pre-check, and does not reserve or increment the number of uses; submit calls nullifier consume within the comment writing transaction of `CommentService`, using a single SQL to complete missing row insertion, blocked/limit determination, `use_count` atomic increment and `first_comment_id`/`last_comment_id` binding. Throws an anonymous nullifier rejection when consume rejects and rolls back comments, region compliance, and blocked-region writes, retaining single consumption semantics under concurrent submit while reducing issue + submit repeated DB round-trips.

The current canonical scope is article-bound v1: the top level `comment:v1:article:{articleId}:top` is used once per credential cycle, and the thread `comment:v1:article:{articleId}:thread:{rootId}` is used 3 times per credential cycle; the client proof scope, ticket payload, comment row and DB unique key use the same string. Old `article:{id}` lines will not be migrated or returned, but new tickets will fail closed; quota or ownership changes can only be released through the new scope version.

The comment strategy maintains a one-way dependency on `backend CommentPolicySnapshotPod -> binary comment adapter -> contracts/commentPolicy.ts -> API/composable/privacy adapter` on the frontend. The contract layer maintains the same wire field catalog as the back-end POD field set. The static test simultaneously compares the back-end struct, front-end catalog and business layer disabling rules; adding fields in the back-end or missing mappings in the front-end Decoder will cause verification to fail. The current 41-byte packed layout is client contract version 3. The historical layout only obtained `contract_invalid` through explicit mapper, which did not allow the business layer to maintain parallel narrow interfaces or optional readiness escape hatch. Runtime shutdown follows the reloadable ZK-Prod/anonymous-comments gate without restarting and does not change the binary frame number, notification stream or admin path.

The blind RSA issuer private key is the anonymous certificate issuance root key and does not belong to the web asset, uploaded assets or backup download side. `AnonymousCredentialIssuer:BlindRsa:PrivateKeyPath` only accepts native PKCS#8 DER, must be on a non-`wwwroot`, non-`uploads`, non-`backups` path and the Unix mode is not wider than `0600`. The read buffer is loaded and cleared once when the process starts; metadata and private key operations are hot-closed through reload-aware `BlindRsa:Enabled` gate during runtime. A fallback that does not require a reboot is to set this value to `false`; hot start and key rotation require a new process to be loaded and SPKI/root hash coordination completed first.

The preview output contains `data-preview-only=true` and `data-markdown-renderer=server-preview`, only the admin JSON API is used, the PublicAOT cache is not written, and the feed/search/sitemap is not entered. The subscription table only saves email hashes and channels to avoid extending site update subscriptions into social relationship chains.

## PWA and anonymous performance telemetry

`public/manifest.webmanifest` exposes installation capabilities; `public/sw.js` only caches public shell routes and search indexes, and does not cache `/user`, `/admin`, and `/login`. `/api/binary/**` includes the new public `.aeds` artifact which only uses service worker network transparent transmission. The browser cache strategy is completely determined by the negative response of server `Cache-Control`, `ETag` and `no-store` and is not written to the shell/search cache. The offline shell response comes with `X-Fsus-Offline-Stale: 1` and `Cache-Control: no-store`, making both the UI and the agent aware of stale content. `check:pwa-offline-smoke` must be run on the production preview or real production URL to verify that the latest public articles can be read offline and the private console route does not hit the cache when offline.

The front-end `telemetryService` collects the Core Web Vitals, hydration time, Wasm decode timing, Markdown render timing and navigation timing of the public page, and only records `pageType`, `aotSource` and numerical indicators; the private page does not send RUM events, and sensitive input does not enter the payload. Author dashboard aggregates P75/average, page type, and AOT source distributions from this table; RUM no longer consumes `sys_audit_log`.

`sys_audit_log` is a structured security audit table with fields including `source/type/action/outcome/severity/actor/target`, trace/path/method, privacy hash, `context_json` and tamper evidence. Ordinary Serilog events are still logged asynchronously through the bounded channel; the ordinary account dimension of the request audit/log context is written as `AccountId`, and the audit subject dimension is written as `AuditActorId`. The generalized `UserId` field is no longer allowed to be output. The mapper only generates actors from explicit `AuditActorType` + `AuditActorId`, does not promote bare `UserId`/`AccountId`/`AdminPrincipalId` in normal log context to audit principals, and will filter these identity plane fields. The `SourceContext` classification of `AuditLogEventMapper` first uses pre-compiled `FrozenDictionary` precise hits, and then uses the fixed rule table and 256-item bounded cache; 20+ switch/Contains serial scans for each audit event must not be recovered. High-value events in admin/security/audit are written directly and synchronously by `IAuditEventService`, and fall to `FSUSBLOG_DATA_ROOT/audit-fallback/critical-audit-*.jsonl` in case of failure. The writing side maintains the `chain_id -> record_hash` tail cache in the process; only in cold start or cache miss, `idx_audit_chain_tail (chain_id, id DESC) WHERE record_hash IS NOT NULL` is used to query the predecessor, and the tail cache is updated only after the batch insert is successful, maintaining the `prev_hash` link semantics without rollback. The audit query response defaults to `pii-redacted`, and the precise value of `IpHash`, `UserAgentHash`, `SessionIdHash` or `DeviceFingerprintHash` will not be returned to the ordinary `audit.read` admin; only the admin with `audit.investigate` explicitly requests `piiMode=investigation` to read the complete hash, and the read itself writes a high-value audit. `runtime.auditLog` of `/api/ops/health/ready-detail` exposes queued/dropped/writeFailure/fallback count; background `LogCleanupService` retains RUM for 14 days, access logs for 30 days, and cleans all audits according to the action-level limited cap of `AuditRetentionCatalog`. High-value/Critical only changes write reliability and investigation priority, and no longer means permanent retention.

`AuditDetachedCheckpointHostedService` periodically recalculates audit record snapshots, order-sensitive Merkle root, record range/head, and checkpoint predecessor in a separate ECDSA P-256 trust domain, and publishes it to `FSUSBLOG_DATA_ROOT/<Audit:DetachedCheckpoint:DirectoryName>` as `FileMode.CreateNew + fsync + atomic move`. Existing checkpoints are rechecked from the database before and after each append; modifications, deletions, rearrangements, full HMAC re-signing, checkpoint gaps/rollbacks, signature or key rotation exceptions are all failed closed. Workers are hot-deactivated via reload-aware `Audit:DetachedCheckpoint:Enabled`, without affecting audit writes or request surfaces; production startup requires independent DER key paths, relative data-root directories, and bounded period/batch configuration. The local directory only provides exportable detached evidence, not WORM; to resist the deletion of privileges on the same host, the package, public registry and expected head still need to be handed over to independent custody. This warehouse is not connected to the external TSA/S3/public chain.

`AuditRetentionPayloadProtector` encrypts actor/target/trace/path/network/device/reason/event/context sensitive fields with retention-epoch AES-256-GCM DEK before audit signing/persistence, retaining only ciphertext envelope, low-radix classification and epoch-keyed pseudonym inline. Cleanup strictly follows the action policy to execute "database snapshot and Merkle checkpoint → #1111 independent signature anchor → destroy batch DEK → write unidentified destruction evidence → active-release fenced delete"; if any step fails, the cleanup will not be declared successful. local fallback uses the same envelope and anchor/destroy/purge order. Database/local fallback is directly controlled by the application; backup/WAL/replica only accepts operator attestation with a limited time limit, site backup does not package `audit-retention/epoch-keys`, and external deletion of the platform must not be disguised as application completion.

Production readiness internally keeps a short-TTL `ProductionReadinessSnapshotCache`; during one refresh, the top-level PostgreSQL, Redis ping, RiskControl, and runtime snapshot tasks wait in parallel via `Task.WhenAll`. RiskControl reads only the Redis consume-once readiness result started by the upper layer and does not issue an independent Redis check in its own path. Configuration health runs `ProductionStartupValidator.ValidateCore` through `IConfigurationHealthSnapshot` at startup and in the background 30s refresh; `CheckConfiguration` reads only the snapshot and continues fixed-error-category redaction for public readiness. PublicHotRead, audit log, and runtime pressure snapshots have independent fanout within the runtime section. Observed metrics include `fsus.readiness.check.elapsed` and per-component postgres/redis/risk_control/runtime elapsed histograms for locating slow probe sources.

## Secure Link Overview

See [security.md](security.md) for details. The main security link is summarized as follows:

```text
Anonymous request
  → Rate Limiter (fixed_ip)
  → PoW Challenges (high-risk operations such as registration/login)
  → Password hash verification (BCrypt, cost ≥ 10)
  ↘ Passkey Verification (FIDO2 Discoverable Credential)

Authentication successful
  → AEDS auth frame + HttpOnly Cookie session（Short-term JWT is only used as internal issuance/verification details of the server)
  → Refresh Token（HttpOnly Cookie，`UserSession.RefreshTokenHash` Hash storage, CAS rotation system)
  → Optional: MFA TOTP challenge (MFA free with Passkey login)
  → Session logging (can list/revoke all others)

Request authorization
  → [anonymous] Public content endpoint
  → [authenticated] User endpoint (requires HttpOnly Cookie session / AEDS auth frame)
  → [admin] Management endpoint (requires `identity_kind=admin_principal` + specific `admin_permission`)
```

## Production Orchestration

```text
Host OpenResty (The only public network entrance)
├── active blue  -> 127.0.0.1:8081 -> fsus-app-blue / project fsusblog-blue
└── active green -> 127.0.0.1:8082 -> fsus-app-green / project fsusblog-green

Two-slot controlled sharing: external PostgreSQL, external Redis, uploads, DataProtection, read-only ZK material, append-only release assets, release-derived partitioned by releaseId
Strict isolation of two slots: container/project/release identity, instance-scoped tmp/runtime snapshots, Serilog logs
```

The production Compose has only one parameterized definition. The slot script always parses the blue/green container name, Compose project, loopback port, and derived volume. It cannot drift by copying two copies of Compose. `slot-preflight.sh` checks the Docker daemon, memory, Docker disk and image reserve, port and persistent active state before any pull/up; `slot-start.sh` only operates the candidate project, directly detects the live/ready of the slot, and then uses temp + file fsync + rename + directory fsync to update `/var/lib/fsusblog/deployment/slots.json`. If the candidate fails, only the candidate project will be cleared. `slot-stop.sh` refuses to stop the active slot from the persistent state; `slot-status.sh` cross-checks the state with the container label/health/loopback binding after the host restarts, and does not make implicit active inference. The lower limit of certification for zero-downtime overlap is fixed at 4 CPU / 6144 MiB memory / 10240 MiB free disk; 2C/2G only belongs to the single-slot profile. The lower slot preflight threshold is just pull/start guard, and the final impact of dual-slot, reload, drain, notification and P95/P99 is determined by continuous resource evidence.

The only entrance for production operators is `tools/deployment/release-rollout.sh`. `slot-start.sh`, `gateway-switch.sh`, `deploy-production.sh`, online migration, asset materialize/GC, and fence/restart helpers are all locked internal steps; `deploy-production.sh` rejects direct calls without internal slot tags, and `slot-start.sh` only accepts explicit one-time bootstraps with rollout inheritance tags or empty durable state. The rollout is fixed with mode-0600 durable state for 15 stages, each attempt and stage output hash; the failed stage cannot be retried before compensation is completed, the completed stage is not repeated when `--resume`, and there is no skip parameter for safety-critical access control. The irreversible boundary of Challenge-kind cutover is located in `source-drain` before activation: after the provisional gateway switch, first close the source issuance and wait for the in-flight, and then obtain the precise target authorization fence required for the endpoint; then persist the destructive marker, perform fixed operation ID cutover, receipt verifier and cross-backend/frontend/static binding. Only when all these steps are completed will `active-fence` revoke source ownership, recheck the target, and persist `activationCommitted`. Failure before the marker can be rolled back; after the marker, target activation can only be restored with the same operation, and rollback of the old source is prohibited. The final evidence is sealed with auxiliary hash receipt, acceptance and binding gate.

The main OpenResty configuration only includes `/etc/openresty/fsusblog/active-upstream.conf`; `gateway-control.mjs` can only generate one line of loopback server for the configured blue/green port, rejecting hostname, any port and multiple upstreams. `gateway-switch.sh` and slot start/stop share the host `flock`, and string target identity/loopback readiness, source public network identity, staged full-config test, fsync + atomic rename, installed config test, graceful reload, target public network/loopback identity and durable state commit into one `stable → switching → stable` transaction. When reload or post-detection fails, restore and reload source first. If recovery cannot be proven, `rollback_required` is retained. `gateway-rollback.sh` only consumes the previous release/digest; `gateway-recover.sh` does a deterministic reconciliation of pending state, controlled include, source/target runtime and public network headers after restarting, and cannot be guessed from the container age or mutable tag.

The application release status is managed by the singleton `DeploymentRuntimeState`, the production slot is fixed from `Starting → Candidate → Ready → Active → Draining → Stopped`, and startup or access control errors enter `Failed`; the immutable release ID, slot and positive integer deployment generation in the container environment are the only identities that activate/drain CAS. ## Runtime capability file boundary

Multi-node capability still obeys [monolithic-distributed-boundary.md](architecture/monolithic-distributed-boundary.md): homogeneous nodes run the same main application publication. `single`, `static-role` and `adaptive` only change runtime responsibilities, and cannot add fixed business sidecars or let domain modules directly sense nodes and transports.

Multi-node stateful responsibilities are unified through `Infrastructure/Distributed/StateControl`. `ILeaseManager` defines a single-writer partition as `responsibility + resource`; the lease has limited TTL, owner-bound renew/release, and monotonically increasing fencing token. Critical writes must verify lease identity and fencing token at the same time, and cannot only rely on node heartbeat or local cancellation to determine that the writer is still valid. `single` uses in-process implementation to maintain a single-machine hot path; `static-role` / `adaptive` uses runtime-scoped Redis Lua/transaction primitives. After the lease key expires, other nodes obtain larger tokens, and the checkpoint, complete, and failure write of the old node all fail closed.

Retryable background tasks use `taskType + objectId + operationId` idempotent keys and durable task records. The default semantics are at-least-once scheduling + effectively-once side effect: the same successful record returns completed replay and does not perform side effects again; running record only allows larger fencing tokens to take over after the old lease expires. Long tasks save checkpoints in compare-version, and the receiver restores from the last successful version. Failures are advanced in the `RetryScheduled -> DeadLettered | CompensationRequired` state machine; retry delay and max attempts are fixed policies from task registration and cannot be silently relaxed by the takeover node. The cluster failure detector is the first stateful responsibility to be connected, and only the current lease owner of `cluster:failure-detector` performs state transitions.

Calls between modules are unified through the stable contract of `Infrastructure/Distributed/Modules`. `single` directly calls typed local operation without querying membership or serialization; `static-role` / `adaptive` first selects local or remote path according to capability and active responsibility, explicitly selects queue for background and long tasks, and explicitly selects event for domain notification. The remote path propagates W3C trace context and enforces timeout, idempotent key-qualified retry, per-contract circuit breaker, and bounded concurrency backpressure. See [Module invocation and ownership boundary](architecture/module-invocation-boundary.md) for module data ownership, version compatibility rules, failure semantics, and drain/recovery paths without restarting.

When Redis is temporarily unavailable, multi-node acquire/mutation fails and new stateful writes are stopped; existing anonymous, login, admin, notification stream and binary request paths do not pass through the coordinator and continue to work according to their original contracts. A partial rollback that does not require restarting is to mark the affected node with `Draining` or remove the corresponding active responsibility, allowing other healthy nodes to take over after TTL; it must not be stored in the multi-node mode rollback process. To restore `single`, the operating mode must be switched via the next process generation, and the stored true source cannot be hot-swapped.

Search index, article service, PublicHotRead and application composition still organize capability files by orchestration, policy/state, I/O/persistence, codec/routing and metrics. Authoring is changed to five scoped modules: analytics, asset library, draft lifecycle, content transfer and moderation workflow, which have independent construction dependencies and failure/transaction boundaries; endpoint only looks at narrow ports, and any module must not pass the original aggregation through another implementation class or `IServiceProvider` callback. The managed capability file must be less than 1,500 lines, and `backend-build-governance` performs machine checks; behavioral testing of the final endpoint data source and DI descriptor is responsible for proving that the authoring 58 method/path, admin permission, frame lookup, and scoped lifetime have not drifted. For historical background on capability slicing, see [Runtime capability slices and source-file budget](architecture/issue-1119-runtime-capability-slices.md).

Schema migration no longer uses runtime service partial. `SchemaMigrationRegistry` only exposes the execution plan verified by `SchemaMigrationManifest`; the release-range catalog declares this range descriptor, and the domain-oriented definition type carries the historical SQL/step that cannot be deleted. The manifest verifies ID uniqueness, phase + migration ID monotonic order, catalog range, phase-tail dependency and explicit gap before database access, and the runner no longer rearranges the array by itself. Both the empty library and the 20260517 representative history fixture must keep their respective columns/indexes/constraints snapshot, history, and data conversion results unchanged before and after repeated execution. For catalogs, version boundaries and new migration rules, see [Database Migration Runbook](database-migration.md#versioned-legacy-catalog).

## PerceptionCharacterV3 provider

`SecurityChallengeOrchestrator` passes the envelopeId to the V3 provider after generating it. V3 provider only relies on `IPerceptionCharacterV3ArtifactPool` and no longer relies on request-time renderer, render semaphore or codec queue. The active identity still consists of the authoritative subject/server-device/IP/action/route without the envelopeId for each refresh. The pool entry is permanently burned by Redis Lua `SET NX` before responding; then the record is read and authenticated from the immutable pack offset, and the `artifactHash` of the exact transported bytes then enters the answer HMAC, AES-256-GCM opaque state and Redis authoritative row. Redis reply loss, response cancellation, state creation failure or encoding failure will not return the entry; the media will not be returned when Redis creation fails. visual/audio replacement uses the old envelope + opaque token + all bound to the same Lua transition atom to revoke the old challenge, then rent a new entry and generate a new envelope/challenge/token/attempt identity. If replacement fails, the old identity will not be revived.

`IPerceptionCharacterV3ResourcePlanner` is the only V3 allocation/disposition owner. The immutable input includes the active generation's visual/audio/total ready inventory, current watermark, action coarse class, risk/escalation, certification and Passkey assurance, and Redis/pool health; output is only allowed for `allocate-v3`, `use-credential-step-up`, `require-cheaper-proof`, `queue-for-moderation`, `throttle`, `block`, or `unavailable`. Public read does not consume V3 by default; low watermark converts unnecessary comment/write to review or cheaper proof; critical watermark is only reserved for the configured recovery/admin security action; empty, revoked, corrupted and Redis unavailable use the action disposition table and never generate `allow`. The provider only executes planner output and does not maintain the second set of fallback.

The pool manifest v1 adds an exact `artifactBytes` to each entry that has been verified by initiating full decryption with an ignorable additive field to the old runtime. The same Redis Lua online linearization point checks generation revoke, operation retry fence, visual/audio/total inventory, minute + rolling-hour lease/egress budget, and IP prefix/server-device/subject/action quotas; only if all pass, it will burn entry, decrement ready, increase leased, record exact bytes and operation identity at the same time. After the return packet is lost, the operation fence prevents retry from renting another item or repeating the billing. Inventory and metrics only use generation state, representation, watermark, coarse action/disposition and exact byte count, and do not include raw IP, challenge ID, token, answer or media.

The same planner only generates bounded entries/bytes plans for idle/offline replenishment; output stop when public request, CPU/memory/I/O/latency pressure, unhealthy pool or high watermark is reached. Active generation must not be switched on generation failure. `Security:PerceptionCharacterV3:Resources:AllocationsEnabled=false` takes effect in the next plan by reload-capable configuration without restarting; it only stops new allocation and forces action disposition, does not revive the retired generation, and does not change the existing verify/cancel drain.

Orchestrator first creates a complete plan based on server-owned cost class and only issues the first item; envelope Redis state saves planned challenge IDs, ordered kinds, binding, policy, pre-selected visual/audio representation and version. Before verifying the current member, CAS `issued -> verifying`, only the winner can consume the provider proof; after success, CAS sets the next item to `issuing`, only the winner can call the next provider, and then set it to `issued` with challenge ID/version. Therefore, the V3 pool lease in `PoW -> PoSpace -> V3` is unreachable before the first two items are completed, and delayed issuance will not reselect the representation from the verify request; concurrency/reply loss will leave at most a fail-closed transition, and the proof will not be consumed repeatedly, the provider will be called again, or the second item will be leased. Downgrades without restarting are stopped by the hot RiskControl policy; the existing planned chain will still expire or be revoked according to the original policy/binding.

The offline pool builder is the only executable owner of reference raster/audio/codec: it generates full PNG/Ogg per machine contract, checks hard limits, encrypts each record with a dedicated external key and fresh nonce, and writes a compact offset/length manifest. The runtime startup performs complete verification on the manifest, pack, each AEAD record, contract/artifact digest, duplicate ID and representation; during the request period, it only loads the index, reads the burned single record, calculates the request-bound HMAC and clears the five-byte answer buffer. Redis only holds lease/revocation metadata, not complete media or answers; the runtime does not splice PCM, does not call external TTS, and does not give the client unit/label/recipe.
