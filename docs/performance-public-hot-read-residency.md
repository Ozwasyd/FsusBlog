# PublicHotRead residency, admission, and snapshot lifecycle

## Physical model

Before candidate publication, `PublicHotReadResidentAccounting` generates `independent-readonly-arrays-upper-bound-v1`. Array-backed `ReadOnlyMemory<byte>` charges full backing capacity, not logical slice length; if the backing array cannot be resolved, it conservatively charges logical length. Frozen maps, entries, keys, ETags, cache-control, template strings/offsets/hashes use stable upper-bound constants. The model may overestimate shared strings and map layout, but never reports unknown overhead as zero. Backing arrays above `85,000` bytes count as LOH-eligible. Runtime telemetry separates raw AEDS, br, gzip, HTML/template, key/index, article/list/taxonomy/HTML, base/overlay/removed, artifact/object/array, and LOH bytes.

With no configuration, limits derive from `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes` and therefore observe container/cgroup memory. Default resident is `1/8` of available memory (64 MiB–2 GiB); raw is `3/4`, compressed `1/2`, HTML `1/2`, candidate/current overlap is `2x` resident, and article detail is the lesser of resident `1/2` and raw `3/4`. Explicit values must still fit the combined Blue/Green two-slot, SSR-worker, managed-heap, and system-headroom budgets.

## Admission and storage choice

Taxonomy, home, archive, hot, and featured lists are always built as critical artifacts. Article-detail candidates interleave view-hotness and recently published segments in deterministic order, subject to both `MaxArticleFrames` and `MaxArticleResidentBytes`. Mutation/view deltas place changed articles at the front of admission, then eviction is deterministic by artifact version/article ID. Non-admitted articles continue through the existing versioned L1/L2/DB binary endpoint path and backfill; AEDS v2, ETag, visibility, and invalidation are unchanged.

The current design uses independent read-only arrays, not a contiguous pack/mmap: the L0 writer already consumes `ReadOnlyMemory<byte>`, snapshot swap replaces references, and packing would add one full copy and a larger publish-overlap peak. If data-scale evidence shows object count, LOH, or GC pause becoming the saturation resource, a release-scoped immutable pack may be introduced only with release/digest binding, offset/corruption validation, N/N-1 retention, and proof that slices remain zero-copy.

br/gzip are generated only during publish/backfill and only when `MinPrecompressedFrameBytes`, `MinCompressionSavingsPercent`, and expected client share all allow them. Default share baseline is br 80%, gzip 15%; a variant below 5% is not resident. Requests select an existing variant and never compress inline. Striped counters record actual `identity/br/gzip` negotiations and expose them through the operations snapshot and `fsus.hotread.encoding.*`. Each release must update expected share from observed distribution; the default baseline cannot stand in for long-term client evidence.

The local release profiler (`bash tools/test/lanes/public-hot-read-residency-profile.sh`) used a 12,000-article, 2,048-byte raw-frame fixture with br 80%/gzip 15% and admitted 6,000 articles. Repeated 2026-07-14 evidence: snapshot upper bound 16,770,460 bytes; raw 12,288,000; compressed 3,071,400; key/index 1,411,060; 41,406 objects; 11,700 arrays; LOH-eligible 0; process RSS delta about 63–64 MB; forced full-GC pause about 40–65 ms; and 95.007% hit rate over 100,000 skewed requests. It passed the dynamic container-visible budget, RSS `<= 2x resident budget`, full GC `<= 1,000 ms`, and hit rate `>= 90%` gates. These are local release evidence, not cross-machine promises; regenerate `.tmp/release-evidence/public-hot-read-residency-profile.json` for every release/data-scale change.

## Lifecycle, evidence, and rollback

Stages are `build -> validate -> admit -> publish -> retire -> active`. The projector owns build/admission; the store aggregates all budget violations before atomic swap. On rejection, the old snapshot stays active. After a swap, the store tracks retiring snapshots in a weak-reference set without extending their lifetime. Weak retiring references are residency/GC overlap only and are never a request-serving store. A Ready, integrity-valid generation is strongly retained as last-good so new allowlisted requests can still receive `200` after `MaxSnapshotAge`, while a coalesced refresh is scheduled. Distributed invalidation must name its policy: `DropToEmpty` clears current and last-good (`invalidated-drop-to-empty:{reason}`); `RetainLastGood` keeps the strong last-good generation requestable until the next publish. Metrics distinguish `fsus.hotread.fresh.hit`, `fsus.hotread.last_good.hit`, and `fsus.hotread.sanity.fallback` (endpoint fallback). The next candidate's overlap includes current, candidate, and every old version still held by a reader; after the last reader releases, GC may reclaim it. `MaxRetiringBytes` is a dynamic hard gate under the same publish lock. `MaxRetiringSnapshots=0` and `RetiringSnapshotDeadline=0` do not treat uncleared weak-reference count/age as publication failure; positive operator values enable those gates. When a weak target is released, remove it in oldest-retirement order and record eviction; while a request holds it, tracking cannot be deleted to force release, and its bytes remain in overlap/retiring budget. Exceeding bytes or an explicit count/deadline rejects the next version. A zero deadline permits a fresh full refresh to replace a stale active snapshot, avoiding permanent publication lockout under low GC pressure. Merge the HTML overlay and removed set at `max(32, base/4)` to prevent unbounded delta growth.

The Public AOT shell memory tier has count/bytes/deadline bounds and access-order LRU. When `PublicAot:MaxMemoryCacheBytes`, `MaxMemoryCacheEntries`, and `MemoryCacheEntryDeadline` are zero, derive them from container-visible memory; each read/set/snapshot first removes expired entries, and a set over count or bytes evicts the least recently accessed items one by one. Eviction falls back to the versioned file layer on the next read; it does not delete the disk artifact or change PublicHotRead, binary, or notification-stream semantics.

Protected `/api/ops/health/ready-detail` and author-operations health expose complete residency/budget/overlap/lifecycle data. OpenTelemetry exposes `fsus.public_hot.resident.bytes`, `snapshot_overlap.bytes`, `loh_eligible.bytes`, `artifact_objects`, `fsus.public_hot.retiring.bytes`, `fsus.public_hot.retiring.evictions`, `fsus.public_aot.memory_cache.resident_bytes`, and `fsus.public_aot.memory_cache.evictions`. Release/data-scale evidence must retain these fields under one release identity together with process RSS, managed heap, LOH, and GC pause; final gates cannot substitute payload counts for RSS.

No-restart degradation order: lower AOT memory-cache count/bytes/deadline so reads fall back to files; raise minimum compression savings or lower the corresponding client share; lower article resident/count and trigger `public-hot-rebuild`. On a retiring-deadline alert, stop new snapshot publication and let current readers finish naturally; if the issue persists, set `PublicHotRead:Enabled=false` to hot-degrade to the regular binary/cache chain. Anonymous, logged-in, admin, notification-stream, and binary-fallback paths retain their existing pipelines; never disable CSP, PoW/risk controls, security headers, or invalidation. Restore the old configuration and rebuild to roll back; no restart is required.
