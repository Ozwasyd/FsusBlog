# 站点账号二次验证

站点账号在 `/user/identity/mfa` 管理 TOTP。该页面沿用 v1 的路径，并用当前 AEDS 帧 48–52、54 和 55 调用账号接口。首次绑定需要当前 Passkey 会话重新签名，服务端把时限为 5 分钟的一次性 `mfa_setup` 授权绑定到账号、会话和代次。浏览器在同一会话确认验证码后启用 TOTP，并获得 8 个一次性恢复码。页面只显示这一次，代码应立即存入可信的密码管理器。

已经启用 TOTP 的账号先完成 Passkey 签名，得到 v1 `AuthLoginFlow` 的 `mfa_required` 阶段。浏览器提供验证码或恢复码后才建立会话。挑战与浏览器的 HttpOnly cookie 绑定。数据库事务保护 TOTP 时间步、一次性恢复码和会话。恢复码含 128 位随机数据，库中保存摘要。单个账号连续失败五次后有五分钟冷却。启用与停用在同一个事务中推进账号代次、撤销所有旧会话凭据，并为当前浏览器签发保留原到期时间的新凭据。当前额外授权只认识 `mfa_setup` 和 `mfa_disable`，二者不能互换，也不能授权管理操作。

运行时设置 `FSUSBLOG_PASSKEY_ORIGIN`、`FSUSBLOG_PASSKEY_RP_ID`，并从独立的密钥存储注入 `FSUSBLOG_TOTP_KEY_HEX`。该值为随机 32 字节密钥的十六进制编码。TOTP seed 使用 AES-256-GCM 与账号关联数据加密，数据库备份和密钥须分别保管并成对进行恢复演练。配置缺少密钥时，已经启用二次验证的账号无法通过仅有 Passkey 的登录。当前格式含封装版本，生产密钥轮换和 v1 现存 TOTP 凭据迁移仍需离线实现。

原生 PostgreSQL 18 验证覆盖旧时间步和恢复码重放、动作与会话绑定、代次撤销和密文认证。Chrome 157 使用虚拟 CTAP2 认证器跑通首次绑定、Passkey 与 TOTP 登录、一次性恢复码登录、二次验证停用和停用后的 Passkey 登录。用例见 `tests/EndToEnd/mfa-flow.mjs`，需隔离测试实例及新的一次性 Passkey 绑定票据。测试截图省略 seed 和恢复码。RFC 6238 的标准 SHA-1 向量在 `tests/Core/TotpTests.cs` 复验。

本地迁移命令在空库建立当前 schema。旧版 v2 若缺少本次新增的表和列，需要专门的升级脚本。启用时若响应丢失，用户可以用已绑定的认证器重新登录。恢复码轮换完成后才能补发替代码。

其余范围包括 MFA 重绑、恢复码轮换、过期绑定记录清理、独立管理员、v1 风险控制、迁入的真实密钥恢复及硬件认证验收。
