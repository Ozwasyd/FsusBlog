# P2 · 首条发布闭环验收与公开读取负载

本文件冻结首次 P2 验收候选的场景、环境和测量口径；还没有测试结果。技术边界来自执行计划、[v1 界面证据](v1-ui-evidence.md)及 #1950 的运行归属要求。本文的 10,000 QPS 是单机公开读目标；其余性能数字是首次 P2 测量使用的 v2 工程预算，不是 v1 实测线、既有 SLA 或凭本地试跑即可宣称的结果。

## 功能验收

P2 测试使用新建的独占 PostgreSQL fixture、实际 Server、实际 v2 静态构建和独立浏览器 context。每个场景记录输入、身份、前置状态、操作、外部可见结果、持久化结果和失败结果。运行报告把下面的 `P2-*` ID 对应到当前提交的实际命令、原始日志和未覆盖项。

| 用例 | 输入 / 身份 / 前置 | 操作 | 可见结果 | 持久化结果 | 反例 / 失败结果 |
| --- | --- | --- | --- | --- | --- |
| P2-01 真实身份边界 | 一次性运维接入票据，匿名浏览器、已授权操作者和无写权限身份 | 消费票据并进入写作，重新使用票据，从另一个 context 直接调用写 API，再注销或撤销当前会话 | 恰好一次消费可以获得实际会话；新身份确认之前没有“成功登录”状态；无授权时没有写作动作或数据 | 会话及撤销状态可复查；票据、会话机密不写进 URL、截图、日志、Web Storage 或持久化的客户端路由 | 无效、过期、跨会话/跨身份、重复和已撤销凭据拒绝；准入查验错误不能让匿名写入 |
| P2-02 保存和并发 | 同文章、同一预期修订的两个并行写操作，不同幂等键 | 竞争保存；再用胜者的原始身份和幂等键重放同一请求，最后重用键但改内容 | 恰一个保存成功；落后写入稳定冲突；完全一致的重放返回原结果，改内容的重用不视为原成功 | 新修订、幂等记录、事件只出现一次；失败请求不覆盖胜者 | 错误文章、旧修订、错误站点、不同身份或无授权均不覆盖；不能按客户端上报的摘要授予权限 |
| P2-03 持久化边界 | 新草稿、可控事务故障点、数据库中无同键命令 | 在持久化提交之前注入故障；重启并用同键重试；另测提交后客户端失去响应 | 未提交不显示“已保存”；重试按原命令身份归属收敛 | 事务失败不留下头部、修订、幂等结果或 outbox 半写；提交后的重试不新增记录 | 禁止用 mock 数据库/内存队列代表真实故障测试 |
| P2-04 发布坐标 | 有草稿修订，未发布时匿名 HTML、AEDS、静态索引不可见 | 授权发布；在发布投影尚未准备好和准备好以后分别读取；然后制造一次投影重试 | 全部入口消费同一公开坐标；未就绪不能逐路暴露半成品；200 的 HTML、AEDS、搜索文档写入同一修订正文与标识 | 文章生命周期、修订和待投递事件的提交可查；消费者重复投递不产生第二代等价发布 | 任何一项投影失败，不能让部分公开路径先变更；可重试与永久无权分开 |
| P2-05 AEDS 交叉证据 | 固定版本契约、独立 golden 和边界输入、真实服务器响应 | 解码服务端 200/错误帧，检查媒体类型、头、FrameType、长度及独立向量；提交截断、未知、超预算数据 | 正常语义一致，畸形输入得到稳定错误；没有 JSON 业务 fallback | 非法输入没有副作用，日志没有凭据或私密正文 | 一端自己生成且用同一代码回读，只作为局部回归；不得计为跨语言或 golden 验收 |
| P2-06 正常首屏和搜索 | 带唯一词的已发布文章、无 cookie 浏览器 context | 直读页面原始 HTML；从首屏激活页面后再读；加载静态索引搜索；重复做窄屏、明暗、键盘导航 | 首响应已有正文与恰当元数据，水合不更换公开版本；浏览器本地检索返回相同修订；实际 FsusUI DOM、可达焦点和合理空错加载状态 | 匿名读不创建业务数据；成功热读持久层访问计数为零 | 验证正文中标记是 fixture 真正文；假登录、静态截图、客户端满屏回退、假索引不计通过 |
| P2-07 撤回和失败闭合 | 曾经公开且已热读的文章及搜索索引；保持已打开标签和独立无 cookie context | 授权撤回，等待服务器给出完成结果；请求 detail HTML、AEDS、最新索引和旧代索引，用旧 ETag/缓存重复；隔离故障下反复读取 | 确认撤回后没有新的 200 泄漏正文；已撤回为权威 404 或证据不明时为 no-store 503。已下载到本地的字节无法远程擦除，但不能新发放含撤回数据的旧快照或将其重新装入索引 | 撤回修订/事件和无资格坐标可查；投影失败或重启不得复活旧公开内容 | 暂时故障不能让撤回、私密、越权或已删除内容走 last-good；必须验证下载旧代和条件请求不泄漏 |
| P2-08 重启/热命中/冷刷新 | 当前 schema、已提交 outbox、热快照、一个未驻留键、只影响此 fixture 的故障配置 | 正常重启重建，再对冷键同发请求；运行热基准；分别测失败拒绝与重新可公开后的恢复 | 热返回准确字节且无数据库/Redis 访问；冷键请求合并、等待有界、响应可取消；条件不明时明确拒绝 | outbox 不丢；重复投递后公开坐标不回退；启动不会自动 DDL 或改旧结构 | 冷/热混报、以缓存无效读充成功、用另一个进程已热资源代替准入，均不计入通过 |

P2 一次性运维接入票据是此切片的真实接入边界。UI-06、UI-07 中的 v1 Passkey 登录/注册、MFA、恢复、独立 admin principal 流程仍需按身份域交付；P2-01 的结果不填入这些用例。发布成功语义以服务端实际状态为依据，若返回“命令已提交、公开投影处理中”，测试须区分两者，不把前者当成公开已完成。

## 负载协议 v1

### 固定 fixture、路由与资源

目标服务是一个 Release build、一个 v2 应用进程、专用 PostgreSQL 数据目录和一个站点；单机模式不用 Redis 若该配置不需要它，实际启用与理由写入运行记录。不同部署形态分表记录。参考环境为 Apple M1 Pro（6 性能核＋2 能效核，16 GiB 统一内存，arm64），首次静态检查为 MacBookPro18,3 / macOS 27.0.1。实跑重取硬件/OS、可用内存和供电状态。共享本机或故障 fixture 的结果可用于诊断，但只有供给者有足够余量、服务及资源归属可验证的运行可以验收。代理链测量须使用拟交付的实际代理/TLS 配置，记录 HTTP 版本、TLS、压缩、keep-alive 与拓扑。代理应将请求送到 Server，不用代理或 CDN 响应缓存满足应用层目标。无法取得合格代理环境时单列缺测；直连数据不能代填。

- 固定输入为 12,000 篇发布文章、32 个分类、128 个标签；另有 50 篇私密/草稿、50 篇专用于后续撤回，不进入稳定热基线的选择集合。按 ID 以公开 seed `20261114`、稳定排序、可独立重新生成的确定性 fixture 导入，不得用真实生产内容。文章正文 UTF-8 输入大小为 2 KiB、8 KiB、32 KiB 三档，占比分别为 70/25/5%，题名含 ID 和搜索词。发布均匀分布于过去 365 天。摘要与正文有稳定多词序列，不能用重复单字制造可异常压缩的数据。每个 payload 记录实际编码前后字节量和摘要。
- 热请求选择公共、已发布、已驻留的 1,200 篇；命中前先完整校验每个抽样路径的状态、预期正文、内容类型、投影坐标和解码。上游输入数据为 12,000 篇，热集不是全部内容。工作负载依确定性每百个请求选择：HTML 首页 20、HTML 详情 30、AEDS 首页列表 20、AEDS 详情 30；详情选取按 seed 固定，80% 从 ID 1–120，20% 从 121–1200；首页列表固定第 1 页、20 条。端点以 v2 对应实际契约为准，执行前记录方法和路径；缺任何路由即为本用例缺测，不能把它的比例移给更快的路由。搜索投影大小、生成和下载另测，不在 10k 热读分母里。
- 热测全部 GET、去凭据、请求完整响应体且不发送条件请求，禁用客户端重试和跳转。Kestrel 直连使用 `identity`，HTTP/1.1 keep-alive，最大 256 个进行中请求；代理链同为 `identity` 的等口径试验必做，可额外测真实的生产压缩组合但分开报告。超时固定 2 s；HTTP 200 正确字节才是成功。每个响应读至流结束，验证状态、长度、路由类型和公开代次，每 1,000 次请求至少做一次预期内容摘要核对并将校验时间计入供给者成本。无效 2xx、304、429、5xx、取消和超时不是成功。
- 冷测用不在驻留集的三个已公开详情键并分别启动 64 个同时请求，另针对 64 个不同的已公开键同时请求以观察并发上限。冷样本用独立命令/状态准备，每轮复查缺页真实成立；记录等待/取消、刷新启动次数、并发度与错误；逐键至多一个实际重建，正常 fixture 的等待端不得超过 750 ms，leader 在 2 s 内完成或按预算拒绝。错误可重试但不能变成错误的公开状态。另对 P2-07 撤回集合验证旧代失败闭合，故障窗口不与正常热读结果混在一起。

### 步骤和通过条件

1. 独占准入后先绑定提交、构建、SDK/运行库、各锁文件、数据库版本与 schema、fixture digest 和实测工况。启用真实请求安全/缓存路径，禁用测试专用快捷响应。预热 30 s（2,000 QPS），确认路由驻留；热阶段开始前归零/标记访问、拒绝和消费 counters。
2. 使用定速供给，每种拓扑以 2,000、5,000、8,000、10,500 个请求/秒各稳定 60 s；每级间隔 15 s 只作冷却，按固定配置重新预热，记录实际送达与供给者漏发/阻塞。10,500 档在两次独立、相同输入的运行中均须 **10,000 正确响应/秒以上**，p95 ≤25 ms（直连）/ ≤40 ms（代理 TLS），p99 ≤75 ms / ≤100 ms，错误、拒绝、超时与漏发合计 ≤0.1%，没有私密数据误发。每个阶段报告每类路径的数量和延迟，不用混合分位隐藏慢路。供给者打满资源或送不进目标流量时记录为供给不足，不把较小负载越线算完成。延迟从计划发送时间算到完整 body 读取完成，以暴露排队。
3. 在 8,000 个请求/秒重复 15 分钟（在已通过短档后）；采样进程 RSS、高水位、managed allocated bytes、GC 次数/暂停分位、堆、队列深度、刷新次数和 DB/Redis 查询。应用只因命中的数据路径发出的 DB/Redis 查询必须为零，访问数与后台刷新/诊断分开；若计数不能归因，本项缺证。稳定后 RSS ≤1.5 GiB，末 5 分钟 RSS 中位比第 6–10 分钟的中位最多增 10%，队列不持续增长。报告每响应分配和延迟/GC 趋势，不把小样本当无泄漏证明。
4. 在独立故障阶段执行 P2-03/04/07/08，保留第一次阻塞原因。沿用相同构建，不将错误阶段从证据中删掉，不拿另一个通过的 attempt 覆盖。

容量测试的资源所有者每次必须有新 `runId` / `invocationId` / `attemptId`，在启动供给者前绑定同一轮的实际数据库、进程、网络/端口、拓扑、启动与就绪探针、初始状态和摘要。旧/跨提交/跨 fixture/owner 死亡/未就绪/篡改的证据拒绝准入；记录失败，无需寻找近来的 receipt 碰运气。开始与结束时间、精确命令、原始报告、输入/输出摘要、退出码、进程配置和资源/GC 采样归档。正常、失败、中断后都查证此轮拥有的进程、地址、数据库目录和 fixture 文件已按约定撤下；其他人的服务或目录未触碰。已授权的 Docker 测试由外部执行环境承担并单列。

最终报告必须区分：未运行、环境阻塞、未实现、局部试跑、完整运行失败和完整通过。没有 v1 同工况数据时，10k 通过只支持 v2 的绝对结论，不支持宣称等同或超越 v1。
