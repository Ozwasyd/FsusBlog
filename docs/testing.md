## Catalog-driven bounded queue drain matrix

`drainParticipant: true` in the sole bounded-channel catalog is the participant admission boundary. `BoundedQueueDeliveryCatalog` loads that same embedded catalog, and `BoundedQueueDrainAggregator` accepts exactly one registered adapter receipt for every participant queue. A receipt is current-run and content-addressed: it binds queue identity, delivery class, generation, sequence, queued/in-flight/durable-pending/terminal counts, commit postcondition, and any class-valid drop proof. Missing, duplicate, unknown, stale, cross-run, underflowed, observer-unavailable, or digest-mismatched observations fail closed. A rejected generation/sequence regression or content collision must not replace the participant watermark; rereading the same rejected snapshot cannot make health, readiness, or qualification succeed. Digest-, run-, or catalog-binding-invalid receipts cannot establish the watermark; correcting only their envelope can recover without changing the queue version, while valid pending receipts still advance monotonic observation.

The release drain wrapper and `ProductionHealth` both consume the aggregate; health, readiness, and qualification are not computed from a second queue list or a `QueuedCount`-only shortcut. Queue adapters only expose existing queue-owned snapshots. The PublicHot adapter remains a wrapper around the authoritative PublicHot activity/quiescence APIs and does not copy or change PublicHot delivery behavior.

`tests/backend/Unit/BoundedQueueDrainAggregatorTests.cs` enumerates `BoundedQueueDeliveryCatalog.Embedded.DrainParticipants` and executes the deterministic ten-case matrix for each queue: `exact-drain`, `queued-pending`, `in-flight-pending`, `durable-pending`, `terminal-failure`, `commit-postcondition-unknown`, `drop-proof-mutation`, `worker-crash`, `cancel-timeout`, and `restart-generation-regression`. The test asserts `catalog participant count × 10` fixtures, keeps peer receipts unchanged when one queue fails, and requires identical health/readiness/qualification status from the aggregate. Per-queue failure semantics, proof references, qualification impact, and recovery disposition remain in the catalog and are the queue-specific runbook; no universal delivery policy is inferred.

### Performance saturation evidence v2

The normal load profile continues to be responsible for regression and availability, but no longer has the authority to draw conclusions about capacity. `tools/perf/run-open-loop-load.mjs` sends requests according to a fixed arrival time. Slowing down the request will not reduce the offered load. Each offered-load step is repeated at least three times; when the press CPU reaches the policy upper limit, schedule lag p99 exceeds the limit, or dropped arrival is non-zero, the load generator itself is judged to be saturated, and the server-side inflection point cannot be inferred based on this. Failed transport samples retain the existing immutable raw evidence, cleanup proof and first-failure diagnostic. Controlled fixture tests demonstrate these rejection controls only; current source/candidate binding and real runtime qualification remain required.
- Warmup binary responses are checked after the original plan joins its workers. A failed response retains diagnostic warmup raw observations, runs the original cleanup owner and stops before sampling. Diagnostic-write errors cannot skip cleanup; incomplete or throwing cleanup is retained alongside the original failure. Warmup diagnostics cannot qualify as a sample receipt.
- Logical bytes and backing capacity are independent hard budgets. Fault scenarios must retain injected/observed timelines and the first failing request with its command trace; a successful rerun cannot erase the first failure.
- Two-node scenarios must prove actual route, durable-row convergence and residency convergence. Every run must remove its namespace and drain active keyed entries before a receipt can pass.
- Each runtime probe must write `observabilityLevel` and `extendedObservability`. `extendedObservability.categories` contains at least three types of extension fields: `managedRuntime` (managed runtime mode, such as runtime, NativeAOT, ReadyToRun, TieredPGO), `threadOrConnection` (thread or connection class readings, such as probe concurrency, sampleCount, active handles), `storageOrCacheLatency` (storage or cache latency, such as cache-backed HTTP p95, Postgres ping, Redis ping). Each field must have `status`; if it cannot be collected, `reason` must be written. The validator will mark evidence that is `ok` in all three categories as `extended-runtime-evidence`, otherwise mark it as `basic-runtime-evidence` and ask for the missing reason.
- QPS, latency, cache hit, compression and static file results must not be mixed with Kestrel-only and proxy layer results.
- If `baseUrl` points to nginx/CDN/reverse proxy, `optional_deployment_layer` must be retained in the evidence and the proxy caching, compression, and buffering settings must be stated separately.
- In-project optimization issues must not count CDN, nginx proxy cache or proxy compression as acceptance benefits.
